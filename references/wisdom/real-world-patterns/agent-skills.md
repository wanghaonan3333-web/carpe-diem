# 实战模式：用 Agent Skills 装备真实世界的 Agent

> 来源：Anthropic Agent 设计模式、LangChain 技能系统、社区工程实践
> 蒸馏日期：2026-08-30

## 问题本质

通用大语言模型拥有广泛的知识，但在特定领域任务中表现不稳定——它不知道你的代码库命名规范、不理解你的业务流程术语、不清楚你的合规要求。每次重复描述这些上下文既低效又容易遗漏。Agent Skills 是一种将「领域知识 + 操作流程 + 约束条件」打包为可复用模块的工程模式，让 Agent 在需要时按需加载，而非在 System Prompt 中一次性塞入所有知识。

## 关键洞察

- **Skill 是「知识 + 流程 + 限制」的三位一体**：一个完整的 Skill 不仅包含领域知识（什么是 XYZ），还包含操作流程（如何做 XYZ）和限制条件（做 XYZ 时不能做什么）。缺少任何一环，Agent 在复杂场景中就会走偏。
- **按需加载优于全局注入**：将 20 个 Skill 一次性塞入 System Prompt 会导致上下文爆炸和注意力稀释。Skill 应该像函数调用一样——Agent 在需要时主动选择加载，用完后卸下。这要求 Agent 框架支持动态 Skill 检索和路由。
- **Skill 的粒度决定复用率**：太粗的 Skill（如「做市场营销」）内部逻辑耦合度高，难以跨项目复用；太细的 Skill（如「给邮件写标题」）Agent 可能根本不知道何时调用。最佳粒度是「一个任务目标 + 一个可交付物」——如「生成竞品分析报告」「提取会议待办事项」。
- **示例比规则更能塑造行为**：Skill 中包含 2-3 个具体输入输出示例，比十行规则描述更能让 Agent 稳定输出预期格式。示例应覆盖：正常情况、边界情况、一个常见错误及纠正方式。
- **Skill 需要版本管理和质量门禁**：Agent 无法区分「好的 Skill」和「过时的 Skill」。引入显式的版本号、最后验证日期、依赖关系声明，以及一个质量门禁（如：必须通过至少两次真实任务测试才能标记为 stable），防止 Agent 被劣质 Skill 误导。

## 对 Carpe Diem 用户的启发

### Discover 阶段

在探索阶段，用户需要快速验证多个方向，Skill 可以帮助他们标准化探索流程：
- 创建「行业调研 Skill」：包含数据来源清单、PEST/波特五力分析模板、输出格式要求——每次调研新行业时直接加载，无需重复描述调研方法
- 创建「用户访谈 Skill」：包含访谈提纲模板、追问策略、关键发现提取格式——让 Agent 在分析用户反馈时保持一致的输出结构
- 鼓励用户为高频重复的探索任务建立 Skill 草稿（即使不完美），在后续使用中迭代完善
- 在 Discover 阶段，Skill 的粒度可以粗一些——因为探索方向不确定，太精细的 Skill 会限制 Agent 的探索广度

### Validate 阶段

验证阶段需要更精确和一致的分析，Skill 的价值在此凸显：
- 创建「假设验证 Skill」：包含验证标准格式、数据来源清单、证据等级评估框架——确保每次验证使用相同的标准，避免标准漂移
- 将 Discover 阶段沉淀的「有效 Prompt 模式」固化到 Skill 中：哪些 Prompt 结构在前一阶段产生了高质量输出？把它们写进 Skill 的示例部分
- 引入「验证报告 Skill」：统一验证结论的输出格式（假设、证据、置信度、下一步建议），让不同验证任务的可交付物具有可比性
- 在 Validate 阶段，Skill 的粒度应该细——因为验证需要精确，每个 Skill 聚焦一个具体的验证假设

### Plan 阶段

制定行动计划时，多个 Skill 需要协同工作，此时 Skill 的编排能力成为关键：
- 创建「计划生成 Skill」：包含计划模板（目标、里程碑、资源、风险、依赖）、输出格式约束、常见陷阱清单
- 创建「风险评估 Skill」：作为计划生成的辅助 Skill，在计划生成后被调用，对计划进行风险审查
- 鼓励用户建立 Skill 依赖关系图——哪些 Skill 需要在哪些 Skill 之后运行。例如「风险评估 Skill」应依赖「计划生成 Skill」的输出为前置输入
- 在 Plan 阶段，Skill 的编排顺序比单个 Skill 的内容更重要。用户应关注「先做什么、后做什么」的流程设计

## 反向提醒

- Skill 不是银弹：如果核心业务流程本身不清晰，封装成 Skill 只会让糟糕的流程被重复执行得更快。先流程梳理，再 Skill 封装。
- 过度 Skill 化增加认知负载：当用户需要维护超过 10-15 个 Skill 时，管理成本可能超过收益。定期审视 Skill 清单，合并或废弃低效的 Skill。
- Skill 之间的冲突需要仲裁：两个 Skill 可能对同一件事给出不同指令（如「回复客户邮件 Skill」要求语气正式，「品牌调性 Skill」要求语气活泼）。需要明确的优先级规则（如「领域特定 Skill 优先于通用 Skill」）。
- 静态 Skill 缺乏环境感知：Skill 内容是固定的，但实际场景有上下文。Agent 需要具备「根据当前上下文调整 Skill 指令」的能力，而非机械执行 Skill 中的每一步。
- 不要混淆「Skill」和「工具」：Skill 是知识+流程+约束的集合，Agent 据此决定如何推理和输出；工具（Tool）是 Agent 可以调用的外部能力（API、数据库、计算器）。Skill 指导 Agent 的思考，工具扩展 Agent 的手脚。
