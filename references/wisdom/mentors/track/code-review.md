# 行为卡：Code Review

> 触发信号：协作改动难以理解、审查沦为形式或个人偏好争论
> 证据编号：WD-P7-02

## 问题本质

审查目标是让代码库整体更健康，同时保持团队前进。改动的“小”是一个自包含、可理解、可测试、可回滚的概念，不是固定行数。

## 触发条件

- 一个变更混合功能、重构、格式化和生成文件；
- 审查者因上下文不足只能扫一眼；
- 评论被个人喜好主导，阻塞项与建议未区分；
- 关键逻辑变更没有相关测试或使用示例。

## 行为指导

1. **按概念拆分**：一个变更解决一件事，并包含理解该行为所需的测试和说明。行数只作信号；生成代码、删除和跨文件分散会改变审查成本。
2. **作者先给上下文**：说明问题、方案、风险、替代方案、验证证据和回滚方式；把纯重构与行为变化分开。
3. **先设计后细节**：先判断需求、架构、接口和整体代码健康，再看正确性、边界、测试、安全、可维护性和文档。
4. **标明评论等级**：阻塞项说明具体风险；非阻塞建议标成 `nit` 或建议。技术事实、测试和项目规范优先于个人偏好。
5. **评论代码和影响**：描述观察、风险和建议，不评价作者；争议长时间无法在评论中收敛时同步讨论，并把结论写回变更记录。
6. **快速反馈但不打断深度工作**：团队约定适合自身时区和风险的响应期；紧急变更走明确例外流程并补审。

## 不适用场景

- 单人项目可做自审或结对审查，不伪造“已被独立审查”；
- 纯机械且可验证的生成改动可调整审查方式，但要验证生成来源和结果；
- 紧急修复可以先恢复服务，随后补测试、审查和复盘；
- 原型可降低代码健康投入，但转入正式产品前必须重新评估。
