# 项目类型模板：CLI 工具

> 适用于命令行工具类项目（CLI、TUI、终端交互工具、脚本化工具链）
> 创建日期：2026-08-30

## 问题本质

CLI 工具解决的是"用最少的交互成本完成确定性的重复任务"。用户的核心诉求不是界面美观，而是**输入 → 处理 → 输出**的路径要短、可预测、可脚本化。一个 CLI 工具的价值在于：它比手动操作快，比 GUI 更适合自动化，并且在 Unix 哲学下可以与其他工具组合。

CLI 工具是 Carpe Diem 用户最容易上手的项目类型——范围可控、边界清晰、单人可在两到三周内完成 MVP。

## 典型特征

### 目录结构

```
project-name/
├── src/                    # 源码
│   ├── main.py             # 入口，解析参数
│   ├── commands/           # 子命令实现
│   │   ├── init.py
│   │   ├── run.py
│   │   └── config.py
│   ├── core/               # 核心逻辑（与 CLI 解耦）
│   │   ├── processor.py
│   │   └── validator.py
│   └── utils/              # 工具函数
│       ├── output.py       # 格式化输出
│       └── config.py       # 配置管理
├── tests/
│   ├── test_commands/
│   └── test_core/
├── scripts/                # 安装脚本、辅助脚本
├── docs/                   # 用户文档
├── README.md               # 安装+使用说明
├── pyproject.toml          # 或 package.json / Cargo.toml
└── Makefile                # 常用命令入口
```

### 技术栈选择

- **语言**：Python（适合数据处理、文本处理）、Node.js/TypeScript（适合前端生态工具）、Rust（追求性能+单文件分发）、Go（单二进制分发+跨平台）。
- **参数解析**：`argparse`/`click`（Python）、`commander.js`（Node.js）、`clap`（Rust）、`cobra`（Go）。
- **输出格式化**：`rich`/`click.style`（Python 彩色输出）、`chalk`（Node.js）、`colored`（Rust）。
- **配置管理**：`toml`/`yaml` 配置文件 + 环境变量覆盖链。
- **发布渠道**：PyPI（`pip install`）、npm Registry（`npm install -g`）、Crates.io（`cargo install`）、Homebrew（`brew install`）、GitHub Release（直接下载二进制）。

### 依赖关系模式

- **最小依赖原则**：CLI 工具应尽量减少运行时依赖，安装不能出现"pip install 半小时"的情况。能用标准库解决的问题不要引入第三方包。
- **可选依赖分组**：如 `pip install mytool[all]` 或 `npm install mytool --include=dev` 模式，核心功能零依赖，高级功能可选安装。
- **静态编译优先**：对于 Rust/Go 工具，优先静态编译为单文件分发，用户只需下载一个文件即可使用。

## 对 Carpe Diem 各阶段的启发

### Discover 阶段

CLI 工具类项目最适合从"个人反复摩擦"出发。引导用户识别：

- 你在日常工作中**重复执行的三步以上操作**是什么？能否用一个命令替代？
- 你是否有**手动处理文件转换、数据清洗、批量操作**的场景？这些是 CLI 工具的最佳候选。
- 用户画像中**技术能力较强的用户**（开发者、运维、数据分析师）是 CLI 工具的核心受众，他们不介意用命令行，但介意做重复劳动。
- **关键信号**：当用户说"我每周都要手动做一次 XX 处理"时，就是 CLI 工具的最佳机会。
- 评估方向时，"可完成性"维度权重较高——CLI 工具的范围通常比 Web 应用更可控，单人开发者在一个月内可以完成 MVP。

### Validate 阶段

验证 CLI 工具方向时，应关注：

- **竞争壁垒**：是否有现成的 CLI 工具做同样的事？用户为什么不用 `awk`、`jq`、`ffmpeg` 等现有工具的组合？差异化不能只是"更好的参数命名"。
- **真实用户验证**：CLI 工具的受众是开发者，去 GitHub Issues、Hacker News、Reddit（r/commandline）找抱怨和功能请求，比搜索"是否有竞品"更有价值。
- **安装发布验证**：用户能否通过 `pip install`、`npm install -g` 或 `brew install` 安装？发布渠道是否畅通（PyPI 包名是否被占用、npm Registry 是否有命名冲突）？
- **脚本化验证**：你的工具能否在 CI 中无交互运行？这是 CLI 工具的基本门槛，如果做不到，开发者不会采用。
- **PASS 标准**：存在至少一个真实的、不能通过现有工具组合解决的痛点，且目标用户（开发者）有明确的采纳意愿。

### Plan 阶段

规划 CLI 工具时注意：

- **MVP 定义**：第一版只支持一个核心子命令 / 一个核心功能，参数不超过 5 个，文档不超过一页 README。更多功能等用户反馈后再加。
- **发布里程碑**：CLI 工具可以发布非常早（甚至第一天就发布 0.1.0），因为用户安装后立即可用，不需要注册账号或配置环境。
- **文档优先级**：`README.md` 中的"安装"和"快速开始"两个区块比详细文档更重要。用户决定是否使用一个 CLI 工具，通常在前 30 秒内。
- **测试环境**：需要在纯净环境（Docker 容器或新虚拟机）中验证安装流程，确保没有隐式依赖或冲突。
- **非目标**：第一版不需要自动补全、彩色输出、进度条、交互式 TUI 等"锦上添花"的功能。先确保核心逻辑正确。

## Prompt 模式

当用户用 Coding Agent 开发 CLI 工具时，以下 Prompt 模式被验证有效：

- **「先定义接口，再实现逻辑」**：让 Agent 先输出完整的 CLI 参数结构和 `--help` 输出草稿，用户确认后再写实现。避免用户对工具行为有预期差异但到实现后发现不匹配。
- **「给出一个典型使用场景」**：用一句 `$ tool-name input.csv --output result.json` 告诉 Agent 工具的典型用法，比描述功能更有效。Agent 能据此推断输入输出格式、错误处理和返回值。
- **「用示例定义边界」**：提供正常输入、空输入、错误输入三个示例，让 Agent 一次性覆盖主要路径和错误处理，避免反复迭代。
- **「先写核心逻辑，再写 CLI 层」**：让 Agent 先实现 `core/` 中的纯函数（输入→处理→输出），再写 CLI 入口。确保核心逻辑可独立测试，不依赖 argparse 或 click。
- **「指定退出码约定」**：明确告诉 Agent 退出码规范（0 成功、1 通用错误、2 参数错误），Agent 会在所有代码路径中一致使用。

## 验证策略

- **核心逻辑验证**：对 `core/` 中的纯函数进行单元测试，覆盖正常输入、空输入、边界值（如超大文件、特殊字符）。纯函数测试应覆盖 90% 以上的代码路径。
- **CLI 集成验证**：用 `subprocess` 运行 CLI 命令，验证退出码、stdout、stderr 和对配置文件的响应。模拟用户实际使用方式运行。
- **管道兼容性验证**：`cmd1 | tool | cmd3` 是否正常工作？输入不是 TTY 时的行为是否正确？输出是否包含 ANSI 转义码（在管道中应自动禁用）？
- **安装验证**：从零安装（`pip install`、`npm install -g`、`cargo install`）后所有子命令可用。在 Docker 纯净容器中验证。
- **跨平台验证**：至少验证 macOS 和 Linux。如果目标是 Windows，验证 PowerShell 和 CMD 两种 shell 下的行为。
- **错误信息验证**：每个错误场景是否输出有意义的错误信息（"发生了什么、为什么发生、如何修复"）？所有错误是否走 `stderr`？

## 常见陷阱

- **参数设计过于灵活**：多种方式做同一件事（如 `--config`、`-c`、`CONFIG_PATH` 环境变量、默认路径）导致用户困惑。保持一个参数一个来源。
- **忽略非 TTY 场景**：`print()` 直接输出带颜色/动画的文本，在管道或 CI 日志中变成乱码。使用 `isatty` 检测并自动降级。
- **输出格式不一致**：错误信息有些走 `stderr` 有些走 `stdout`，导致用户脚本难以捕捉错误信号。
- **过早优化性能**：CLI 工具通常不是性能瓶颈，保持代码可读性比微优化更重要。仅当工具处理大量数据（GB 级别）时才需要针对性优化。
- **缺少 `--dry-run` 或 `--yes` 标志**：在 CI 或自动化脚本中，用户需要确认操作的标志（如覆盖文件）会导致管道挂起。提供 `--yes` 自动确认，`--dry-run` 预览变更。
- **依赖膨胀**：引入大量第三方库，导致安装时间过长或版本冲突。CLI 工具应保持核心零依赖，使用标准库替代第三方包。

## 反向提醒

这个模板不适合：
- **需要图形界面引导的操作**：如安装向导、配置初始化、首次体验教程——这些更适合 TUI 或 Web 界面。
- **需要长期运行守护进程**：CLI 工具是"启动→完成→退出"模式，不适合后台服务或监控进程（除非设计为 daemon 子命令）。
- **目标用户是非技术团队**：如果用户是设计师、编辑、运营人员，他们可能从不使用命令行，CLI 工具对他们不可达。
- **需要复杂依赖环境**：如果工具需要 Python 3.12+、Node 20+、特定系统库版本，安装门槛会大幅降低采用率。考虑静态编译或 Docker 镜像。
- **输出需要直观可视化**：CLI 的文本输出无法展示图表、地图、复杂关系图。如果用户需要可视化理解结果，考虑 Web 应用或 TUI。
