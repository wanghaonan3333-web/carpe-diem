# 行为卡：RFC / 设计文档

> 触发条件：项目进入多人协作阶段，或用户说"我们讨论过但大家理解不一样"

## 问题本质

口头决策是团队协作的隐形杀手。一个决策在会议上"达成共识"了，但一周后每个人对"共识"的理解都不一样——有些人记得的是"决定 A"，有些人记得的是"决定 B"，有些人记得的是"没决定"。等到项目推进到一半，才发现大家理解不一致，导致返工、冲突、延期。

问题的根源是：**你把"口头同意"当成了"决策达成"**。但"口头同意"只意味着"当时没有反对"，不意味着"每个人都理解且同意具体方案"。真正的决策达成需要"书面化"——用文字把决策的背景、方案、理由、风险记录下来，让每个人都能看到、理解、引用。

## 触发条件

用户正在执行以下任一操作时触发：

- **场景一：项目进入多人协作阶段，决策开始依赖"口头讨论"和"会议纪要"**。如果团队在做重大决策时，依赖的是"会上说的"和"记在笔记里的"，而不是"一份所有人都能看到的文档"，说明决策已经进入了"口头决策"的危险区。

- **场景二：用户说"我们讨论过但大家理解不一样"或"我记得当时的决定不是这样的"**。如果团队成员对同一个决策有不同的理解，说明决策没有书面化——每个人都在用自己的"记忆"来理解决策，而记忆是不可靠的。

- **场景三：用户说"这个决策已经讨论过了，为什么还要再讨论一次"**。如果团队反复讨论同一个决策，说明上次的讨论没有产出一个"可引用的决策记录"——每个人都在用自己的理解来推动，导致同一个问题反复出现。

- **场景四：用户说"这个决策是谁做的？为什么这么做？"——但找不到答案**。如果团队需要回溯一个决策的背景和理由，但找不到任何记录，说明决策过程缺乏书面化——决策者可能已经离职、可能忘记了当时的理由、可能当初就没有明确的理由。

## 行为指导

### 1. 重大决策先写 RFC 再讨论

RFC（Request for Comments）是一种"先写后说"的决策方式——在开会讨论之前，先把方案写下来，让大家看完书面方案后再讨论。

具体做法：
- 对于重大决策（架构选型、技术方案、产品方向），先写 RFC 文档，再安排会议讨论
- RFC 的写作者在写的过程中，会发现自己对问题的理解是否清晰、方案是否完整、风险是否被考虑
- 会议讨论不再是从零开始，而是针对 RFC 中的具体内容进行讨论——效率更高、结论更清晰
- 讨论结束后，直接在 RFC 中更新决策结果——不需要另写会议纪要

### 2. RFC 格式：背景/方案/替代方案/风险/决策

一个好的 RFC 格式能让阅读者快速理解决策内容和理由。推荐格式：

- **背景**：为什么要做这个决策？当前有什么问题？如果不做决策会怎样？
- **方案**：你建议怎么做？具体的方案描述、实现方式、影响范围。
- **替代方案**：你考虑了哪些其他方案？为什么没有选择它们？每个替代方案的优缺点。
- **风险**：这个方案有什么风险？如何缓解？最坏情况是什么？
- **决策**：最终的决定是什么？谁做的决定？什么时候做的决定？

### 3. 设置评论期（如 48h）收集反馈

RFC 写完后，不要立刻执行——给团队一个"评论期"来收集反馈。

具体做法：
- 设置评论期通常为 48 小时（根据决策的复杂度，可以延长到 1 周）
- 在评论期内，团队成员可以阅读 RFC 并提出修改建议
- 评论期的目的是"收集反馈"，不是"寻求批准"——写作者有权决定是否采纳反馈
- 评论期结束后，写作者更新 RFC 为最终版本，开始执行

### 4. 决策后归档 RFC 作为项目记录

RCF 不仅是一个"决策工具"，还是一个"项目记录"——让未来的你和未来的团队成员能够回溯决策背景。

具体做法：
- 每个决策完成后，将 RFC 归档到项目的"决策记录"目录
- 归档的 RFC 包含：决策背景、考虑过的方案、最终决定、决策理由、决策时间
- 当未来有人问"为什么这么设计"时，可以直接引用 RFC 作为答案
- 归档的 RFC 也是一个"学习记录"——如果决策结果不好，可以回溯当时的决策过程，找到问题所在

### 5. 区分"征求意见"和"寻求批准"

RFC 评论期的目标不是"让所有人都同意"，而是"让所有人都知道"。

具体做法：
- "征求意见"：你写了一个方案，想听听大家的想法——评论期结束后，你有权决定是否采纳
- "寻求批准"：你写了一个方案，需要得到某个人的批准才能执行——评论期结束后，需要等待批准
- 在 RFC 的开头明确标注"这是征求意见还是寻求批准"——让读者知道他们的角色是什么
- 如果是"征求意见"，评论期结束后，不需要等待任何人批准——直接执行

### 6. 不必事无巨细都写 RFC，关键决策才需要

RFC 的目标是"提高决策质量"，不是"增加文档工作量"。如果每个决策都要写 RFC，团队会变得效率低下。

具体做法：
- 只有"关键决策"需要写 RFC——那些影响范围大、不可逆、或者需要团队共识的决策
- 日常决策、小改动、紧急修复——不需要写 RFC，直接执行
- 判断标准：如果这个决策做错了，需要花多少时间来纠正？如果需要花超过 1 天的时间来纠正，就需要写 RFC
- 如果拿不准"要不要写 RFC"，先写一个简短的 RFC（1 页以内）——比不写要好

## 不适用场景

- **单人项目**：如果用户是独自开发，没有其他人需要对齐，那么"口头决策"不是问题——因为"口头"和"书面"对同一个人来说是一样的。RFC 的主要价值是"让团队对齐"，单人项目不需要这个功能。

- **紧急修复**：如果用户正在处理线上故障或紧急安全漏洞，没有时间写 RFC。紧急问题需要立即决策和修复，写完 RFC 再修复可能已经造成了不可挽回的损失。但修复完成后，建议补写一个"事后记录"——记录当时做了什么、为什么这么做、以及如何避免类似问题。

- **微小改动**：如果用户在做的是"修复一个拼写错误"、"调整一个按钮颜色"、"优化一个查询语句"这类微小改动，写 RFC 的成本远高于改动的价值。对于这类改动，直接提交代码即可。

- **团队已经建立了高效的同步沟通机制**：如果团队已经建立了高效的"站立会议+即时消息"沟通机制，并且团队成员之间配合默契，决策的书面化可以适当降低。但"适当降低"不等于"完全放弃"——对于关键决策，仍然建议写 RFC，只是频率可以降低。
