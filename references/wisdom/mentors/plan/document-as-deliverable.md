# 行为卡：文档即交付物

> 触发条件：Plan 阶段进入"里程碑和任务"章节，定义交付物时，用户只列出"代码"而未包含"文档"

## 问题本质

大多数人在规划交付物时，只列"代码功能"——"完成用户注册模块"、"实现搜索功能"、"优化数据库查询"。但问题是：**代码写完了不代表交付完成了——没有文档的功能，对用户和开发者来说等于不存在**。

用户不知道这个功能怎么用，你需要花时间一遍遍解释；其他开发者不知道怎么维护，你要花时间带他们读代码；半年后你自己回来，也看不懂当初为什么这么设计。所有这些"花时间解释"的成本，都是因为文档没有被当作"交付物的一部分"。

问题的根源是：**你把"写文档"当成了"可选的善后工作"，但好的文档和好的代码是同一件事的两个面**。如果一个功能没有文档，它不是"完成"了，而是"写完了但没交付"。

## 触发条件

用户正在执行以下任一操作时触发：
- Plan 阶段定义每个里程碑的交付物时，只列出了"代码功能"，没有列出"文档"
- 用户在 Plan 阶段说"这个功能很简单，不需要文档"——对简单功能来说，不需要文档的通常是"只有你自己觉得简单"
- 里程碑完成时，用户说"代码写完了，但文档还没写，下次补上"——"下次补上"通常意味着永远不会补
- 用户评审代码时，发现"这个功能不知道怎么用"或"API 接口没有说明"

## 行为指导

### 1. 把文档列为每个里程碑的交付物之一

在 Plan 阶段定义每个里程碑的交付物时，明确列出"文档交付物"：

- 用户文档：用户如何安装、配置、使用这个功能？包括 README 更新、使用指南、示例代码。
- 开发者文档：其他开发者如何理解、维护、扩展这个功能？包括 API 文档、架构说明、数据模型变更。
- 运维文档：如何部署、监控、排错？包括配置说明、环境要求、常见问题排查。

每个文档交付物应该有明确的验收标准——"写完了"不是标准，"别人能看懂"才是。

### 2. 文档和代码同时提交——一份 PR 包含代码和文档

在 Plan 阶段的"测试策略"或"提交规范"章节中，明确要求：

- 每个 Pull Request 或提交，必须同时包含代码和对应的文档更新
- 如果代码变更了 API 接口、配置项、数据模型，必须有对应的文档更新
- 如果代码新增了功能，必须有对应的使用说明

如果某个 PR 只包含代码不包含文档，评审者应该打回——不是因为代码不好，而是因为"交付物不完整"。

### 3. 文档的"第一读者"不是专家，而是新手

写文档最常见的错误是：假设读者和你一样了解这个项目。但"和你一样了解"的人不需要看文档——文档是给"不了解的人"看的。

写文档时的三个原则：
- **不要假设常识**：你觉得"这个不用说明白"，但新手可能完全不知道。如果你不确定，写下来。
- **用示例说话**：抽象的描述不如一个具体的例子。示例应该覆盖"正常使用"和"常见错误"两种情况。
- **先写"为什么"再写"是什么"**：读者需要先知道"为什么要用这个功能"，才想知道"这个功能是什么"。把"为什么"放在文档开头，把"技术细节"放在后面。

判断标准：如果你把文档给一个不了解项目的人看，他能否独立完成"安装→配置→使用"的全流程？如果他需要来问你问题，说明文档不够完整。

### 4. 文档是活的——代码改了，文档必须同步更新

代码变更时，文档不是"之后补"的，而是"同步更新"的。在 Plan 阶段定义"文档维护策略"：

- **代码变更触发文档更新**：每次代码变更，都要检查对应的文档是否需要更新
- **文档与代码同版本**：文档和代码应该在同一个版本中——如果用户看到的是 v1.0 的文档，但代码已经是 v1.1，那就说明文档没有同步
- **废弃的文档比没有文档更糟糕**：如果文档描述的行为和实际代码不一致，用户会信任文档（然后发现它不对），或者不信任文档（然后不看任何文档）。两种情况都意味着文档没有价值。

操作建议：在里程碑的"完成检查"清单中，增加一条："文档是否已同步更新？"

### 5. 区分"文档"和"注释"——文档面向读者，注释面向维护者

明确区分两种"文字"：

- **文档**：面向用户、其他开发者、运维人员——说明"怎么用"、"为什么"、"注意事项"。文档应该放在项目的 `docs/` 目录、README、Wiki 中。
- **注释**：面向代码维护者——说明"为什么这么写"、"这个边界条件是什么"。注释应该放在代码中，靠近它所解释的代码。

不要用注释代替文档，也不要用文档代替注释。两者各自解决不同的问题：
- 如果用户需要读代码注释才能知道怎么用这个功能，说明文档缺失
- 如果维护者需要翻文档才能知道某段代码为什么这么写，说明注释缺失

### 6. 用一个"文档质量检查清单"来验收文档

在 Plan 阶段的"验收标准"章节中，增加文档质量检查清单：

- [ ] 用户文档：是否包含了"安装、配置、使用"三个步骤？每个步骤是否提供了示例？
- [ ] API 文档：每个接口是否有"请求示例、响应示例、错误码说明"？
- [ ] 架构文档：是否包含了"系统上下文图、容器/服务图、组件图"？（参见"架构可视化"行为卡）
- [ ] 变更日志：代码变更是否有对应的 CHANGELOG 或版本发布说明？
- [ ] 新手测试：一个不了解项目的人，能否根据文档独立完成"安装→配置→使用"？

如果一个文档交付物在这些检查项上缺失，它就不算"完成"——需要补充完整后再标记为"已交付"。

## 不适用场景

- **用户做的是原型验证或一次性脚本**：如果代码的目的是"快速验证想法"，完成后会被丢弃，不需要正式文档。原型阶段只需要足够的注释让开发者在迭代过程中能理解代码即可。
- **用户做的是探索性/实验性项目**：如果项目方向还不确定，频繁变动，写正式文档的收益很低。这种情况下，建议用"实验笔记"或"设计草稿"代替正式文档，等方向确定后再补充。
- **用户的项目只有他自己一个人维护**：如果项目是个人工具，且不打算公开或共享，文档可以简化到"自己看得懂的笔记"级别。但注意：一个月后的你，也是"陌生人"——如果 30 天后你回来看不懂自己的代码，那说明你需要的文档可能比你以为的多。
- **用户已经建立了良好的文档习惯**：如果用户团队已经在每个 PR 中同步更新文档，并且在需求评审时就把文档作为交付物之一，说明文档即交付物的原则已经内化。不需要再引入额外的检查清单，只需要保持现有习惯。
