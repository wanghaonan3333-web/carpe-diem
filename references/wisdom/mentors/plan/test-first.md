# 行为卡：测试优先——测试是重构的安全网

> 触发条件：Plan 阶段进入"测试策略"章节，或用户说"先写代码，测试后面再补"时

## 问题本质

大多数人在写代码时，会把测试当作"可选项"——"先实现功能，等代码稳定了再补测试"、"发布前跑一下手动测试就够"、"测试覆盖率差不多就行"。但问题是：**没有测试覆盖的代码，不是"可维护的代码"，而是"不敢改的代码"**。

当代码没有测试时，每次重构都像在雷区里走路——你不敢动老代码，因为不知道改了之后会出什么问题。你只能"加"新代码，不能"改"旧代码，于是代码越来越臃肿，越来越不可维护。最终，系统变成了"能跑就别动"的遗产。

问题的根源是：**你把"测试"当成了"验证"——验证写好的代码对不对。但测试的真正价值不是"验证"，而是"保障"——保障你可以在任何时候安全地修改代码**。没有测试，重构就是豪赌；有测试，重构就是日常操作。

## 触发条件

用户正在执行以下任一操作时触发：
- Plan 阶段进入"测试策略"章节，但用户说"测试后面再补"或"先手动测试，上线后再加自动化测试"
- 架构设计涉及重构现有代码，但用户说"这部分代码不敢动"——因为怕改坏了
- 用户说"我们的代码覆盖率很高"，但问"覆盖了哪些分支"时回答不上来
- 用户说"这个功能改完了，但我不知道有没有影响到其他功能"——这是测试缺失的典型信号

## 行为指导

### 1. 把测试当作"安全网"，而不是"验证"

区分"测试的两种心态"：

- **验证心态**："代码写完了，跑一下测试看看对不对。"——测试是事后检查，可有可无。
- **安全网心态**："代码改了，跑一下测试看看有没有改坏什么。"——测试是保护网，必须存在。

安全网心态的核心价值不在于"发现 bug"，而在于"让你敢改代码"。当你需要重构、优化、升级依赖时，测试告诉你：改完后，原有的功能还在。没有测试，你每次都要手动测试所有功能；有测试，你只需要跑一下测试套件。

判断标准：如果你每次修改代码后，都要手动测试一遍所有功能才能放心上线，说明你的测试没有起到"安全网"的作用。好的测试应该是：修改完代码后，跑一次测试套件，如果全部通过，你就可以放心上线。

### 2. 以"分支覆盖"为目标，而不是"行覆盖"

大多数人说"测试覆盖率"时，指的是"行覆盖"——代码中有多少行被执行到了。但行覆盖是一个很弱的指标——即使 100% 的行覆盖，也可能漏掉大量逻辑错误。

更可靠的指标是**分支覆盖**——代码中每个条件分支（if/else、switch、循环边界）是否都被测试到了。分支覆盖的要求是：每个判断条件的"真"和"假"分支都要被测试覆盖。

例如：
```
if (count > 0) {
  // 处理正常情况
} else {
  // 处理空值情况
}
```

- 行覆盖：只需要跑一次（count > 0 或 count <= 0 都行），两行代码都被执行了
- 分支覆盖：必须跑两次——一次 count > 0，一次 count <= 0

操作建议：
- 在测试策略中，明确要求"所有条件分支至少覆盖一次"
- 在代码审查时，检查测试是否覆盖了所有分支
- 不要在测试策略中写"覆盖率不低于 80%"——这个数字没有意义，因为 80% 的行覆盖可能漏掉 50% 的分支

### 3. 先写测试，再写代码——测试是"定义"，不是"验证"

"先写测试"不是宗教教条，而是有实际意义的工程实践：

- **测试定义行为**：先写测试，意味着你先想清楚"这个功能应该做什么"，再写代码"让它做得到"。测试是"需求"，代码是"实现"。
- **测试驱动设计**：如果测试很难写，说明代码设计有问题——接口太复杂、依赖太多、职责不清晰。先写测试能倒逼你写出更简洁、更模块化的代码。
- **测试即文档**：好的测试本身就是文档——它说明了"什么输入应该产生什么输出"，比任何文档都准确。

操作建议：
- 不要求每个功能都严格 TDD（测试驱动开发），但至少做到：**核心逻辑和边界条件，先写测试再写代码**
- 对于简单的 CRUD 和 UI 代码，可以后补测试——但关键的业务逻辑和算法，必须先写测试

### 4. 每次修改代码，先跑测试——建立"回归测试"习惯

"回归测试"的意思是：修改代码后，跑一遍所有已有测试，确保没有引入新的问题。

操作建议：
- 在 Plan 阶段的"测试策略"章节中，明确要求：**每次修改代码后，必须运行完整的测试套件**
- 测试套件应该在 5 分钟内跑完——如果超过 5 分钟，说明测试需要优化（拆分、并行、减少不必要的集成测试）
- 如果测试跑不完，或者跑得慢到没人愿意跑，那测试就没有价值——"测试太慢"是测试策略中最需要解决的问题，不是"测试覆盖率不够"

### 5. 用"测试金字塔"决定测试策略

在 Plan 阶段的测试策略章节中，明确三类测试的比例：

- **单元测试（底层）**：测试单个函数、模块、类的行为。速度快、覆盖率高、容易定位问题。应该占测试的 70% 以上。
- **集成测试（中层）**：测试模块之间的交互、外部依赖的集成。速度快慢适中，覆盖关键路径。应该占 20% 左右。
- **端到端测试（顶层）**：测试完整用户流程。速度慢、维护成本高、容易不稳定。只覆盖核心用户路径，应该占 10% 以下。

常见错误：
- 大量写端到端测试，单元测试很少——结果测试跑得慢、不稳定、每次修改都要改测试
- 把所有测试都写成集成测试——结果测试跑得慢，定位问题困难
- 没有单元测试，全靠手动测试——结果无法做回归测试，重构风险极高

判断标准：如果测试套件中端到端测试的比例超过 20%，说明测试策略有问题——需要把更多功能下放到单元测试和集成测试。

### 6. 为"重构"保留测试备份——重构前先冻结测试状态

当需要对现有代码进行大规模重构时，遵循以下步骤：

1. **冻结测试**：在重构前，确保所有现有测试通过。记录当前测试的状态（通过数、失败数、覆盖率）。
2. **写测试**：为即将重构的代码写测试，确保覆盖所有关键分支。
3. **重构**：修改代码，不改变外部行为。
4. **验证**：跑测试，确保所有测试通过。如果发现有测试失败，说明重构改变了行为——需要检查是测试错了还是重构错了。
5. **对比**：重构后的测试结果与"冻结"时的测试结果一致，说明重构成功。

这个步骤确保：重构不是"盲改"，而是"在安全网保护下的修改"。如果重构过程中发现测试缺失，说明你没有覆盖到某个分支——先补测试，再继续重构。

## 不适用场景

- **用户做的是原型验证或一次性脚本**：如果代码的目的是"快速验证想法是否可行"，完成后会被丢弃，不需要写测试。原型阶段的目标是"学习"，不是"维护"。等原型验证通过后，进入正式开发时再写测试。
- **用户做的是纯 UI 探索**（如设计稿、静态页面、交互原型）：这类工作没有业务逻辑，测试的价值有限。UI 测试应该在"功能逻辑确定后"再写，而不是在 UI 探索阶段。
- **用户的项目是极小的个人工具**（如一个只有 100 行代码的脚本）：如果项目很小、逻辑简单，而且不会长期维护，测试带来的收益小于成本。判断标准：如果修改代码后，手动测试所有功能只需要 5 分钟，那就不需要自动化测试。
- **用户已经建立了完善的测试体系**：如果项目已经有测试覆盖、有 CI 流程、有回归测试习惯，并且用户能自信地说"改了代码后跑测试就知道有没有出问题"，那说明测试体系已经建立。此时不需要再重新设计测试策略，而是关注测试覆盖的盲区（如未覆盖的分支、未测试的边界条件）。
