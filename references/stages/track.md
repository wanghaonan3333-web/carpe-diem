# Track · 记录开发进度与计划偏差

## 一句话本质

对照计划和证据看清真实进度，不做监督式催促，也不越界开发。

## 进入条件

- 正式项目计划和开发交接包已获批准；
- 项目状态为 `track`、`paused` 或 `completed`；
- 用户再次调用 Carpe Diem 查看或更新项目进度。

## 主动讲授

先给结果，不先询问“最近做了什么”。用恢复摘要说明上次里程碑、这次观察到的变化、证据强度、偏差和当前建议。

## Agent 动作

1. 读取正式计划、项目状态、事件历史和上次 Git 引用。
2. 只读采集当前 Git HEAD、分支、提交摘要和工作区状态。
3. 读取已有的测试、CI 或 Issue 证据；不主动运行项目测试。
4. 将任务区分为“有证据完成”“声称完成”“未完成”“无法判断”。
5. 对照计划识别范围偏移、阻塞和新的关键决定。
6. 给出继续、调整、暂停或结束的建议。
7. 生成下一阶段开发交接建议，而不是执行任务。

## 用户决策

只有需要改变正式计划、接受范围偏移、暂停或结束项目时才请求用户决定。普通进度记录不把事实确认拆成一连串问题。

## 表达示例

> 上次计划停在 {milestone}。根据 {git/test/issue evidence}，目前有证据完成 {items}，仍缺 {items}；我看到 {deviation}。下一步最值得交给开发 Agent 的是 {next}。

## 成功信号

- 每个进度结论能追溯到证据或明确标为未知；
- 计划偏差及原因被记录；
- 下一阶段交接建议具体；
- 工作区和业务源码没有被修改；
- `next_recommended` 可供另一 Agent 直接续接。

## 常见误区

- 只根据文件存在就声称功能完成；
- 自动运行可能改动工作区的测试或脚本；
- 发现问题后直接修复；
- 用催促或责备代替进度判断；
- 为了保持“按计划”而隐藏合理偏差；
- 读取到脏工作区后尝试清理。

## 状态写入

保存前后 Git 引用、里程碑变化、证据引用、偏差、用户决定和下一步建议。事件记录不保存完整 Diff、源码副本或完整聊天。

## 下一步路由

- 继续开发：保持 `phase=track`，更新 `next_recommended`。
- 计划变更：展示正式计划 Diff，用户确认后更新并保持 Track。
- 暂停：`phase=paused`，记录恢复条件。
- 完成：`phase=completed`，记录验收证据和复盘结论。
