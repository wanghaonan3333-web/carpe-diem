# 行为卡：上下文边界

> 触发条件：Plan 阶段进入"架构、组件、数据流"章节，开始划分模块边界时

## 问题本质

大多数人在做架构设计时，会本能地按"技术层"来划分模块——"前端模块"、"后端模块"、"数据库模块"、"工具模块"。但问题是：**技术层划分只告诉你"代码放在哪里"，不告诉你"每个模块负责什么业务逻辑"**。

更隐蔽的问题是：当不同模块使用不同术语来描述同一件事时，开发 Agent 会误解需求。例如，"用户"在登录模块里指的是"账户持有人"，在支付模块里指的是"付款方"，在客服模块里指的是"需要帮助的人"——这三个"用户"不是同一个概念，但如果你把它们放在同一个模块里，用同一个术语，就会产生混乱。

问题的根源是：**你把"技术分类"当成了"模块划分"**。但真正有效的模块边界不是按"前端/后端"来切的，而是按"业务上下文"来切的——每个模块有明确的职责边界、专有的术语体系、以及与其他模块的正式接口。

## 触发条件

用户正在执行以下任一操作时触发：

- **场景一：Plan 阶段进入"架构"章节时，用户按技术层划分模块**。如果用户说"我们有前端模块、后端模块、数据库模块"，但没有先按职责边界划分"业务模块"，说明模块划分的依据是"技术层"而不是"业务上下文"。

- **场景二：同一个术语在多处使用，但含义不同**。如果"用户"在架构的不同地方指代不同概念、"订单"既指"购物车中的待支付订单"又指"已完成的订单"、"文档"既指"用户输入的草稿"又指"审核通过的终稿"，说明术语边界不清晰——需要为每个概念划定明确的上下文边界。

- **场景三：模块之间的依赖关系混乱，无法说清"谁依赖谁"**。如果模块 A 直接调用模块 B 的内部数据、模块 B 又反过来调用模块 A 的某个函数，或者"不清楚这个模块到底依赖什么外部系统"，说明模块边界有问题——需要重新划定上下文边界，明确每个模块的职责范围。

- **场景四：项目依赖外部系统或遗留代码，但不确定外部变化会如何影响内部代码**。如果用户说"我们要对接 XX 平台的 API，但不知道它改版后我们的代码会不会崩"，说明需要为外部依赖建立保护层。

## 行为指导

### 1. 先按"业务职责"划分模块边界，再考虑技术实现

在讨论任何技术栈之前，先回答这个问题：**这个系统涉及哪些不同的业务领域？每个领域解决什么具体问题？**

每个业务领域是一个独立的"上下文"——它有自己专属的术语、自己的规则、自己的数据模型。不同上下文之间的术语可以不同，但它们的映射关系必须明确。

示例：
- 一个电商系统可能包含以下上下文：**商品目录**（管理商品信息、库存、分类）、**订单处理**（管理下单、支付、退款流程）、**物流配送**（管理发货、追踪、配送状态）、**客户服务**（管理咨询、投诉、售后）
- 一个内容平台可能包含：**内容创作**（写作、编辑、发布）、**内容审核**（审核、标注、策略配置）、**内容分发**（推荐、推送、搜索）、**用户管理**（注册、权限、订阅）

判断标准：当你把每个上下文用一句话说清"它负责什么、不负责什么"时，如果两句话之间没有重叠，说明边界划分是清晰的。如果两个上下文的职责描述看起来"差不多"，说明它们应该合并为一个上下文。

### 2. 为每个上下文建立"术语表"，确保术语一致

在每个上下文中，所有使用的术语必须有统一的定义。不要在不同的地方使用同一术语指代不同事物，也不要用不同术语指代同一事物。

具体做法：
- 在 Plan 阶段产出"项目术语表"，列出每个上下文中使用的核心术语及其精确定义
- 所有 ADR（架构决策记录）、里程碑描述、测试用例必须使用同一套术语
- 如果两个上下文使用相同的词但含义不同，必须在术语表中明确标注

示例术语表：
| 上下文 | 术语 | 定义 | 注意 |
|--------|------|------|------|
| 订单处理 | 订单 | 用户已确认支付、等待发货的交易记录 | 不包括"购物车中的待支付订单" |
| 商品目录 | 商品 | 可供销售的产品单元，包含 SKU、价格、库存 | 不包括"已下架商品" |
| 物流配送 | 配送单 | 从仓库到用户的运输任务，一个订单可能拆为多个配送单 | 每个配送单对应一个包裹 |

判断标准：如果两个开发 Agent 在讨论同一个模块时，对"用户"、"订单"、"状态"等核心术语的理解一致，说明术语表是有效的。如果他们在对需求时发现"你说的用户和我说的用户不是一回事"，说明术语表需要补充精确的定义。

### 3. 明确上下文之间的接口和依赖关系

每个上下文不是孤立的——它们之间需要通信和协作。但通信必须通过正式的接口，而不是直接访问对方的内部数据。

上下文之间的协作关系有几种常见模式：

- **调用关系**：上下文 A 调用上下文 B 的接口获取数据。例如"订单处理"上下文调用"商品目录"上下文的接口查询商品信息。这是最松散的耦合方式，推荐优先使用。
- **共享数据**：两个上下文共享同一个数据源，但各自只读取自己的字段。例如"订单处理"和"物流配送"共享同一个订单状态表。这种方式耦合度较高，需要谨慎控制。
- **事件通知**：一个上下文发生某个事件时，通知其他上下文。例如"订单处理"上下文在订单支付成功后发出"订单已支付"事件，"物流配送"上下文监听这个事件并创建配送单。这是耦合度最低的方式，适合异步场景。

在 Plan 阶段，对每个上下文明确：
- 它依赖哪些其他上下文？依赖的方式是什么（接口调用、共享数据、事件通知）？
- 其他上下文依赖它的哪些能力？接口契约是什么？
- 如果依赖的上下文发生变化，如何处理？

### 4. 为外部依赖建立保护层

当项目依赖外部系统（第三方 API、遗留代码、其他团队的服务）时，不要让外部系统的变化直接波及你的核心代码。做法是：在外部系统和你的核心逻辑之间加一层"保护层"，把所有外部交互集中在这一层中。

具体操作：
- 识别所有外部依赖，标注每个依赖的稳定性和变更频率
- 对每个外部依赖，定义一个"你认为它应该提供什么能力"的理想接口
- 写一个适配层，把外部系统的实际接口映射到你的理想接口
- 核心代码只依赖"理想接口"，不直接依赖外部系统

这样做的价值：
- 外部系统改版时，只需要修改适配层，核心代码不受影响
- 如果需要替换外部系统，只需要替换适配层，核心代码的逻辑不变
- 测试时可以轻松模拟外部系统，因为核心代码只依赖你定义的接口，不依赖具体的实现

判断标准：如果你可以在不修改核心业务逻辑的前提下，把某个外部依赖从 A 服务切换到 B 服务，说明保护层是有效的。如果切换需要修改多处的核心代码，说明外部依赖已经渗透到了你的核心逻辑中——需要重新设计保护层。

### 5. 区分"有身份标识的对象"和"仅凭属性定义的对象"

在定义每个上下文的数据模型时，区分两类对象：

- **有身份标识的对象**：即使属性全变了，它仍然是同一个对象。例如"用户"——即使换了手机号、邮箱、头像，它仍然是同一个用户。这类对象需要唯一的标识符（如用户 ID）。
- **仅凭属性定义的对象**：如果属性变了，它就变成了另一个对象。例如"地址"——"北京市朝阳区 XX 路"和"上海市浦东新区 YY 路"是两个不同的地址，没有"同一个地址"的概念。这类对象不需要身份标识，直接比较属性值即可。

在 Plan 阶段的"数据流"章节中，明确标注每个核心数据模型的类型，以及它们之间的关系。这有助于设计合理的数据存储结构——有身份标识的对象通常需要独立的数据库表，仅凭属性定义的对象通常作为值嵌入在其他对象中。

## 不适用场景

- **极简单的单模块项目**：如果用户的项目是一个"单文件脚本"、"仅有一个 CRUD 接口的简单工具"或"没有复杂业务逻辑的演示项目"，那么上下文边界的划分是过度工程化——一个上下文就够了。此卡适用于"项目有多个模块、多个职责领域"的场景，而非"单模块"场景。

- **纯技术基础设施项目**（如 CLI 工具、库、开发框架）：如果用户的项目是技术基础设施（如"一个 JSON 解析库"、"一个命令行工具"、"一个 CI/CD 工具"），它的模块划分依据是"技术职责"而非"业务领域"。这类项目不需要按业务上下文划分，而是按"功能职责"划分（如"解析器"、"生成器"、"格式化器"等）。

- **用户已经熟练使用上下文边界划分**：如果用户已经能自然地按职责边界划分模块、建立术语表、定义接口契约，说明上下文边界的方法已经内化，不需要再走一遍完整的流程。此卡适用于"模块边界混乱"或"术语使用不一致"的场景。

- **探索性/原型阶段**：如果用户还在做"快速验证想法"的原型，系统边界和模块划分本身还在变化中，此时强行划分上下文边界会导致"边界频繁变动"。等原型验证通过、进入正式开发阶段时再启用此卡。原型阶段只需要一个"大概的模块划分"就够了。
