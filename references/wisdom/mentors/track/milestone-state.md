# 行为卡：里程碑状态

> 用测试证据和集成频率判断里程碑的真实完成状态——而非"声称完成"
> 蒸馏日期：2026-09-01

## 问题本质

"做完了"和"做完了且做好了"是两回事。

大多数里程碑的完成状态依赖一个简单的判断：**开发者说做完了，所以就是做完了**。但"声称完成"和"有证据证明完成"之间有一条鸿沟——代码写完了，但可能没有测试覆盖；功能实现了，但可能破坏了其他功能；代码提交了，但可能从未被集成到主分支。

问题的根源是：**你把"代码存在"当成了"功能完成"**。

一个典型的例子：
- 开发者完成了功能代码，但没写测试 → 你说"做完了"，但下次变更时这个功能可能悄无声息地坏掉
- 开发者提交了代码，但没合并到主分支 → 你说"做完了"，但代码永远活在分支里，从未被集成验证
- 开发者深夜赶工完成了任务 → 你说"做完了"，但代码质量可能因为疲劳而下降，遗留了技术债

你需要一种更可靠的"完成"定义——**不是"代码存在"，而是"测试通过、代码已集成、没有破坏现有功能"**。

里程碑状态卡的目的是：**用客观证据（测试、CI、集成频率）替代主观判断（"做完了"的声称），让"完成"的定义从"写完了代码"升级为"代码通过了验证"**。

## 触发条件

在以下任一场景中触发：

- Track 阶段开始检查里程碑的完成状态时
- 某个里程碑被标记为"已完成"，但缺少自动化测试证据
- 长时间没有代码被合并到主分支
- 用户说"这个功能做完了"（需要用证据验证这个声称）
- 里程碑的完成状态只有"声称完成"而没有客观证据支撑
- 用户说"代码写完了，但还没来得及测试"
- 发现大量提交集中在深夜或周末（可能表明节奏失控）

## 行为指导

### 1. 检查"测试是否先于代码存在"——这是最可靠的完成信号

如果项目遵循测试驱动开发，检查"测试提交"和"代码提交"的时间顺序：

```
测试-代码顺序检查：
  里程碑：用户认证模块
  检查结果：
    - 测试文件 tests/auth.test.ts 提交于 2026-08-28 10:00
    - 代码文件 src/auth.ts 提交于 2026-08-28 10:30
    - 结论：✅ 测试先于代码——符合测试驱动开发规范，完成信号强
    - 测试覆盖率：85%（核心逻辑有测试覆盖）
  
  里程碑：通知模块
  检查结果：
    - 代码文件 src/notification.ts 提交于 2026-08-27 14:00
    - 测试文件 tests/notification.test.ts 提交于 2026-08-28 09:00
    - 结论：⚠️ 代码先于测试——虽然最终有测试，但测试是"事后补的"
    - 可信度：中等（测试存在，但可能只覆盖了"容易测的部分"）
```

**如何解读测试-代码顺序**：

| 模式 | 信号 | 可信度 |
|------|------|--------|
| **测试先于代码** | 功能是"设计好再实现的"，测试驱动了设计 | 高——这是最可靠的完成信号 |
| **测试与代码同时提交** | 可能是先写代码再补测试，也可能是同时完成的 | 中——测试存在，但可能不是设计驱动 |
| **代码先于测试（间隔短）** | 代码写完后补了测试，但有遗漏风险 | 中低——有测试，但可能是"为了让测试通过而写的测试" |
| **代码先于测试（间隔长）** | 测试是"后来补的"，可能只在关键路径上有测试 | 低——测试覆盖率可能不足 |
| **只有代码，没有测试** | 功能完成了，但没有验证手段 | 不可信——"做完了"但没有证据 |

**如果项目没有测试文件**：
- 这不是"项目做错了"，而是"完成信号不完整"
- 在 Track 报告中注明："该里程碑的完成状态仅基于代码存在，缺少测试验证"
- 建议用户：如果项目进入维护期，考虑为关键路径补充测试

### 2. 检查集成频率——最近一次代码合并距今多久

代码存在但未被集成，等于"代码还躺在开发者自己的机器上"。集成频率是第二个关键的完成信号：

```
集成频率检查：
  里程碑：用户认证模块
  主分支最新合并：2026-08-28 10:30（合并了 auth 模块）
  合并到主分支后的 CI 状态：✅ 通过
  结论：代码已集成到主分支，通过了 CI 验证
  
  里程碑：通知模块
  主分支最新合并：2026-08-25（合并了其他模块，通知模块尚未合并）
  通知模块分支最新提交：2026-08-28 09:00
  分支存在天数：3 天
  结论：⚠️ 代码已提交但未合并到主分支——"完成了"但"未集成"
```

**集成频率的解读标准**：

| 频率 | 信号 | 健康度 |
|------|------|--------|
| **每天多次集成** | 代码在持续流动，每次集成都是小批量 | 优秀——"完成"的定义从"代码写完"升级为"代码已集成" |
| **每天 1 次** | 每日集成节奏，代码不会堆积太久 | 良好——集成延迟在可接受范围内 |
| **每周 2-3 次** | 有一定集成延迟，但仍在可控范围内 | 一般——关注为什么没有更频繁地集成 |
| **每周不到 1 次** | 代码在分支上堆积，集成风险增加 | 危险——"完成了"可能只是"代码写完了"，从未被验证 |
| **连续一周无集成** | 项目可能遇到了阻塞，或者开发者在独立工作 | 红色预警——建议检查"为什么没有集成" |

**处理"未集成"的里程碑**：
- 不要自动将其标记为"未完成"——代码可能确实写完了，只是还没合并
- 在报告中注明："代码存在但未集成到主分支，完成状态待验证"
- 建议用户：如果代码已完成，尽快合并到主分支并通过 CI 验证
- 如果分支存在超过 1 周且没有合并，建议检查"分支是否遇到了冲突"或"分支是否被遗忘了"

### 3. 检查 CI 状态——自动化验证比任何声称都可靠

CI 通过是"有证据完成"的最高等级证据。在 Track 阶段，检查 CI 状态比检查"文件是否存在"更可靠：

```
CI 状态检查：
  里程碑：用户认证模块
  相关 CI 运行：
    - 最后一次合并触发的 CI：✅ 通过（2026-08-28 10:35）
    - 测试用例数：120 个，全部通过
    - 测试覆盖率：87%
  结论：自动化验证通过，完成状态可信度高
  
  里程碑：通知模块
  相关 CI 运行：
    - 分支最新提交触发的 CI：⚠️ 运行中（2026-08-28 09:05）
    - 上次 CI 运行：❌ 失败（2026-08-27 16:00，3 个测试失败）
    - 失败原因：测试配置问题，非功能逻辑问题
  结论：CI 尚未通过，完成状态不可信
```

**CI 状态的解读**：

| CI 状态 | 对完成状态的影响 |
|---------|----------------|
| **全部通过** | 这是最可靠的"有证据完成"信号。如果代码已合并且 CI 通过，里程碑可以标记为"有证据完成" |
| **部分通过** | 核心测试通过，但边缘场景有失败。需要进一步检查失败原因——是"真的有问题"还是"测试配置问题" |
| **运行中** | 完成状态待定。等待 CI 结果再确认 |
| **失败** | 完成状态不可信。即使代码写完了，CI 失败说明"做完了"但"没做好" |
| **未触发 CI** | 仅基于代码存在，缺少自动化验证。完成状态可信度低 |
| **无 CI 配置** | 项目没有 CI 基础设施。无法通过自动化验证确认完成状态，只能依赖其他证据 |

**如果项目没有 CI 配置**：
- 这不是"项目做错了"——很多个人项目没有 CI
- 在报告中注明："缺少 CI 验证，完成状态仅基于代码存在和测试文件存在"
- 建议用户：如果项目进入稳定期，考虑配置基本的 CI 流程

### 4. 检测"提交时间分布"——防止节奏失控导致的质量问题

完成状态不仅是"代码有没有写完"，也是"代码是在什么状态下写的"。提交时间分布是一个辅助信号：

```
提交时间分布检查：
  里程碑：用户认证模块
  最近 7 天的提交时间分布：
    - 工作时间（9:00-18:00）：12 次提交
    - 晚间（18:00-22:00）：3 次提交
    - 深夜（22:00-6:00）：0 次提交
    - 周末：1 次提交（周六下午）
  结论：✅ 提交时间分布健康——主要在正常工作时间内完成
  
  里程碑：通知模块
  最近 7 天的提交时间分布：
    - 工作时间（9:00-18:00）：5 次提交
    - 晚间（18:00-22:00）：8 次提交
    - 深夜（22:00-6:00）：4 次提交
    - 周末：6 次提交（周六 3 次，周日 3 次）
  结论：⚠️ 大量提交在深夜和周末——可能表明：
    1. 计划不合理，导致赶工
    2. 开发者低估了工作量
    3. 节奏失控，可能导致质量下降
```

**如何解读提交时间分布**：

| 模式 | 对里程碑状态的影响 |
|------|-------------------|
| **主要在正常工作时间** | 节奏健康，完成状态可信——代码是在正常状态下写的 |
| **有少量晚间/周末提交** | 偶尔加班，可能是个别任务的突发情况，不影响整体完成状态的可信度 |
| **大量深夜和周末提交** | ⚠️ 节奏失控——代码可能是在疲劳状态下写的，质量不可靠。即使"完成了"，也可能遗留了技术债或 bug |
| **全部在深夜提交** | 🚨 严重节奏失控——项目可能遇到了严重的计划问题。建议重新评估计划 |

**需要注意**：提交时间分布是一个**辅助信号**，不是决定性证据。它不改变"完成/未完成"的状态，但影响"完成质量"的评估：
- 如果提交时间分布健康，完成状态的可信度更高
- 如果提交时间分布显示节奏失控，在报告中注明"完成状态可信，但建议检查代码质量"
- 不要替用户判断"什么节奏是可持续的"——有些人习惯在深夜工作，这不一定是节奏失控。关注的是"模式变化"——如果之前的提交在正常工作时间，突然变成大量深夜提交，才是需要关注的信号

### 5. 综合判断里程碑的完成状态

综合以上四个维度的证据，对里程碑的完成状态做出综合判断：

```
里程碑完成状态综合判断：

里程碑：用户认证模块
├── 测试证据：✅ 测试先于代码，覆盖率 87%
├── 集成证据：✅ 已合并到主分支
├── CI 证据：✅ 全部通过
├── 节奏证据：✅ 提交时间分布健康
└── 综合结论：✅ 有证据完成——完成状态可信度高

里程碑：通知模块
├── 测试证据：⚠️ 代码先于测试，测试是事后补的
├── 集成证据：❌ 未合并到主分支，分支存在 3 天
├── CI 证据：⚠️ 上次 CI 失败，最新 CI 运行中
├── 节奏证据：⚠️ 大量深夜和周末提交
└── 综合结论：❌ 未完成——代码存在但未集成、未验证、节奏失控
```

**完成状态可信度分级**：

| 证据组合 | 综合结论 | 说明 |
|---------|---------|------|
| 测试 + 集成 + CI 全部通过，且节奏健康 | **有证据完成** | 最可靠的完成状态——代码写完了、验证了、集成了 |
| 测试 + 集成 + CI 全部通过，但节奏异常 | **有证据完成（质量存疑）** | 虽然验证通过了，但节奏异常可能影响代码质量 |
| 测试存在 + 已集成，但 CI 未运行 | **有证据完成（待验证）** | 代码存在且已集成，但缺少自动化验证 |
| 测试存在 + 未集成 | **部分完成** | 代码写完了，但还没有集成到主分支 |
| 只有代码，没有测试、没有集成、没有 CI | **声称完成** | 缺乏任何客观证据，完成状态不可信 |
| 代码存在但有 CI 失败 | **未完成** | 即使代码写完了，CI 失败说明"没有做好" |
| 代码不存在 | **未开始** | 根本没有开始做 |

**证据冲突时的处理**：
- 如果"测试证据"和"节奏证据"冲突（如测试先于代码但大量深夜提交）——以"测试证据"为准，但注明"节奏异常"
- 如果"CI 证据"和"测试证据"冲突（如测试存在但 CI 失败）——以"CI 证据"为准，因为 CI 运行的是完整验证
- 如果"集成证据"和"测试证据"冲突（如测试存在但未集成）——两者都不可偏废，建议"先集成再验证"
- 不存在"一个证据否定另一个证据"的情况——每类证据回答不同的问题，综合判断时取"最弱的一环"

### 6. 生成里程碑状态报告

将以上检查结果汇总为里程碑状态报告，作为 Track 报告的组成部分：

```
## 里程碑状态报告

### 全部里程碑概览

| 里程碑 | 测试证据 | 已集成 | CI 通过 | 节奏健康 | 综合状态 |
|--------|---------|--------|---------|---------|---------|
| 用户认证模块 | ✅ | ✅ | ✅ | ✅ | 有证据完成 |
| 通知模块 | ⚠️ | ❌ | ⚠️ | ⚠️ | 未完成 |
| 项目初始化 | ✅ | ✅ | ✅ | ✅ | 有证据完成 |
| 数据库设计 | ✅ | ✅ | ⚠️ 无 CI | ✅ | 有证据完成（待验证） |

### 需要关注的里程碑

**通知模块**（未完成）
- 测试：代码先于测试，测试是事后补的
- 集成：未合并到主分支，分支存在 3 天
- CI：上次 CI 失败，当前运行中
- 节奏：大量深夜和周末提交
- 建议：先解决 CI 失败问题，再合并到主分支，最后重新评估完成状态

### 整体状态
- 有证据完成：3 个
- 有证据完成（待验证）：1 个
- 未完成：1 个
- 未开始：0 个
- 完成率：60%（3/5）
- 可信度：高（大部分里程碑有测试和 CI 证据支撑）
```

## 不适用场景

- **原型项目**：对于一次性原型或探索性项目，要求"测试先于代码"和"CI 通过"是不合理的。原型阶段的代码本来就是"用完就扔"的，测试和 CI 会拖慢探索速度。此时忽略测试和 CI 检查，只检查"代码是否存在"和"是否已集成"。
- **纯文档类工作**：写文档、画设计图、做调研报告——这些工作通常没有测试和 CI 的概念。里程碑状态直接按"文件是否存在"判断即可。
- **无测试文化的项目**：如果用户明确表示"我不写测试，我只是快速验证想法"，强制要求测试证据是不恰当的。此时只检查"代码是否已集成"和"是否已合并到主分支"。
- **个人实验项目**：个人项目可能没有 CI 配置、没有正式的测试框架、没有主分支保护。里程碑状态的检查应该降低标准——"代码存在"和"文档存在"就是足够的证据。
- **配置类变更**：修改配置文件、调整 CI 流程、升级依赖——这些变更本身不需要测试（它们有自身的验证机制，如 CI 配置本身在 CI 中运行）。里程碑状态按"变更是否已合并"判断即可。
- **用户明确表示"不需要质量检查"**：如果用户说"我只是想快速做个东西，不在乎质量"，里程碑状态卡的核心假设（"完成"需要证据）就不适用了。此时直接按"声称完成"报告即可，不做额外验证。
