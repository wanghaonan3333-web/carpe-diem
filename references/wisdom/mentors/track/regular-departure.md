# 行为卡：定期发车

> 固定时间表，不等特性——用时间约束替代范围承诺，让交付节奏可预测

## 问题本质

大多数项目的时间管理方式是**范围驱动**的：先定要做什么，再估算需要多少时间，然后让时间去适应范围。当一个特性没做完时，延期——因为"不能让它没做完就发车"。

但这种方式有一个根本问题：**范围是无限的，时间是有限的**。当你说"这个特性很重要，必须等它"时，下一个特性也会同样重要，再下一个也一样。每次延期都有"充分的理由"，但结果永远是同一个——交付时间不可预测。

问题的根源是：**你把"范围"当成了约束，把"时间"当成了变量**。但有效的项目交付需要的恰恰相反——**时间是约束，范围是变量**。

"定期发车"的核心逻辑是：

1. **时间表是固定的**——下一个交付节点在时刻表上写得清清楚楚，到了就发车
2. **特性赶不上就等下一班**——不是"等特性"，而是"特性等下一班车"
3. **质量门禁是严格的**——即使特性在最后一刻完成了，如果质量不达标，仍然不能上车
4. **Go/No-Go 决策是正式的**——每个节点都有明确的决策点，不靠"感觉"决定

这不是"严格"或"不近人情"——而是"可预测"。用户的可预测性比"多一个特性"更重要：一个可预测的、每六周交付一次的节奏，比一个"等所有特性都做好才交付、但不知道什么时候能做好"的承诺，更有价值。

## 触发条件

在以下任一场景中触发：

- **一个特性超出预期时间，团队在讨论是否延期交付**——"这个特性快做完了，再等两天就好"——这是最典型的触发场景，说明时间约束正在被范围侵蚀
- **用户说"再加一个小功能，应该不会影响交付时间"**——"小功能"的累积效应是范围蔓延的根源
- **交付时间被多次推迟，且每次都是"因为某个特性还没做完"**——说明"范围驱动"的模式已经形成，需要切换到"时间驱动"
- **用户说"这个版本做完了就发布，但不知道什么时候能做完"**——没有固定时间表，交付节奏不可预测，需要建立定期发车机制
- **多个利益相关方同时要求"这个版本必须包含我的功能"**——范围竞争导致时间表不断膨胀，需要用固定时间表来约束范围

## 行为指导

### 1. 建立固定的交付节奏——时间表是铁律

确定一个固定的交付周期（如每 4 周、每 6 周、每 8 周，取决于项目类型和复杂度），然后把时间表写得清清楚楚：

```
交付节奏示例：
  周期：每 6 周一次交付
  时间表：
    第 1 周：确定本次交付的范围（已确认上车的特性）
    第 2-3 周：开发和内测
    第 4 周：集成测试和验收
    第 5 周：发布候选（RC）阶段
    第 6 周：正式交付
  下一个交付节点：2026-10-15（第 6 周，不可更改）
```

**时间表的核心原则**：
- 时间表是**对外承诺**，不是对内参考——一旦公布，除非有不可抗力，否则不更改
- 时间表以**固定间隔**为单位，而不是以"完成哪些特性"为单位——"每 6 周一次"是承诺，"做完这 5 个功能就发布"不是承诺
- 时间表让用户知道"什么时候能得到什么"，而不是"什么功能什么时候能得到"

**如何说服团队接受固定时间表**：
- 说明"可预测性"的价值：用户更愿意接受"每 6 周稳定交付少量功能"，而不是"不知道什么时候能交付大量功能"
- 强调"错过一班车不等于永远错过"——赶不上的特性会在下一班车优先考虑
- 用一个试验周期来验证：先试行 2 个周期，如果确实不适合再调整

### 2. 设立质量门禁——每个节点都有明确的通过标准

在每个交付周期中设立**质量门禁**——只有通过门禁的特性才能继续前进，未通过的退回修改或等待下一班车：

```
质量门禁示例：

门禁 1：开发完成（第 3 周末）
  通过标准：
    - 代码已通过代码审查
    - 单元测试覆盖率达到 80% 以上
    - 所有测试通过
  未通过处理：特性退回修改，修改后如果赶不上第 4 周的集成测试，则自动进入下一班车

门禁 2：集成测试通过（第 4 周末）
  通过标准：
    - 所有特性已合并到主分支
    - 集成测试全部通过
    - 没有回归缺陷
  未通过处理：特性拆下，主分支回滚到上一个稳定版本，问题特性等待下一班车

门禁 3：验收通过（第 5 周末）
  通过标准：
    - 产品验收测试通过
    - 性能测试达标
    - 文档已更新
  未通过处理：候选版本回退，未通过的特性等待下一班车
```

**门禁的四个关键原则**：

1. **标准是公开的，不是临时的**——每个门禁的通过标准在周期开始时就要公布，不能临到门禁前才说"这个也要检查"
2. **标准是客观的，不是主观的**——"代码审查通过"是客观标准，"代码质量好"是主观标准。所有门禁标准都应该是可验证的
3. **门禁是自动化的，不是人工的**——尽可能把门禁自动化（CI 检查、测试覆盖率检查、lint 检查），减少"人工判断"带来的不一致
4. **门禁是严格的，不是可协商的**——如果某个特性在门禁前没有达到标准，不要"通融一次"。通融一次就会有第二次，门禁就形同虚设

### 3. 在每个门禁点做 Go/No-Go 决策

在每个门禁点，不做"这个特性做完了吗"的检查，而是做**"这个特性是否应该继续前进"的决策**：

```
Go/No-Go 决策表：

门禁 1（开发完成）：
  特性 A：✅ 代码审查通过，测试覆盖率 85%，全部测试通过 → Go
  特性 B：⚠️ 代码审查通过，但测试覆盖率仅 60% → No-Go
    处理方式：退回修改测试覆盖，如果第 4 天前完成修改，可以赶上集成测试
    如果赶不上，特性 B 自动进入下一班车
  特性 C：❌ 代码审查未通过，5 个测试失败 → No-Go
    处理方式：退回修改，自动进入下一班车

门禁 2（集成测试）：
  特性 A：✅ 已合并到主分支，集成测试通过 → Go
  特性 B：❌ 未完成修改，未赶上集成测试 → 自动进入下一班车
  特性 C：❌ 未完成修改，未赶上集成测试 → 自动进入下一班车

门禁 3（验收）：
  特性 A：✅ 验收测试通过，性能达标，文档已更新 → Go
```

**Go/No-Go 决策的四个原则**：

1. **No-Go 不是"失败"**——No-Go 的意思是"这个特性还没准备好，但下个周期会准备好"。这不是对特性的否定，而是对交付节奏的保护
2. **决策要基于门禁标准，而不是基于"感觉"**——"我觉得这个特性差不多了"不是决策依据，"门禁标准全部通过"才是
3. **错过一班车不等于永远错过**——赶不上本班车的特性，在下一班车优先考虑。这不是惩罚，这是节奏
4. **No-Go 决策要尽早做**——不要在门禁截止时间才说"这个特性来不及了"。如果中途发现特性可能赶不上，尽早通知，让团队有心理准备

### 4. 范围管理——"特性等下一班车"是正常流程，不是例外

当某个特性赶不上本班车时，不要把它当作"事故"来处理——它应该是**正常流程的一部分**：

```
特性赶不上本班车时的处理流程：

1. 发现特性可能赶不上（在门禁前 2-3 天）
   → 评估：是真的赶不上，还是需要加班就能赶上？
   → 如果赶不上：确认特性不会临时上车，通知相关方

2. 门禁点正式判断
   → 如果未通过门禁：特性自动进入下一班车
   → 记录：本班车发了什么，什么特性在等下一班车

3. 下一班车规划时
   → 优先考虑上一班车未赶上的特性
   → 评估特性的优先级是否有变化（如果上一班车赶不上，这个特性是否还那么重要？）
   → 如果特性仍然重要，安排上车

4. 对外沟通
   → 告知用户：本班车发了什么，什么特性在下一班车
   → 不解释"为什么没赶上"——解释原因会让人误以为"下次可以通融"
   → 只陈述事实：这个特性在下一班车，下一班车的时间是 X 月 X 日
```

**"特性等下一班车"的四个关键认知**：

1. **这不是惩罚，是节奏**——特性赶不上本班车，不是"做错了什么"，而是"时间表是固定的，特性需要时间"
2. **这不是浪费，是投资**——没有完成的特性不是"白做了"，而是"为下一班车积累了经验"。代码、测试、设计文档都在，下一班车复用这些积累，完成速度会更快
3. **这不是事故，是常态**——在一个固定时间表的交付周期中，总会有特性赶不上。这不是"出了问题"，而是"系统在正常运作"
4. **这不是失败，是学习**——如果某个特性连续两班车都赶不上，说明这个特性的评估有问题。下次评估时，要么把它拆得更小，要么给它更多的周期

### 5. 定期回顾节奏——每个周期结束后复盘

每完成一个交付周期，做一次简短回顾，检查节奏是否健康：

```
周期回顾模板：

周期：第 3 次交付（2026-08-15 至 2026-09-26）

本班车发出：
  - 特性 A：用户认证模块（按计划完成）
  - 特性 B：通知模块（按计划完成）
  - 特性 C：数据库优化（按计划完成）

等下一班车：
  - 特性 D：高级搜索功能（未通过集成测试门禁，自动进入下一班车）
  - 特性 E：导出功能（未通过开发完成门禁，自动进入下一班车）

门禁通过率：
  - 门禁 1（开发完成）：3/5 通过（60%）
  - 门禁 2（集成测试）：3/4 通过（75%）
  - 门禁 3（验收）：3/3 通过（100%）

周期健康度：
  - 按时交付率：3/5（60%）——本班车计划的 5 个特性，按时发出了 3 个
  - 门禁严格度：良好——没有因为"赶时间"而放宽门禁标准
  - 节奏稳定性：良好——周期长度与计划一致（6 周）

改进方向：
  - 特性评估：两个特性未能完成，说明评估时高估了团队吞吐量
  - 门禁标准：门禁 1 的通过率偏低（60%），需要检查"开发完成"的标准是否过于严格，或特性拆分是否合理
  - 范围管理：下个周期考虑减少上车特性的数量，从 5 个减少到 4 个
```

**回顾的核心问题**：

- **本班车发出了多少？**——按时交付率是衡量节奏健康度的关键指标
- **门禁是否被严格执行？**——如果某个周期没有 No-Go，说明门禁可能太松了
- **特性是否被合理拆分？**——如果某个特性连续两班车都赶不上，说明它应该被拆分成更小的特性
- **节奏是否稳定？**——如果周期长度在变化（如第一次 6 周，第二次 8 周，第三次 5 周），说明节奏还没有建立起来
- **用户是否满意？**——固定时间表的最终目的是让用户获得可预测的交付。如果用户不满意，需要重新评估节奏是否适合

### 6. 处理"紧急例外"——真正的紧急情况如何处理

固定时间表不等于"死板"。当真正的紧急情况出现时，需要有一个明确的例外处理流程：

```
紧急例外处理流程：

第一步：判断是否真的是"紧急"
  真正紧急的标准：
    - 安全漏洞（需要立即修复）
    - 用户数据丢失或损坏
    - 核心功能完全不可用
    - 法律或合规要求的紧急变更
  不是紧急的标准：
    - "重要客户要求"——除非这个要求有明确的截止日期和法律后果
    - "老板说这个功能很重要"——重要的功能应该在下一班车规划中优先考虑
    - "竞争对手发布了类似功能"——这不是紧急，这是竞争压力

第二步：走"紧急通道"而不是"推迟列车"
  紧急通道规则：
    - 紧急修复可以单独发布（不占本班车的位置）
    - 紧急修复走独立的快速验证流程（不经过正常的门禁流程）
    - 紧急修复在完成后，立即补入本班车或单独发布

第三步：记录紧急事件
    - 记录：什么事件、为什么是紧急、如何处理的
    - 在周期回顾中讨论：这个紧急事件是否可以避免？
    - 如果某类紧急事件频繁出现，说明系统层面有问题，需要从源头解决
```

**紧急例外的核心原则**：不要因为"这个特性很重要"就推迟列车——推迟列车会破坏整个交付节奏，对所有用户和所有特性都造成影响。真正紧急的情况应该走专门的紧急通道，而不是破坏时间表。

## 不适用场景

- **探索性项目**：如果项目是探索性的（如"研究一个新技术是否可行"），没有固定的交付节奏——你不知道什么时候会有结果，也不应该设定硬性的时间表。此时"定期发车"不适用，应该用"里程碑状态"卡来追踪进展。

- **个人自由项目**：如果项目是个人自由时间做的（如"周末写一个小工具"），没有外部交付承诺，固定时间表反而会压制创造力。此时没有"必须发车"的压力，应该让范围驱动时间，而不是时间驱动范围。

- **MVP / 初创项目**：在项目的最早期（寻找产品-市场匹配的阶段），你可能需要快速迭代、频繁调整方向，固定的时间表反而会成为束缚。此时每个周期可能都在做不同的事，节奏本身没有意义。当产品-市场匹配确定后，再引入固定节奏。

- **外部硬性截止日期项目**：如果项目有一个不可更改的外部截止日期（如"必须在 12 月 31 日前完成，因为法规要求"），这个截止日期本身就是固定的，但"定期发车"的节奏不适用——因为只有一个截止日期，没有"连续的多班车"。此时应该用"里程碑状态"卡来管理到这个截止日期的进展。

- **团队规模极小（1-2 人）**：对于单人项目或两人项目，正式的门禁和 Go/No-Go 决策带来的管理成本可能超过收益。当团队规模很小时，简单的"做完了就发布"可能比固定的交付节奏更高效。
