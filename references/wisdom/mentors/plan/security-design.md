# 行为卡：安全设计

> 触发条件：Plan 阶段进入"架构、组件、数据流"章节，系统涉及用户数据或外部访问

## 问题本质

大多数人认为安全是"上线前加一层安全防护"——等代码写完了，再加一个防火墙、上一个 WAF、做一次安全扫描，就算是"安全了"。但问题是：**安全不是贴上去的一层东西，而是从设计阶段就融入每个决策的质量属性**。

如果你在架构设计时没有考虑安全，等到实现完成后再去"加固"，你会面临：数据结构需要重新设计（因为密码没有加密存储）、接口需要重新设计（因为权限校验没有做）、大量代码需要重写（因为输入校验被分散在各处）。安全"加"上去的成本，比"设计进去"的成本高出一个数量级。

问题的根源是：**你把"安全"当成了"上线前的检查项"，但它其实是"设计阶段的质量要求"**。就像一栋楼，你不能先把楼盖好，再去"加"地基——安全就是地基的一部分。

## 触发条件

用户正在执行以下任一操作时触发：
- Plan 阶段进入"架构"章节，系统涉及用户数据（个人信息、密码、支付信息等）或外部访问（公开 API、Web 页面等）
- 用户说"安全后面再考虑"或"先实现功能，上线前再补安全"——这是最危险的信号，说明安全完全被排除在设计之外
- 用户说"我们项目小，没人会攻击"——攻击不一定是针对你的，自动扫描工具每天都在扫描所有公网服务
- 架构讨论中完全没有涉及"谁可以访问什么"、"数据如何保护"、"如何应对攻击"等安全话题

## 行为指导

### 1. 在设计阶段识别敏感数据和攻击面——不知道什么东西需要保护，就无法设计保护方案

在开始设计系统之前，先回答这些问题：

- **系统中有哪些敏感数据？** 用户密码、个人信息、支付信息、会话令牌、业务机密……不是所有数据都需要同样的保护级别。先列出所有敏感数据，然后对它们分级。
- **谁可以访问这些数据？** 用户本人可以访问自己的数据，管理员可以访问管理数据，但普通用户不能访问其他用户的数据。这是最基本的权限边界。
- **系统的攻击面在哪里？** 所有外部输入的入口都是攻击面：用户输入、API 请求、文件上传、第三方回调、Webhook。每个入口都需要考虑"如果这里传入恶意数据，会发生什么"。
- **最坏情况下能造成什么损失？** 如果攻击者攻破了系统，能获得什么？用户数据泄露？系统被控制？业务中断？不同的损失级别需要不同的防护投入。

具体做法：在架构设计文档中，单独开一个"安全设计"章节，明确列出敏感数据、访问权限、攻击面，以及每个攻击面的防护措施。不要等到代码写完再写这个章节——它应该影响架构决策。

### 2. 默认最小权限原则——给每个组件、每个用户恰好够用的权限，不多不少

最小权限原则是安全设计中最基础也最重要的原则：**任何主体（用户、服务、进程）只拥有完成其任务所必需的最小权限**。

- **用户权限**：普通用户只能访问自己的数据，不能访问其他用户的数据。管理员有管理权限，但管理权限应该分角色（如"用户管理"和"系统配置"可以分开）。
- **服务间权限**：服务 A 调用服务 B 时，只应该获得它需要的接口权限，而不是"所有接口"。不要因为"方便"而让一个服务拥有调用所有其他服务的权限。
- **数据库权限**：应用连接数据库的用户，只应该拥有它需要的表级权限，而不是"所有权限"。比如，只读查询用只读用户，数据写入用写用户——不要用一个"超级用户"连接所有应用。
- **文件系统权限**：应用只应该读写它需要的目录，而不是整个文件系统。

具体做法：在架构设计阶段，明确标注每个组件的"最小权限范围"，并在实现时强制实施。如果某个组件需要额外的权限，应该通过审批流程获得，而不是默认拥有所有权限。

### 3. 输入校验从第一天开始——所有外部输入都是不可信的，直到被验证

安全设计的核心假设是：**所有来自系统外部的输入都是不可信的**。用户输入、API 请求、文件上传、第三方回调——这些数据必须在被使用之前进行校验。

- **校验输入格式**：如果输入是邮箱，校验它是否符合邮箱格式；如果是数字，校验它是否是数字。不要假设"用户不会乱填"。
- **校验输入长度**：设置合理的输入长度限制。防止缓冲区溢出、防止数据被无限写入。
- **校验输入范围**：如果输入是枚举值（如状态），校验它是否在合法范围内。不要接受"值被篡改"的请求。
- **拒绝而非过滤**：输入校验的原则是"拒绝不合法的输入，而不是过滤掉危险的部分"。过滤往往有遗漏，拒绝是安全的。

具体做法：在系统入口处（API 网关、请求处理中间件）统一做输入校验，而不是在每个接口内部单独做。这样即使有接口忘记校验，入口层也能兜底。

### 4. 使用经过验证的库而非自己实现——安全领域没有"自己实现更好"这回事

在安全领域，自己实现加密、认证、鉴权是最常见的安全漏洞来源。原因是：**安全实现需要大量的专业知识和经验，而大多数开发者没有这些知识**。

- **密码存储**：不要自己实现密码哈希算法，使用 bcrypt、scrypt、Argon2 等经过验证的库。不要用 MD5 或 SHA-1 存储密码——它们是为完整性设计的，不是为密码存储设计的。
- **认证**：使用标准的认证框架（如 OAuth 2.0、OpenID Connect），不要自己实现令牌生成和验证。如果你自己实现，很可能会漏掉签名验证、令牌过期、刷新机制等关键环节。
- **加密**：使用标准的加密库（如 libsodium、OpenSSL），不要自己实现加密算法。自己实现加密几乎必然存在漏洞。
- **会话管理**：使用框架提供的会话管理机制，不要自己实现。自己实现的会话管理通常存在会话固定、会话劫持等问题。

具体做法：在技术选型阶段，就确定使用的安全库和框架。不要等到需要的时候才去找——那时候很容易因为"赶进度"而选择"自己实现"。

### 5. 建立安全响应计划——不是"如果"被攻击，而是"当"被攻击时怎么办

安全设计不是"防止所有攻击"——因为没有任何系统能防止所有攻击。安全设计是"在被攻击时，能快速发现、快速响应、快速恢复"。

- **发现机制**：如何知道系统被攻击了？日志告警、异常流量检测、错误率飙升、用户投诉……这些都需要在系统设计时就规划好。
- **响应流程**：当发现攻击时，第一步做什么？隔离受影响的系统？通知相关人员？保存攻击证据？这些步骤应该在事前确定，而不是在攻击发生时临时想。
- **恢复流程**：攻击发生后，如何恢复系统正常运行？数据恢复、服务重启、漏洞修复、用户通知……这些也需要预先规划。
- **事后复盘**：攻击事件后，如何总结教训并改进系统？每次攻击都是改进安全设计的机会。

具体做法：在架构设计文档中，包含"安全响应计划"章节，明确"谁在什么情况下做什么"。即使你的系统很小，也需要一个简单的响应计划——至少知道"被攻击时联系谁"。

### 6. 定期进行安全审查——安全不是"一次做完就完事"，需要持续维护

安全不是一次性的工作。随着系统的发展、依赖的更新、攻击手段的演进，安全风险也在不断变化。定期安全审查是保持系统安全的关键。

- **代码审查中的安全视角**：在每次 Code Review 中，加入安全检查点——"这个改动是否引入了新的安全风险？这个接口是否做了权限校验？这个输入是否做了校验？"
- **依赖更新审查**：定期检查依赖库的安全漏洞。使用依赖扫描工具（如 Dependabot、Snyk）自动检测已知漏洞，并评估是否需要更新。
- **渗透测试**：定期（如每季度或每半年）进行渗透测试，模拟真实攻击场景，发现系统的安全弱点。
- **安全培训**：定期对团队成员进行安全培训，让每个人都知道"什么做法是安全的、什么做法是危险的"。

具体做法：在项目计划中，将"安全审查"列为定期活动（如每个 sprint 一次），而不是"上线前做一次"。安全审查应该像代码审查一样自然。

## 不适用场景

- **纯本地工具**：如果系统只在本地运行，不对外提供服务，不处理其他用户的数据，安全设计可以简化。纯本地工具不需要考虑网络攻击、权限管理、认证等安全性问题，但基本的敏感数据保护（如密码存储）仍然需要。
- **不处理用户数据的原型**：如果项目处于原型阶段，且不处理真实用户数据（如使用测试数据、模拟数据），安全设计是过度设计。原型结束后会被丢弃，不需要考虑安全防护。但注意：一旦原型需要处理真实用户数据，安全设计就必须引入。
- **学习项目**：如果项目是个人学习用途（如学习新语言、新框架的练习项目），不处理真实数据，不对外提供服务，安全设计不需要。学习项目的目的不是"上线"，而是"练习"。
- **内部演示工具**：如果系统只在内部网络中使用，访问者都是可信的内部成员，且不涉及敏感数据，安全设计可以简化。但需要确保：内部网络不等于安全网络——如果内部网络中有其他不安全的系统，你的系统也可能被影响到。
