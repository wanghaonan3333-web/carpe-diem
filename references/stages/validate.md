# Validate · 用现实证据验证方向

## 一句话本质

一个点子只有经得起现实世界的反证，才值得变成项目。

## 进入条件

- Discover 已记录用户确认的方向；
- 问题和目标用户已经可以明确表述；
- 至少有一个可被证据推翻的核心假设。

## 主动讲授

先讲清“功能相似”不等于“问题定义相同”，也不等于存在市场空缺。验证的目标不是证明用户一定正确，而是尽快找到足以否定或收窄方向的事实。

## Agent 动作

1. 定义直接竞品、间接替代品和相邻基础设施三类搜索范围。
2. 优先使用当前、权威或一手来源；记录来源链接和检索日期。
3. 比较问题定义、目标用户、关键工作流、核心承诺和缺口。
4. 查找用户抱怨、未满足场景和已知失败尝试。
5. 提出最危险的反对意见和明确淘汰条件。
6. 区分已证实差异、合理推断和未知项。
7. 给出 `PASS`、`PIVOT` 或 `REJECT` 建议。

## 用户决策

Carpe Diem 先给推荐和理由。只有证据允许多种合理解释时，请用户在接受建议、调整切口或退回 Discover 中选择。

## 表达示例

> 现在我要主动寻找谁已经做过、用户用什么替代、这个方向为什么可能失败。只有找完反证，我们才谈独特性。

## 成功信号

- 最接近的竞品和替代行为已被覆盖；
- 差异化陈述带来源与不确定性；
- 核心反对意见有回应；
- 验证结论明确为 `PASS`、`PIVOT` 或 `REJECT`；
- 用户确认是否进入 Plan。

## 常见误区

- 用 GitHub Star 数代替用户价值；
- 堆链接但没有结论；
- 搜索不到就声称“没人做过”；
- 只找支持方向的证据；
- 把多个普通功能的组合自动称为创新。

## 状态写入

保存来源、检索日期、竞品摘要、差异、未知项、淘汰条件、结论和用户决定。联网或证据不足时把 `validation.status` 设为 `incomplete`。

## 下一步路由

- `PASS` 且用户确认：`phase=plan`，加载 `references/stages/plan.md`。
- `PIVOT`：保留原问题和证据，更新方向后继续 Validate。
- `REJECT`：记录淘汰原因，`phase=discover`。
