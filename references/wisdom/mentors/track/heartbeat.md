# 行为卡：心跳

> 建立持续反馈循环——采集流动证据、收集反馈、沉淀学习，形成规律的追踪脉搏
> 蒸馏日期：2026-09-01

## 问题本质

大多数进度报告是**单向汇报**的：Track 阶段采集证据、生成报告、交给用户，然后就结束了。但项目追踪不是"报告完了就完了"——它是一个持续循环。

问题的根源是：**你把追踪当成了"拍照"，而不是"脉搏"**。

拍照是定点的——一个时间点上的快照，告诉你"现在怎么样了"。但项目不是静止的，它是一个流动的系统——代码在不断提交、分支在不断合并、阻塞在不断出现又在不断被解决。如果你只在某个时间点拍一张照片，你看到的只是"项目在那个瞬间的样子"，而不是"项目在如何变化"。

更糟糕的是，没有反馈循环的追踪往往导致以下问题：

1. **同样的偏差反复出现**——上次 Track 报告了"测试环节阻塞"，这次 Track 发现"测试环节仍然阻塞"，但没有任何机制确保阻塞被解决
2. **经验没有沉淀**——每次 Track 都从零开始，不记得上次的教训，不积累改进的方向
3. **建议变成了噪音**——每次 Track 都给出建议，但建议是否被采纳、是否有效，没有人追踪

**心跳**解决这个问题：把 Track 从"一次性的报告"变成"持续的循环"——每次 Track 不是独立的，而是上一次心跳的延续。这次发现的问题，在下一次心跳中检查是否被解决；这次学到的经验，在下一次心跳中验证是否被沉淀。

## 触发条件

在以下任一场景中触发：

- Track 阶段开始执行时（每次 Track 都应该是一次心跳）
- 用户说"上次 Track 说的问题还在吗"（需要检查前次心跳的反馈是否被闭环）
- 里程碑到达计划中的检查点
- 用户说"感觉同样的偏差出现了好几次"（说明反馈循环没有建立）
- 用户说"每次 Track 都给出建议，但好像没什么变化"（说明学习环节缺失）
- 用户说"项目状态好像停滞了，但不知道卡在哪里"（需要价值流视角的诊断）

## 行为指导

### 1. 建立"流动 → 反馈 → 学习"的三段式心跳循环

每次 Track 执行时，遵循三段式结构——不是单向汇报，而是循环的脉搏：

```
第一段：采集流动证据
  检查代码是否在流动——合并频率、提交活跃度、CI 管道状态
  检查里程碑是否在推进——哪些完成了、哪些进行中、哪些阻塞了
  采集量化指标——前置时间、变更失败率、恢复时间
  目标：回答"项目的血液是否在流动"

第二段：收集反馈信号
  对比计划 vs 实际——识别偏差
  定位偏差发生环节——是规划问题、开发问题、还是验证问题？
  检查前次心跳的建议是否被采纳
  目标：回答"流动中的偏差在哪里"

第三段：沉淀学习，生成下一步
  将本次发现总结为可复用的经验
  生成改进建议——不只是"修复问题"，而是"避免下次再出现"
  设定下一次心跳的检查重点
  目标：回答"这次学到了什么，下次该关注什么"
```

这个三段式结构确保每次 Track 不是独立的，而是上一次心跳的延续：

```
心跳 1 → 心跳 2 → 心跳 3 → ...
  │         │         │
  │         └─ 检查心跳 1 的建议是否被采纳
  │         └─ 检查心跳 1 发现的偏差是否被纠正
  │
  └──── 沉淀的经验 → 用于心跳 2 的改进建议
  └──── 设定的检查点 → 心跳 2 的关注重点
```

### 2. 绘制"价值流"——定位偏差在哪个环节

当 Track 发现进度偏差时，不是简单报告"慢了"，而是定位"哪个环节"出了问题：

```
价值流分析：
  当前里程碑的流动路径：
    规划 → 设计 → 编码 → 测试 → 验收 → 部署

  各环节当前状态：
    规划：✅ 已完成（2 天前完成）
    设计：✅ 已完成（1 天前完成）
    编码：⚠️ 进行中（已 5 天，预计仍需 2 天）
    测试：⏳ 等待中（编码完成后才能开始）
    验收：⏳ 等待中
    部署：⏳ 等待中

  偏差定位：
    编码环节是当前瓶颈——原计划 3 天，实际已 5 天
    可能原因：
      - 任务粒度太大，中间没有检查点
      - 编码过程中遇到了未预料的复杂度
      - 开发者在并行处理其他任务，编码被中断

  建议：
    1. 检查编码环节是否遇到了技术难题
    2. 考虑将编码任务拆分为更小的子任务
    3. 下次规划时，为编码环节预留更多缓冲时间
```

**价值流分析的核心问题**：
- **哪个环节消耗了最多的时间？**——找到"时间黑洞"环节
- **哪个环节前堆积了最多的等待任务？**——找到"瓶颈堆积"环节
- **哪个环节的偏差最大？**——找到"计划最不准"的环节
- **哪个环节的偏差在持续扩大？**——找到"恶化中"的环节

**价值流分析不适用于**：
- 单环节项目（如"写一篇博客"只有一个环节）
- 探索性项目（没有固定的流程环节）
- 高度不确定的非流程化工作（流程本身在变化）

### 3. 使用"当前状态 → 目标状态 → 瓶颈 → 下一步"结构输出建议

每次心跳输出的建议，使用四步结构——确保建议不是"应该做什么"的模糊说教，而是"基于当前状态，指向目标状态，识别瓶颈，给出具体下一步"的结构化输出：

```
## 心跳建议

### 当前状态
- 项目正在推进 3 个里程碑，其中 1 个已完成，1 个进行中，1 个阻塞
- 合并频率：每周 3 次（稳定）
- 前置时间：平均 5 天（稳定）
- 变更失败率：20%（偏高）
- 上次心跳的建议：关注测试环节的阻塞——已解决（测试队列从 3 个减少到 1 个）

### 目标状态
- 合并频率：每周 5 次（加速集成）
- 前置时间：平均 3 天（缩短交付周期）
- 变更失败率：低于 15%（提升质量）
- 更具体的：所有里程碑在计划时间内完成，偏差不超过 20%

### 瓶颈分析
- 当前最大瓶颈：编码环节耗时超出预期（计划 3 天，实际 5 天）
- 瓶颈成因：编码任务粒度太大，没有中间检查点；开发者在编码过程中被中断
- 瓶颈影响：编码环节的延迟正在向下游传递——测试和验收的等待时间在增加
- 如果不解决：下一个里程碑也将面临同样的编码延迟

### 下一步
- 短期：将当前编码任务拆分为 3 个子任务，每个子任务设置 1 天的检查点
- 中期：在下次 Plan 阶段，为编码环节预留更多缓冲时间（从 3 天调整为 5 天）
- 具体动作：下一次心跳时，检查编码子任务的完成情况
- 谁来做：用户决定是否拆分任务，Track 负责跟踪拆分后的进度
```

**四步结构的核心原则**：
- **当前状态**：基于事实，不判断好坏——只说"是什么"，不说"好不好"
- **目标状态**：可衡量、可验证——不是"做得更好"，而是"前置时间缩短到 3 天"
- **瓶颈分析**：找到根本原因——不是"编码慢了"，而是"编码任务粒度太大"
- **下一步**：具体到"谁、做什么、什么时候检查"——不是"加快编码"，而是"拆分为 3 个子任务"

### 4. 建立"反馈闭环"——追踪建议是否被采纳

心跳的核心价值不是"给出建议"，而是"检查建议是否被采纳"：

```
反馈闭环追踪：

心跳 1（2026-08-25）：
  建议：关注测试环节的阻塞，建议减少并行测试的数量
  采纳状态：✅ 已采纳——测试队列从 3 个减少到 1 个
  效果：✅ 有效——测试前置时间从 3 天缩短到 1.5 天

心跳 2（2026-08-28）：
  建议：将编码任务拆分为更小的子任务
  采纳状态：⚠️ 部分采纳——拆分了一个任务，但其余任务仍然是原粒度
  效果：待验证——下次心跳检查拆分后的前置时间变化

心跳 3（2026-08-31）：
  建议：为编码环节预留更多缓冲时间
  采纳状态：❌ 未采纳——用户认为"编码慢是个别现象"
  效果：无法评估——建议未被采纳，前置时间仍在增长
  建议升级：如果编码前置时间持续增长超过 2 周，建议重新评估
```

**追踪建议的四个状态**：

| 状态 | 说明 | 建议的处理方式 |
|------|------|--------------|
| **已采纳，有效** | 建议被采纳，且产生了正面效果 | 记录为"有效经验"，下次遇到类似问题时优先使用 |
| **已采纳，无效** | 建议被采纳，但问题没有改善 | 重新分析瓶颈——可能是"找错了瓶颈"或"建议不够具体" |
| **部分采纳** | 建议被部分执行 | 检查未执行的部分——是"觉得没必要"还是"执行有困难" |
| **未采纳** | 建议未被采纳 | 不要重复建议——如果同一个建议连续 3 次未采纳，说明用户不认同这个方向。改为提供不同的建议，或询问用户的需求 |

**关键原则**：Track 不替用户做决定。建议被采纳或不被采纳，都是用户的自由。Track 的职责是：
- 记录建议的采纳状态
- 如果建议被采纳，验证效果
- 如果建议未被采纳，提供不同的建议（而不是重复同一个建议）
- 如果同一个建议连续 3 次未采纳，停止建议，改为询问用户的需求

### 5. 心跳报告模板

每次心跳的输出格式，建议使用以下标准模板。模板的三段式结构对应"流动 → 反馈 → 学习"循环：

```
## 心跳报告：第 {N} 次

### 流动概览
- 时间范围：2026-08-25 至 2026-08-31
- 合并频率：5 次/周（与上周持平）
- 平均前置时间：5 天（与上周持平）
- 变更失败率：15%（较上周的 20% 有所改善）
- 在制品数量：2 个（正常范围）

### 里程碑状态
| 里程碑 | 状态 | 前置时间 | 偏差 |
|--------|------|---------|------|
| 用户认证模块 | 有证据完成 | 3 天 | 无偏差 |
| 通知模块 | 进行中（编码） | 进行中，已 5 天 | 超期 2 天 |
| 数据库设计 | 有证据完成 | 2 天 | 无偏差 |

### 偏差分析
- 主要偏差：通知模块编码超期 2 天
- 偏差环节：编码环节（原计划 3 天，实际 5 天）
- 偏差原因：任务粒度太大，没有中间检查点
- 建议采纳率：上次心跳的 2 个建议中，1 个已采纳（测试阻塞解决），1 个部分采纳（任务拆分）

### 经验沉淀
- 什么做得好：测试环节的阻塞问题已解决，队列从 3 个减少到 1 个
- 什么做得不好：编码任务没有及时拆分，导致前置时间增长
- 学到的经验：编码任务粒度控制在 2 天以内，超过 2 天就应该设置检查点

### 下一步建议
- 短期：将通知模块的编码任务拆分为 3 个子任务
- 中期：下次 Plan 阶段，为编码环节预留更多缓冲时间
- 检查点：下一次心跳时检查编码子任务的完成情况
- 建议优先级：先解决编码环节的瓶颈，再关注其他环节
```

**心跳报告的频率**：
- 默认频率：每 3-5 天一次（或与里程碑的粒度匹配）
- 如果项目推进快（每天都有合并）：频率可以加快到每 1-2 天一次
- 如果项目推进慢（每周只有少量提交）：频率可以降低到每周一次
- 关键原则：**频率应该与项目的变化速度匹配**——如果项目每天都有变化，每周一次心跳会错过太多信号；如果项目每周只有一次提交，每天一次心跳就是噪音

### 6. 持续改进的螺旋——让每次心跳都比上一次更好

心跳不是"每次重复同样的流程"，而是"每次都比上一次更好"：

```
持续改进的螺旋：

心跳 1：建立基线
  - 采集所有指标和状态
  - 发现"测试环节是瓶颈"
  - 建议：减少测试队列

心跳 2：检查改进
  - 测试队列已减少，瓶颈转移到编码环节
  - 经验：测试环节的改进有效
  - 建议：拆分编码任务

心跳 3：再次检查
  - 编码任务已拆分，前置时间缩短了 30%
  - 新的瓶颈：验收环节（等待用户确认）
  - 经验：任务拆分对编码效率有明显提升
  - 建议：设置验收环节的截止时间

心跳 4：系统优化
  - 所有环节的流动效率都在改善
  - 关注点从"修复瓶颈"转向"维持稳定"
  - 经验：持续改进不是一次性修复，而是不断发现和解决新的瓶颈
```

**持续改进的核心原则**：
- 每次心跳关注 1-2 个关键改进点——不要试图一次解决所有问题
- 改进方向由"数据"决定，而非"感觉"——哪个环节的偏差最大，就优先改进哪个环节
- 改进效果需要 2-3 次心跳来验证——不要因为一次心跳没有看到效果就放弃
- 当所有环节都稳定后，关注点从"改进"转向"维持"——不再追求"更快"，而是追求"稳定可预测"

## 不适用场景

- **一次性项目**：如果项目是"做一次就结束了"（如"写一本电子书"），没有持续改进的必要。心跳卡的核心假设是"项目会持续一段时间，需要不断改进"——如果项目没有"下一次"，心跳就没有意义。
- **用户明确表示"不需要追踪"**：如果用户说"我不需要汇报，我只想自己把事做完"，心跳卡不适用。心跳的核心假设是"用户需要追踪反馈"，如果用户不需要，不要强加。
- **极短周期项目**：如果项目只有 1-2 天，建立心跳循环的时间成本高于收益。此时直接完成项目即可，不需要心跳报告。
- **探索性项目**：如果用户在做探索性研究，项目本身没有固定的流程和节奏，心跳的"流动 → 反馈 → 学习"循环不适用。探索性项目应该关注"学到了什么"而非"流动效率如何"。
- **没有"下一次"的项目**：如果用户明确表示"这是最后一个里程碑，完成后项目就结束了"，心跳卡不适用。心跳的核心价值是"下次比这次更好"，如果项目没有"下次"，这个价值就不存在。
- **用户拒绝采纳建议**：如果用户连续 3 次以上不采纳任何建议，说明用户对"改进"不感兴趣。此时不应继续使用心跳卡——改为只报告数据，不给出建议。
