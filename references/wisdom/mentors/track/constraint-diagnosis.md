# 行为卡：约束诊断

> 找到并消除瓶颈，把约束作为追踪焦点——而不是平等关注所有环节
> 蒸馏日期：2026-09-01

## 问题本质

大多数进度报告采用"平均视角"：报告所有里程碑的进度，关注每个里程碑的完成情况，试图"全面覆盖"。但平均视角掩盖了一个事实——**整个项目的吞吐量，取决于最慢的那个环节**。

一个典型的例子：如果你的项目有"设计→编码→测试→验收"四个环节，其中"测试"环节需要 3 天才能完成一轮，而其他环节只需要 1 天——那么无论你把设计和编码的速度提升多少，项目的整体交付速度仍然是 3 天一轮。因为"测试"环节决定了整个系统的节奏。

问题的根源是：**你把"平均速度"当成了"系统速度"**。

- 平均速度告诉你：每个环节平均 1.5 天完成——看起来不错
- 但系统速度是：最慢的环节需要 3 天——这才是真正的交付节奏

如果你优化了"编码"环节（从 1 天优化到 0.5 天），但"测试"环节仍然是 3 天——你的整体交付速度没有任何变化。你优化了一个不重要的环节，浪费了时间。

## 触发条件

在以下任一场景中触发：

- Track 阶段发现进度偏差，里程碑未按计划推进
- 多个里程碑都卡在同一个环节（如"等待测试"、"等待用户确认"、"等待 API 文档"）
- 用户说"感觉一直在推进，但项目没有实质性进展"
- 某个里程碑的前置时间远超其他里程碑
- 用户说"不知道哪个环节拖了后腿"

## 行为指导

### 1. 识别约束：哪个环节最慢？

在 Track 报告开始时，先做"约束识别"——找出当前项目中最慢的环节：

```
约束识别：
  里程碑进展：
    设计已完成 → 编码进行中 → 测试阻塞 → 验收未开始
    设计已完成 → 编码已完成 → 测试阻塞 → 验收未开始
    设计已完成 → 编码已完成 → 测试阻塞 → 验收未开始
    ...

  约束分析：
    - 所有里程碑都卡在"测试"环节
    - 测试环节目前是系统的瓶颈——它决定了整个项目的交付速度
    - 建议：先解决测试环节的问题，再关注其他环节
```

如何识别约束环节：
- **看堆积**：哪个环节前堆积了最多"等待中"的里程碑？堆积的地方就是瓶颈
- **看等待时间**：里程碑在哪个环节停留时间最长？停留时间最长的地方就是瓶颈
- **看排队**：如果多个里程碑在等待同一个资源或同一个条件，那就是瓶颈

常见的约束环节（按项目类型不同）：

| 典型环节 | 识别信号 | 说明 |
|---------|---------|------|
| 方案设计 | 多个里程碑在等待"方案确定" | 设计方案本身需要时间，且不确定性高 |
| 开发编码 | 开发人员过度忙碌，多个任务排队 | 纯粹的开发工作量瓶颈 |
| 测试验证 | 测试队列堆积，等待测试的里程碑越来越多 | 测试资源不足或测试流程过慢 |
| 用户确认 | 功能完成但等待用户反馈，长期无回应 | 外部依赖，难以控制 |
| 决策审批 | 等待某个决策才能继续推进 | 组织层面的瓶颈 |
| 集成部署 | 功能完成但集成/部署流程复杂 | 基础设施瓶颈 |

### 2. 利用约束：让最慢环节全力工作

找到约束环节后，下一步是"利用约束"——确保这个环节在全力工作，不受其他因素干扰：

```
利用约束检查：
  - 约束环节：测试
  - 是否在全力工作？是/否 → 测试资源被多个任务分时使用，不是全力工作
  - 是否有等待？有/无 → 测试人员在等待开发人员提供测试环境
  - 是否有干扰？有/无 → 测试人员被要求同时参与其他项目的验收
  - 建议：集中测试资源，减少分时任务，确保测试环境提前就绪
```

检查清单：
1. 约束环节是否在全力工作？——如果约束环节有闲置时间，整体交付速度会进一步下降
2. 约束环节是否有不必要的等待？——如果约束环节在等待输入，先解决输入问题
3. 约束环节是否有不必要的干扰？——如果约束环节被多任务分散，减少并行任务

**关键原则**：约束环节的"闲置"是最大的浪费。一个非约束环节闲置 1 小时，损失 1 小时；但约束环节闲置 1 小时，整个项目损失 1 小时。

### 3. 服从约束：其他环节配合最慢环节

识别约束后，其他环节应该"服从"约束——以约束环节的节奏来安排自己的工作：

```
服从约束检查：
  - 约束环节：测试
  - 其他环节是否在等待约束环节？是——编码完成后等待测试
  - 其他环节是否在向约束环节堆积工作？是——多个编码完成的任务同时进入测试队列
  - 其他环节是否在做"约束环节做不了的事"？是——编码人员在等待测试时，可以开始做后续的文档工作
  - 建议：
    1. 控制编码完成的节奏，不要一次性让多个任务进入测试队列
    2. 编码人员在等待测试时，优先做"不需要测试结果"的工作
    3. 确保测试队列的"先进先出"，不要因为某个任务"优先级高"就插队
```

服从约束的具体做法：
- 不要一次性向约束环节输入太多任务——这会导致堆积，而不是提升吞吐量
- 非约束环节的"额外产能"是虚幻的——如果编码环节每天能完成 2 个任务，但测试环节每天只能完成 1 个，那么编码环节的"额外产能"只是创造了更多的排队
- 非约束环节在等待时，可以做"不依赖约束环节"的工作——比如写文档、做调研、优化工具链

### 4. 提升约束：如何提升最慢环节的能力

在"利用"和"服从"之后，如果约束环节仍然是瓶颈，考虑"提升"——增加约束环节的能力：

```
提升约束建议：
  - 约束环节：测试
  - 可能的提升方式：
    1. 测试自动化：将重复性测试自动化，减少人工测试时间
    2. 测试并行化：将测试拆分为可并行运行的子任务
    3. 测试范围缩小：优先测试核心功能，非核心功能延后测试
    4. 测试资源增加：如果可能，增加测试资源或测试时间
  - 建议优先级：自动化 > 并行化 > 范围缩小 > 资源增加
```

注意：提升约束不是"让所有环节都更快"，而是"让最慢的环节变快"。提升非约束环节的产能，对整体交付速度没有任何影响。

提升约束的几种方式（按推荐优先级排序）：
1. **消除约束环节的浪费**：约束环节是否在做不必要的步骤？能否简化流程？
2. **自动化约束环节**：约束环节中最耗时的步骤能否自动化？
3. **并行化约束环节**：约束环节能否拆分为多个并行子任务？
4. **缩小输入范围**：让约束环节处理更少、更核心的任务
5. **增加资源**：最后的手段——增加人力、时间、工具投入

### 5. 识别鼓点节奏：最慢环节决定整体节奏

约束环节的节奏决定了整个项目的"鼓点节奏"——所有里程碑的进度应该以这个节奏为参照：

```
鼓点节奏分析：
  - 约束环节：测试，每轮测试需要 3 天
  - 这意味着：整个项目的交付节奏是 3 天一轮
  - 如果某个里程碑的"编码"只用了 1 天，但"测试"排了 3 天队——这个里程碑的实际交付时间是 4 天，而不是 1 天
  - 建议：在 Plan 阶段，里程碑的时间估计应以"约束环节的节奏"为基准，而非"所有环节的平均节奏"
```

鼓点节奏的用途：
- **计划参考**：规划里程碑时，以约束环节的节奏作为时间基准——如果测试需要 3 天，那么每个里程碑至少需要 3 天
- **偏差预警**：如果某个里程碑的实际进度严重偏离鼓点节奏，说明可能遇到了新的约束
- **期望管理**：向用户展示鼓点节奏，让用户理解"为什么项目不能更快"——因为约束环节决定了速度

### 6. 约束可能转移——重新识别

约束不是固定的。当解决了当前的约束后，新的约束会出现：

```
约束转移检测：
  - 上一轮约束：测试（已解决——测试自动化上线）
  - 本轮约束：用户确认（等待用户反馈，平均等待 5 天）
  - 约束转移了！从"测试"变为了"用户确认"
  - 建议：如果用户确认成为新的约束，考虑在 Plan 阶段为"用户确认"设置更短的截止时间
```

Track 报告应该持续跟踪"约束位置"的变化：

```
约束追踪历史：
  第 1 轮 Track：约束在"编码"环节
  第 2 轮 Track：约束在"编码"环节（未转移）
  第 3 轮 Track：约束在"测试"环节（转移了！编码问题已解决，测试成为新瓶颈）
  第 4 轮 Track：约束在"用户确认"环节（再次转移）
```

如果约束长时间不转移，说明：
- 要么是约束环节的问题没有被真正解决（只是在"将就"）
- 要么是约束环节确实是最难的，需要更长时间来提升

## 不适用场景

- **单环节项目**：如果项目只有一个环节（如"写一篇博客"），不存在"哪个环节最慢"的问题——约束诊断不适用。此时应关注"完成时间"而非"瓶颈识别"。
- **探索性项目**：如果用户在做探索性项目（如"研究某个技术方案"），项目本身没有固定的流程环节，约束诊断不适用。探索性项目的不确定性来自"不知道怎么做"，而不是"流程中的某个环节慢"。
- **高度不确定的非流程化工作**：如果项目的工作流程尚未建立（如"第一次做这类项目"），无法识别"哪个环节最慢"——因为每个环节都在变。此时应先建立基本流程，再应用约束诊断。
- **个人日常维护**：修复 bug、更新依赖、调整配置——这些是离散的、独立的任务，没有"流程环节"的概念，约束诊断不适用。
- **用户明确表示"不需要优化速度"**：如果用户说"我不在乎速度，我只想做出好的产品"，约束诊断就不是用户需要的东西。约束诊断的核心假设是"速度是优化目标"，如果用户不认同这个假设，不要强加。
