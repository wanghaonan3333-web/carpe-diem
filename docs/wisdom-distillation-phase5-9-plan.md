## 一、蒸馏方法论

### 1.1 四种来源类型及蒸馏方法

| 来源类型 | 定义 | 蒸馏方法 | 验证方式 |
|:--------|:----|:--------|:--------|
| **书籍** | 有完整方法论框架的出版物 | 提取可操作的步骤框架，而非整个理论体系；只取对 Carpe Diem 四阶段有直接作用的部分 | 书中有明确的方法论和案例支撑，可验证其逻辑链 |
| **工程案例** | 实际运行的项目、平台、组织 | 分析其具体机制和规则，而非"他们为什么成功"的故事；关注"他们怎么做"而非"他们做对了什么" | 机制是公开可查的（如 Stripe 的 API 文档、Google 的 CR 标准），可验证 |
| **思想领袖** | 有长期实践和独特方法论的个人 | 提取其反复强调的可操作原则，而非个人轶事；关注"他们观察到什么规律"而非"他们说过什么" | 规律应是跨场景可验证的，而非依赖个人权威背书 |
| **反模式** | 被反复验证的失败模式 | 从多个来源归纳共同模式，而非单一案例；关注"什么情况下会掉坑"而非"谁掉过这个坑" | 模式应在多个项目中可重复观察到 |

### 1.2 蒸馏颗粒度

每个来源只被提取 **1-2 条** 可蒸馏规则。我们不做"把整本书变成一张卡"的事，也不做"把一个人的所有思想蒸馏成一张卡"的事。

| 来源 | 提取规则数 | 产出 |
|:----|:---------:|:----|
| The Lean Startup | 1 条（实验设计循环） | 1 张卡 |
| Hooked | 1 条（习惯四步模型） | 1 张卡 |
| Stripe API 设计 | 1 条（API 设计哲学） | 1 张卡 |
| Jeff Bezos | 1 条（Type 1 vs Type 2 决策） | 1 张卡（分析瘫痪反模式） |

### 1.3 三条铁律（已有）

| 规则 | 含义 |
|:----|:----|
| **不露来源** | 全文使用 Carpe Diem 自己的语言，不出现人名、书名、公司名 |
| **不抽象** | 不是"什么是 X"，而是"当你遇到 Y 时，怎么做 Z" |
| **可操作** | 指导步骤可在 3-5 轮对话内执行 |

### 1.4 新增一条原则：可验证而非可引用

**不写**："Jeff Bezos 认为……"（这是引用权威）
**不写**："根据 Amazon 的 PR/FAQ 流程……"（这是引用来源）
**写**："当团队讨论一个重大决策时，可以试试这个框架：先写一页纸描述你假设用户需要什么，然后列出三个可能的方案，最后说明你选择某个方案的理由。"（这是可验证的方法——读者可以实际操作并验证它是否有效）

验证标准：这个方法本身有内在逻辑，读者试用后可以自己判断"有用"或"没用"，不需要知道 Jeff Bezos 是谁。

## 二、Phase 5 — Validate 补强（5 张卡）

### 2.1 定价验证 — 测试用户是否愿意付钱

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Ash Maurya 的《Running Lean》 |
| **来源类型** | 书籍 |
| **为什么选这个来源** | Running Lean 是唯一一本把"定价验证"作为验证阶段核心步骤来系统化论述的书。它提出了"定价不是最后决定的事，而是验证阶段就要做的事"这一可操作原则。 |
| **具体蒸馏什么** | 从 Running Lean 中提取"定价验证三步法"：1) 先定一个价格 2) 用预购测试付费意愿 3) 分档测试。同时参考 Buffer 公开的定价实验数据（工程案例）。 |
| **验证方式** | Buffer 公开分享了他们的定价实验过程和数据，这是可验证的工程案例。Running Lean 的方法论被多家创业公司实践过。 |
| **不蒸馏什么** | 不蒸馏 Running Lean 的完整 Lean Canvas 体系，只取定价验证部分。不蒸馏"定价心理学"或"定价策略"（太宽泛）。 |

### 2.2 竞品/替代品分析 — 系统化分析竞争格局

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Steve Blank 的《四步创业法》(Customer Development) + Kim & Mauborgne 的《蓝海战略》 |
| **来源类型** | 书籍 × 2 |
| **为什么选这个来源** | 大多数人对竞品分析的理解停留在"列几个竞品名字"，Steve Blank 引入了"替代方案分析"（用户当前用什么解决这个问题，哪怕那个方案是 Excel 或纸笔），这是更实用的视角。蓝海战略提供了"消除-减少-提升-创造"框架。 |
| **具体蒸馏什么** | 将两个来源融合为一条可操作的竞品分析路径：1) 列出直接竞品、间接竞品、替代方案（来自 Blank） 2) 评估每个方案的优缺点 3) 找到差异化切入点（来自蓝海战略的四步框架）。 |
| **验证方式** | 这个方法可以在任何项目中操作，结果可验证——做完分析后应该能回答"为什么用户会选我而不是替代方案"。 |
| **不蒸馏什么** | 不蒸馏蓝海战略的完整战略画布工具（太复杂），不蒸馏"市场细分"（太宽泛）。 |

### 2.3 实验设计 — 最小实验验证假设

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Eric Ries 的《精益创业》(The Lean Startup) + 补充 Ash Maurya |
| **来源类型** | 书籍 |
| **为什么选这个来源** | BML（Build-Measure-Learn）循环是精益创业最核心的可操作框架，它把"验证"从模糊概念变成了具体循环。但原始 BML 容易让人先 Build 再 Learn，我们需要指导用户如何从"最少的实验"开始。 |
| **具体蒸馏什么** | 提取 BML 循环的核心机制，但强调"先定义假设→选最小实验→设定成功标准→执行→决策"的顺序。结合 Maurya 的"实验类型矩阵"（访谈/落地页/原型/预购/concierge）。 |
| **验证方式** | 实验设计有明确的结果标准——如果实验做完还不能判断假设是否成立，说明实验设计有问题。这个标准本身可验证。 |
| **不蒸馏什么** | 不蒸馏精益创业的完整体系（MVP、转型、核算等），只取实验设计循环。不蒸馏"创新核算"（太复杂）。 |

### 2.4 Go/No-Go 决策 — 验证后如何判断方向

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Eric Ries 的"转型或坚持"决策 + Steve Blank 的"走出大楼"验证循环 + David Bland 的 Test Card |
| **来源类型** | 书籍 + 方法论 |
| **为什么选这个来源** | 验证阶段最难的不是做实验，而是实验结束后如何做决定。三个来源共同指向一个问题：如何判断"证据够不够"。Ries 的"转型或坚持"会议是个具体机制，Bland 的 Test Card 提供了明确的结构。 |
| **具体蒸馏什么** | 提取"做决策前必须回答的问题清单"：1) 验证开始前设定的成功标准达到了吗？2) 信号够强还是模糊？3) 如果模糊，下一个实验是什么？4) 沉没成本是否在影响判断？ |
| **验证方式** | 决策质量可以在后续执行中验证——如果做了 Go 决策但项目始终无法推进，说明决策依据不足。 |
| **不蒸馏什么** | 不蒸馏 Lean Startup 的"三种转型类型"（太具体），不蒸馏"创新核算"（太复杂）。 |

### 2.5 用户访谈技巧 — 深入访谈方法

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Teresa Torres 的《Continuous Discovery Habits》 |
| **来源类型** | 书籍 |
| **为什么选这个来源** | 我们已经有了 Mom Test（教用户不问什么），但缺少"怎么问"的正面指导。Teresa Torres 提供了具体的访谈框架：机会解法树、结构化访谈、追问技巧。这是 Mom Test 的补充，而非替代。 |
| **具体蒸馏什么** | 提取访谈技巧：1) 问过去的行为而非未来的意愿 2) 用具体场景替代抽象问题 3) 追问"为什么"和"然后呢" 4) 寻找情绪信号 5) 记录原话而非解读。 |
| **验证方式** | 访谈技巧可以在实践中验证——好的访谈应该能发现用户之前没说的需求，而不是验证你已有的假设。 |
| **不蒸馏什么** | 不蒸馏机会解法树的完整框架（需要整本书才能理解），只取访谈技巧部分。 |

## 三、Phase 6 — 反模式系列（4 张卡）

### 3.1 过早优化

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Donald Knuth 的论文（"过早优化是万恶之源"） + YC 创始人经验 + 多个工程案例 |
| **来源类型** | 思想领袖 + 工程案例（多来源归纳） |
| **为什么选这个来源** | "过早优化"是最常见的工程反模式，Knuth 的原话被广泛引用但很少有人把它转化为可操作原则。我们做的事情是：把这条原则变成"什么时候该优化、什么时候不该优化"的决策框架。 |
| **具体蒸馏什么** | 不蒸馏 Knuth 的原话，而是提取"优化决策框架"：1) 这个优化解决的是现在的问题还是未来的问题？2) 最简方案是否足够？3) 80/20 法则。验证方式：等用户告诉你需要优化。 |
| **验证方式** | 这个原则在几乎所有项目中可验证——过早优化的项目往往在方向错误时浪费了大量时间；不优化而先发布的项目有更多机会调整方向。 |
| **不蒸馏什么** | 不蒸馏"性能优化技术"，不蒸馏 Knuth 的算法理论。 |

### 3.2 功能蔓延

| 维度 | 内容 |
|:----|:------|
| **核心来源** | DHH/Jason Fried 的《Rework》《Getting Real》《It Doesn't Have to Be Crazy at Work》 + Basecamp 产品实践 |
| **来源类型** | 书籍 + 工程案例 |
| **为什么选这个来源** | 37signals/Basecamp 是功能蔓延的"反面教材"——他们以"说不是产品的一部分"著称。三本书中反复出现的核心原则是"砍功能比加功能重要"。我们已经有了"默认说不"卡，这张卡是反向提醒：不砍功能会怎样。 |
| **具体蒸馏什么** | 提取"功能蔓延预警和应对机制"：1) 每个新功能必须回答"它解决什么核心问题" 2) 加一个功能前先想删一个功能 3) 用"不做清单"管理被拒绝的需求 4) 定期审视使用率，删除低使用率功能。 |
| **验证方式** | 功能蔓延的后果可验证——产品功能越多，维护成本越高，核心价值越模糊。相反，砍功能后产品往往变得更清晰。 |
| **不蒸馏什么** | 不蒸馏 Basecamp 的完整产品哲学，只取功能蔓延的识别和应对。 |

### 3.3 分析瘫痪

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Jeff Bezos 的"Type 1 vs Type 2 决策"框架 + Reid Hoffman 的"如果第一版不让你尴尬，说明你 launch 太晚了" |
| **来源类型** | 思想领袖（多来源归纳） |
| **为什么选这个来源** | 分析瘫痪是个人项目和创业项目中最常见的失败模式之一。两个来源从不同角度给出了解决方案：Bezos 告诉你如何区分决策类型，Hoffman 告诉你快速行动的价值。结合后形成完整的决策框架。 |
| **具体蒸馏什么** | 提取"决策框架"：1) 区分"可逆决策"和"不可逆决策" 2) 可逆决策快速做，不可逆决策谨慎做 3) 用"足够好"替代"最优" 4) 问"最坏情况是什么" 5) 做决定后不回头。 |
| **验证方式** | 决策框架可验证——做了决策后回头看，如果大部分"可逆决策"的结果是可以接受的，说明分类方法有效。 |
| **不蒸馏什么** | 不蒸馏 Bezos 的 Amazon 决策历史，不蒸馏 Hoffman 的创业故事。 |

### 3.4 独角兽思维

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Paul Graham 的 essays（"做用户需要的，不是 VC 想要的"） + Peter Thiel《Zero to One》（补充视角） |
| **来源类型** | 思想领袖（多来源归纳） |
| **为什么选这个来源** | 我们已经有了 Peter Thiel 的"反共识检验"卡（帮用户判断方向是否独特），但缺少"反向提醒"：不是每个项目都需要做成 billion-dollar 公司。Paul Graham 多次强调"先服务一小群人"比"想做大市场"更重要。 |
| **具体蒸馏什么** | 提取"从小做起"的决策框架：1) 谁能成为你的第一个用户 2) 从服务一个人开始 3) 先成为细分市场第一 4) 承认小众市场也可以是好生意。 |
| **验证方式** | 可验证——大部分成功的项目都是从服务一小群人开始的，而不是从"大市场"切入的。 |
| **不蒸馏什么** | 不蒸馏 Thiel 的"垄断理论"（我们已经有了 secret-test 卡），不蒸馏 Paul Graham 的创业故事。 |

## 四、Phase 7 — 团队与协作（5 张卡）

### 4.1 RFC/设计文档 — 书面化决策文化

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Stripe 的 RFC 文化 + Jeff Bezos 的 Amazon 6 页叙事 + 大型开源项目（Kubernetes KEP、React RFC） |
| **来源类型** | 工程案例（多来源归纳） |
| **为什么选这个来源** | 多个高绩效组织（Stripe、Amazon、Kubernetes、React）都有书面化决策的传统。这不是巧合——书面化决策解决的是"口头决策容易遗忘、误解、无法追溯"的问题。我们已经有 ADR 增强卡（ADR + RFC 融合），这张卡补充的是"什么时候需要写 RFC、怎么写、怎么评审"的完整流程。 |
| **具体蒸馏什么** | 提取"RFC 编写-评审-归档"流程：1) 重大决策先写 RFC 再讨论 2) 格式：背景/方案/替代方案/风险/决策 3) 设置评论期 4) 决策后归档 5) 区分"征求意见"和"寻求批准"。 |
| **验证方式** | 可验证——采用 RFC 流程后，团队应该能回答"为什么做这个决策"以及"有没有考虑过其他方案"。 |
| **不蒸馏什么** | 不蒸馏 Stripe 的完整内部流程，不蒸馏 Amazon 的 6 页叙事写作技巧（太具体）。 |

### 4.2 Code Review — 有效的代码审查文化

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Google 的 Code Review 标准（公开发布） + Linux Kernel 的维护者模型 |
| **来源类型** | 工程案例 |
| **为什么选这个来源** | Google 和 Linux Kernel 是世界上最成熟的两个 CR 体系，它们的标准是公开的、经过数十年验证的。Google 的"PR 应小而专注"和 Linux Kernel 的"审查者关注整体设计"是可以直接操作的原则。 |
| **具体蒸馏什么** | 提取 CR 最佳实践：1) PR 小而专注（< 200 行） 2) 先看整体设计再读细节 3) 评论针对代码而非作者 4) 区分"必须改"和"建议改" 5) 建立 CR 检查清单。 |
| **验证方式** | 可验证——好的 CR 应该减少 Bug、提高代码质量、传播知识（而不是拖慢速度）。 |
| **不蒸馏什么** | 不蒸馏 Google 的完整 CR 工具链，不蒸馏 Linux Kernel 的邮件列表协作方式。 |

### 4.3 回顾/复盘 — 团队回顾和持续改进

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Etsy 的 blameless postmortem 文化（公开分享） + Kent Beck 的 XP 回顾实践 |
| **来源类型** | 工程案例 + 方法论 |
| **为什么选这个来源** | Etsy 是最早系统化实践"无指责复盘"的技术公司之一，他们的复盘格式是公开的。Kent Beck 在 XP 中把"回顾"作为核心实践。两者结合形成可操作的复盘流程。 |
| **具体蒸馏什么** | 提取"无指责复盘"流程：1) 设定无指责基调 2) 收集事实而非观点 3) 找到系统性原因而非个人原因 4) 提出可执行的改进措施 5) 跟踪改进措施的落实情况。 |
| **验证方式** | 可验证——好的复盘应该让团队在下次遇到类似问题时能做得更好，而不是找到"责任人"。 |
| **不蒸馏什么** | 不蒸馏 Etsy 的特定事故案例，不蒸馏 XP 的完整实践体系。 |

### 4.4 技术债管理

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Ward Cunningham（技术债概念的提出者，1992 年） + Martin Fowler（技术债分类和管理方法） |
| **来源类型** | 思想领袖 |
| **为什么选这个来源** | 技术债概念来自 Cunningham，但如何管理技术债的框架来自 Fowler。Fowler 区分了"有意为之的债务"和"无意识的糟糕代码"，并提出了"童子军规则"（每次改动让代码比之前好一点）。 |
| **具体蒸馏什么** | 提取技术债管理框架：1) 区分"合理债务"和"糟糕代码" 2) 童子军规则 3) 建立技术债清单 4) 预留还债时间 5) 在技术债影响速度之前处理。 |
| **验证方式** | 可验证——技术债高的项目，添加新功能的速度会越来越慢；定期还债的项目，速度保持稳定。 |
| **不蒸馏什么** | 不蒸馏 Cunningham 的原始比喻，不蒸馏 Fowler 的完整 Refactoring 目录。 |

### 4.5 异步沟通

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Basecamp 的《Remote》和《It Doesn't Have to Be Crazy at Work》 + GitLab Handbook（公开的远程协作手册） |
| **来源类型** | 书籍 + 工程案例 |
| **为什么选这个来源** | Basecamp 和 GitLab 是异步沟通最彻底的实践者。Basecamp 的书提供了"为什么异步沟通重要"的哲学，GitLab 的 Handbook 提供了"怎么做"的具体机制。两者互补。 |
| **具体蒸馏什么** | 提取异步沟通的核心原则：1) 默认用文档替代会议 2) 写清楚才能想清楚 3) 设定回复时间期望 4) 使用决策日志 5) 区分"需要同步讨论"和"可以异步解决"。 |

## 五、Phase 8 — 产品维度（4 张卡）

### 5.1 增长飞轮

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Andrew Chen 的《The Cold Start Problem》 + Brian Balfour 的增长循环框架 |
| **来源类型** | 书籍 + 方法论 |
| **为什么选这个来源** | 增长不是"投广告"或"加功能"，而是找到闭环。Chen 的"冷启动问题"分析了网络效应的启动机制，Balfour 的增长循环框架替代了传统的增长漏斗。两者都指向同一个核心：增长是一个循环，不是一条线。 |
| **具体蒸馏什么** | 提取"增长循环"的核心原则：1) 找到增长循环（不是漏斗） 2) 先手动获取用户再自动化 3) 聚焦一个渠道做到极致 4) 让产品本身具有传播性。 |
| **验证方式** | 可验证——找到增长循环后，每个用户应该能带来>1个新用户。 |
| **不蒸馏什么** | 不蒸馏 Chen 的完整"冷启动"理论（太学术），不蒸馏 Balfour 的"增长循环"分类体系（太复杂）。 |

### 5.2 用户留存

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Nir Eyal 的《Hooked》 |
| **来源类型** | 书籍 |
| **为什么选这个来源** | Hooked 是唯一一本系统化论述"用户习惯"的书籍，它提出了"触发→行动→奖励→投入"四步模型。这张卡与 PMF 调查卡互补——PMF 卡帮你判断"是否达到产品-市场匹配"，留存卡帮你"在达到 PMF 后让用户持续回来"。 |
| **具体蒸馏什么** | 提取"用户习惯形成"的核心原则：1) 定义"激活"——用户第一次体验核心价值的时刻 2) 测量留存曲线 3) 找到留存用户和流失用户的行为差异 4) 建立习惯循环。 |
| **验证方式** | 可验证——留存率是可以用数据衡量的，好的留存策略应该让留存曲线趋于平缓。 |
| **不蒸馏什么** | 不蒸馏 Hooked 的完整模型（整本书的内容），不蒸馏"行为设计"的心理学理论。 |

### 5.3 产品战略

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Marty Cagan 的《Inspired》《Empowered》 + Melissa Perri 的《Escaping the Build Trap》 |
| **来源类型** | 书籍 × 2 |
| **为什么选这个来源** | Cagan 和 Perri 是产品管理领域最被广泛认可的两位作者。Cagan 强调"产品发现 vs 产品交付"的区分，Perri 强调"产品战略 vs 功能列表"的区分。两者共同指向：产品战略是"选择不做什么"，不是"列出要做什么"。 |
| **具体蒸馏什么** | 提取产品战略框架：1) 定义产品愿景 2) 聚焦一个核心用户群体 3) 识别核心价值主张 4) 用"现在→下一步→未来"规划路线图 5) 对每个功能问"它支持我们的战略吗？" |
| **验证方式** | 可验证——有产品战略的团队，应该能回答"为什么这个功能比那个功能更重要"，而不只是"这个功能用户想要"。 |
| **不蒸馏什么** | 不蒸馏 Cagan 的完整产品团队组织模型，不蒸馏 Perri 的"产品经理角色"讨论。 |

### 5.4 持续发现

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Teresa Torres 的《Continuous Discovery Habits》 |
| **来源类型** | 书籍 |
| **为什么选这个来源** | 我们已经有了 Discover 阶段（一次性的方向发现），但缺少"持续发现"——进入开发阶段后如何继续验证假设。Torres 的"机会解法树"和"每周发现活动"就是把发现从"一次性事件"变成"持续节奏"的方法。这张卡与 continuous-check 卡互补——continuous-check 是"验证要持续"，这张卡是"发现要持续"。 |
| **具体蒸馏什么** | 提取持续发现框架：1) 建立持续发现节奏 2) 维护机会解法树 3) 区分"探索"和"交付" 4) 每次发现活动产出可测试的假设 5) 让发现结果驱动路线图。 |
| **验证方式** | 可验证——持续发现做得好的团队，应该能说出"这个月我们发现了什么新机会"以及"我们验证了哪些假设"。 |
| **不蒸馏什么** | 不蒸馏机会解法树的完整绘制方法（需要整本书学习），不蒸馏 Torres 的访谈技巧（已在 2.5 覆盖）。 |

## 六、Phase 9 — 工程维度（4 张卡）

### 6.1 API 设计哲学

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Stripe 的 API 设计哲学（公开文档） + 微软 REST API 指南（公开） |
| **来源类型** | 工程案例 |
| **为什么选这个来源** | Stripe 的 API 被广泛认为是"最好的 API 设计"之一，他们的设计原则是公开的：一致性、直觉性、为调用者设计。微软的 REST API 指南则是业界最完整的 API 设计规范。两者结合形成可操作的 API 设计原则。 |
| **具体蒸馏什么** | 提取核心 API 设计原则：1) 先设计 API 再实现 2) 一致性比完美更重要 3) 让正确用法显而易见 4) 为调用者设计 5) 版本化从第一天开始 6) 文档是 API 的一部分。 |
| **验证方式** | 可验证——好的 API 设计，调用者不需要看文档就能猜对用法。 |
| **不蒸馏什么** | 不蒸馏 Stripe 的特定 API 实现细节，不蒸馏微软的完整 REST 指南（几百页）。 |

### 6.2 可观测性

| 维度 | 内容 |
|:----|:------|
| **核心来源** | Charity Majors（Honeycomb CTO，可观测性概念的推动者） + Honeycomb 的实践 |
| **来源类型** | 思想领袖 + 工程案例 |
| **为什么选这个来源** | Charity Majors 是"可观测性"运动的核心人物，她区分了"监控"（你知道什么问题可能出现）和"可观测性"（你不知道什么问题可能出现）。Honeycomb 是践行这一理念的产品。 |
| **具体蒸馏什么** | 提取可观测性建设原则：1) 建立三支柱：日志/指标/追踪 2) 先定义"健康"再定义"告警" 3) 关注"信号"而非"噪音" 4) 建立仪表盘 5) 设置告警阈值但不设置过多告警。 |
| **验证方式** | 可验证——可观测性做得好的系统，在出问题之前就能发现异常信号，而不是等用户报告。 |
| **不蒸馏什么** | 不蒸馏 Charity Majors 的 Twitter 观点，不蒸馏 Honeycomb 的产品功能。 |

### 6.3 数据建模

| 维度 | 内容 |
|:----|:------|
| **核心来源** | PostgreSQL 的设计哲学 + 实际数据建模经验（多项目归纳） |
| **来源类型** | 工程案例 + 经验总结 |
| **为什么选这个来源** | PostgreSQL 是最成功的关系数据库之一，它的设计哲学（如"数据完整性由数据库保障"、"扩展性源于正确性"）是经过数十年验证的。数据建模本身没有单一权威书籍，最佳实践来自多个项目的经验积累。 |
| **具体蒸馏什么** | 提取数据建模的核心原则：1) 从业务概念出发 2) 规范化到够用即可 3) 为查询建模 4) 预留扩展点但不做过度设计 5) 命名一致性 6) 数据完整性由数据库保障。 |
| **验证方式** | 可验证——好的数据模型，业务变化时只需要加字段而非改结构。 |
| **不蒸馏什么** | 不蒸馏 PostgreSQL 的完整功能特性，不蒸馏数据库调优技巧。 |

### 6.4 安全设计

| 维度 | 内容 |
|:----|:------|
| **核心来源** | OWASP 安全设计原则（公开） + 安全开发生命周期（SDL） |
| **来源类型** | 工程案例 |
| **为什么选这个来源** | OWASP 是安全领域最权威的社区组织，其安全设计原则是公开的、经过广泛验证的。SDL（最初由微软推广）提供了"安全不是最后一层，而是从设计开始"的框架。 |
| **具体蒸馏什么** | 提取核心安全设计原则：1) 在设计阶段识别敏感数据和攻击面 2) 默认最小权限原则 3) 输入校验从第一天开始 4) 使用经过验证的库而非自己实现 5) 建立安全响应计划。 |
| **验证方式** | 可验证——安全设计做得好的项目，大部分常见漏洞（如 XSS、SQL 注入）在架构层面就被避免了，不需要靠最后一层"安全扫描"发现。 |

## 八、不蒸馏什么（明确排除）

| 排除项 | 原因 |
|:------|:----|
| 完整的理论体系（如 Lean Startup 整个框架） | 只取 1-2 条可操作规则，不搬整个体系 |
| 个人轶事（如"Bezos 在 Amazon 早期如何……"） | 不蒸馏故事，只蒸馏可重复的方法 |
| 工具推荐（如"用 Postman 测试 API"） | 不绑定具体工具，只蒸馏原则 |
| 无法验证的断言（如"好的产品经理都有 X 特质"） | 只蒸馏"可操作"的指导，不蒸馏"不可证伪"的判断 |
| 过于学术的概念（如"网络效应拓扑分类"） | 只蒸馏用户能用到的部分 |
| 已被已有卡片覆盖的内容 | 每张新卡必须填补现有空白，不重复 |
| 中国法律/监管/合规内容 | 不在本范围，需单独规划 |

## 九、执行策略

### 9.1 卡片创建顺序

每个设计师按"先易后难"顺序创建卡片——先做理解最充分的来源，再做需要更多思考的来源。

### 9.2 每条卡片的创建流程

1. 阅读规划文档中对应卡片的来源描述
2. 识别来源中的 1-2 条可蒸馏规则
3. 用 Carpe Diem 自有语言重写（不出现来源名称）
4. 补充触发条件（4 个场景，让 Agent 知道何时激活）
5. 补充行为指导（6 条可操作步骤）
6. 补充不适用场景（4 个边界条件）
7. 自我检查：三条铁律是否通过？
8. 更新 mentors/README.md

### 9.3 审核标准

```
三条铁律检查：
  [ ] 不露来源 — 全文扫描：零来源名称
  [ ] 不抽象   — 有触发条件 + 行为指导
  [ ] 可操作   — 步骤可在 3-5 轮对话内执行

可验证检查：
  [ ] 指导步骤有内在逻辑，不依赖权威背书
  [ ] 用户操作后可以自己判断"有用"或"没用"
  [ ] 指导不要求用户知道某个特定人物或书籍

格式检查：
  [ ] 有"问题本质"部分
  [ ] 有"触发条件"部分（3-5 个）
  [ ] 有"行为指导"部分（5-6 条）
  [ ] 有"不适用场景"部分（3-5 个）
```
