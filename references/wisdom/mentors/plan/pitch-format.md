# 行为卡：用 Pitch 格式组织规划章节

> 触发条件：Plan 阶段开始组织章节结构时，用户提供的章节内容分散、缺乏统一格式

## 问题本质

大多数人在写计划时，每个章节的格式都不一样——"核心挑战"写了背景故事，"里程碑"列了功能清单，"架构"画了技术图，"测试策略"又是另一套格式。每个章节看起来都有自己的逻辑，但合在一起时，你无法快速回答：**这个计划到底解决了什么问题？为什么选择这个方案？风险在哪里？**

问题的根源是：**你把"写计划"当成了"填模板"，而不是"回答五个关键问题"**。这五个问题是：我们为什么要做（问题）、我们愿意投入多少（时间预算）、我们打算怎么做（方案）、什么可能出问题（风险陷阱）、以及我们明确不做什么（非目标）。如果每个章节不能统一回答这五个问题中的某一个，计划就失去了内在的一致性。

## 触发条件

用户正在执行以下任一操作时触发：
- Plan 阶段开始组织章节结构时，各章节的格式和详略程度不统一（如"核心挑战"写了三页，"架构"只有两行）
- 用户说"我们先列一下计划需要包含哪些章节"，但每个章节的用途和内容要求不清晰
- 评审计划时，发现"问题"和"方案"之间缺乏逻辑关联——问题说的是 A，方案做的是 B
- 用户完成计划初稿后，说不清"最大的风险是什么"和"哪些事情明确不做"

## 行为指导

### 1. 把每个规划章节统一为"Pitch 五要素"格式

无论章节叫什么名字（核心挑战、里程碑、架构、测试策略），每个章节的内容都应该回答以下五个问题中的某一个。整个计划由这五个要素构成：

| 要素 | 章节对应 | 核心问题 |
|------|---------|---------|
| **问题** | 核心挑战、背景 | 我们为什么现在做这个？什么场景、什么用户、什么痛点？ |
| **时间预算** | 里程碑、时间规划 | 我们愿意投入多少时间？不是"需要多少时间"，而是"值得花多少时间" |
| **方案** | 架构、功能设计、技术方案 | 我们打算怎么做？核心思路是什么，不是细节实现 |
| **风险陷阱** | 风险、依赖、边界情况 | 什么地方可能出问题？什么环节容易超时？ |
| **非目标** | 范围边界、不做什么 | 我们明确不做什么？什么功能、场景、技术方案排除在外？ |

判断标准：如果你能用一个表格把整个计划的五个要素列清楚，说明计划结构是清晰的。如果你发现某个要素在计划中缺失（如没有"风险陷阱"章节），或者某个章节不属于任何一个要素，说明计划结构需要调整。

### 2. 写"问题"时，用一个具体场景开头

"问题"部分最常见的错误是写得太抽象——"用户需要更好的体验"、"市场在增长"、"技术栈需要升级"。这些抽象描述无法驱动后续决策。

好的"问题"部分应该这样写：
- **用具体场景开头**：不说"用户管理任务效率低"，而是说"用户每天花 15 分钟在三个不同的工具之间切换，只是为了找到今天要做的五件事"
- **说明"为什么现在做"**：不说"这个功能很重要"，而是说"我们收到 20 个用户反馈，其中 15 个提到同一个问题——而且竞争对手已经开始解决它了"
- **说明"如果不做会怎样"**：不说"错过了机会"，而是说"如果三个月内不解决这个问题，用户流失率预计会从 5% 上升到 15%"

判断标准：如果你把"问题"部分单独拿出来给一个不了解项目的人看，他是否能理解"为什么这件事值得做"？如果不能，说明问题定义得不够具体。

### 3. 写"方案"时，只描述核心思路，不写实现细节

"方案"部分最常见的错误是写得太细——把具体的 API 接口、数据库表结构、UI 组件都写进去。方案应该是"思路"，不是"实现手册"。

好的"方案"部分应该：
- **描述方案的核心逻辑**：不说"用 Redis 做缓存，API 返回 JSON，前端渲染列表"，而是说"用户只需一次点击就能完成操作，而不是三次"
- **用示例或草图说明**：附上一个具体的用户操作流程示例，而不是抽象的功能描述
- **说明"为什么选这个方案"**：不说"用微服务架构"，而是说"选择微服务架构是因为我们预期三个独立模块会由不同团队维护，而单体架构会在半年后成为瓶颈"

判断标准：如果方案中的某个细节在实现时可能会改变（比如具体的技术选型），那它就不应该出现在方案中——方案应该只包含"不会轻易改变"的核心思路。

### 4. 写"风险陷阱"时，区分三类风险

"风险陷阱"部分不仅要列出风险，还要对每个风险给出应对策略。把风险分为三类：

- **技术风险**：技术方案是否可行？有没有未知的技术难点？
  - 应对策略：做技术调研（Spike），设定调研截止时间
- **依赖风险**：是否依赖外部因素（第三方 API、其他团队、用户提供数据）？
  - 应对策略：明确依赖的触发条件，设置"如果依赖未满足则走备选方案"
- **范围风险**：某个功能看起来简单，但实现起来可能复杂？
  - 应对策略：提前划定"如果这个功能超时，就拆到下一版"

判断标准：如果"风险陷阱"部分写完之后，你仍然觉得"应该不会出问题吧"，说明风险识别不充分——一个好的风险列表应该让你觉得"这些地方确实有可能出问题，但我们已经想好了对策"。

### 5. 写"非目标"时，用"如果有人说……"来检验

"非目标"部分的作用不是"列出所有不做的功能"，而是"防止计划在执行过程中被悄悄扩大"。用这个检验方法：

> **如果有人说"这个功能应该加进去"，你的"非目标"清单是否足够明确，让你能快速回答"这个功能在我们的非目标清单里，不在本期范围内"？**

好的"非目标"示例：
- 本期不做的场景：不支持团队协作功能，不支持离线模式
- 本期不做的用户群体：不面向企业客户，只面向个人用户
- 本期不做的技术方案：不使用微服务架构，不引入消息队列

判断标准：如果你在"非目标"中写了"不做 XX"，但实际执行中 "XX" 的需求一定会出现（比如"不做搜索功能"——但用户一定会问搜索），那说明"非目标"的定义过于宽泛，需要更精确地界定边界。

### 6. 用一个"五要素清单"做计划完成检查

在计划完成初稿后，用以下清单检查完整性：

- [ ] **问题**：是否用一个具体场景开头，说明"为什么现在做"和"如果不做会怎样"？
- [ ] **时间预算**：是否明确每个里程碑的时间预算，而不是"先列功能再估算时间"？
- [ ] **方案**：是否只描述了核心思路，没有陷入实现细节？
- [ ] **风险陷阱**：是否列出了三类风险，且每个风险都有应对策略？
- [ ] **非目标**：是否明确列出了"不做什么"，且能用来快速拒绝范围扩大？

如果其中任何一个要素缺失，说明计划还不完整——不要急着进入执行阶段，先把缺失的要素补上。

## 不适用场景

- **用户做的是极短周期的项目**（如 1-2 天的任务）：如果整个项目只需要 1-2 天完成，Pitch 五要素的格式过于繁琐。这种情况下，只需要一个简单的"问题 + 方案"描述就够了。
- **用户已经有一套成熟的计划格式**：如果用户团队已经有自己习惯的计划格式（如 Notion 模板、Google Docs 模板、Confluence 页面），并且团队内部沟通顺畅，不需要强制切换到 Pitch 格式。这套方法的目的是"统一格式、提升沟通效率"，如果现有格式已经做到了这一点，就没必要换。
- **用户处于探索性阶段，尚未确定方向**：如果用户还在做方向探索（Discover 阶段），Pitch 格式过于正式。探索阶段更适合"假设 + 验证"的记录方式，而不是完整的提案格式。等方向确定后再进入 Pitch 格式的规划。
- **用户做的是纯技术研究/实验项目**：如果用户的项目是"研究 WebGPU 性能"或"探索新的算法"，这类项目没有明确的"用户问题"和"时间预算"，Pitch 格式不适用。这类项目更适合"研究目标 + 方法 + 预期产出"的格式。
