# 行为卡：四种量化指标

> 用四个信号替代"感觉"——部署频率、前置时间、变更失败率、恢复时间
> 蒸馏日期：2026-09-01

## 问题本质

大多数进度报告依赖一个模糊的"感觉"来判断项目健康度："感觉进度不错"或"感觉有点慢"。但感觉是骗人的——一个项目可能看起来进展顺利，但实际交付速度在下降；也可能感觉"卡住了"，但其实是正常的探索阶段。

问题的根源是：**你缺少标准化的量化信号**。

你问"项目进展怎么样"，得到的回答是"还不错"或"有点慢"。但"还不错"是什么意思？是和上周比、和计划比、还是和预期比？"有点慢"是慢了多少？是完全停顿了还是只是增长速度放缓？

没有量化指标，你无法区分以下三种状态：

1. **项目真的在按计划推进**——只是你焦虑了
2. **项目确实变慢了**——但需要知道是哪个环节出问题
3. **项目已经完全停滞**——但被"看起来在忙"掩盖了

四个量化指标解决这个问题：**用四个标准化的信号，替代"感觉"**。它们不回答"项目好不好"，而是回答"项目现在的状态是什么"——让你能基于数据判断，而非基于感觉判断。

## 触发条件

在以下任一场景中触发：

- Track 阶段开始采集证据，需要判断项目整体健康度
- 用户说"感觉项目进展不错"（需要用数据验证这个感觉）
- 用户说"项目好像变慢了"（需要确认是否真的变慢了）
- 用户说"不知道项目到底怎么样"（需要量化信号辅助判断）
- Track 报告需要向用户展示"项目健康度"时
- 多个里程碑之间需要横向比较"哪个执行得更顺利"

## 行为指导

### 1. 采集四类量化指标

在 Track 阶段采集证据时，同时采集以下四个量化指标。注意：Carpe Diem 是只读的，所有指标只能通过观察 Git 历史、CI 状态和文件变更来推断，不能修改工作区。

#### 指标一：合并/提交频率

**含义**：项目团队实际将代码合并到主分支的频率。这是吞吐量的前置信号——如果代码不被合并，就不会有交付。

**采集方式**：
- 统计最近 7 天或 14 天内的合并次数（Git 合并提交）
- 如果没有合并提交，统计活跃分支的提交次数
- 记录"最近一次合并"距今的天数

```
合并频率报告：
  最近 7 天合并次数：5 次
  最近 14 天合并次数：9 次
  最近一次合并：2 天前
  趋势：上周 5 次 vs 上上周 4 次 → 稳定
  评估：如果连续 3 天无合并，建议检查是否遇到了阻塞
```

**解读方式**：
- **频繁合并**（每天 1 次以上）：项目在持续交付，代码在流动。这是健康信号。
- **偶尔合并**（每周 2-3 次）：项目在按节奏交付，但可能有集成等待时间。
- **罕见合并**（每周不到 1 次）：项目可能遇到了阻塞、或者代码变更过于庞大、或者团队在等待某个条件。建议进一步检查。
- **连续多日无合并**：这是一个危险信号——即使"在做"，但代码没有被集成，意味着"做的东西"还没有变成"可交付的东西"。

#### 指标二：变更前置时间

**含义**：从"开始做"到"有证据证明完成"的时间。这是流动效率的核心指标——前置时间越短，流动效率越高。

**采集方式**：
- 对每个里程碑，记录"第一个提交"的日期到"有证据证明完成"的日期
- 如果里程碑未完成，记录"第一个提交"到"当前"的时间
- 汇总所有已完成的里程碑，计算平均前置时间

```
前置时间报告：
  里程碑 A 前置时间：3 天（从开始到完成）
  里程碑 B 前置时间：12 天（从开始到完成）
  里程碑 C 前置时间：进行中，已 8 天
  平均前置时间：7.5 天（基于已完成里程碑）

  趋势分析：
    最近 3 个里程碑的前置时间变化：3 天 → 5 天 → 12 天
    趋势：⬆ 前置时间在增长
    建议：如果前置时间持续增长，说明流动效率在下降——
      可能是任务粒度变大了，也可能是外部依赖增加了
```

**解读方式**：
- **趋势比绝对值重要**：前置时间 12 天本身不一定是问题，但如果从 3 天增长到 12 天，说明流动效率在下降
- **前置时间持续增长**：通常意味着——在制品过多、任务粒度变大、外部依赖增加、或阻塞未被及时处理
- **前置时间稳定**：说明系统在健康运转，每个里程碑的交付节奏是可预测的
- **前置时间缩短**：说明系统在改善——可能是任务拆分更细了，也可能是阻塞被解决了

#### 指标三：变更失败率

**含义**：已完成里程碑中，出现回归问题或质量问题的比例。这是稳定性指标——如果吞吐量很高但失败率也很高，说明"做得多但做得不稳"。

**采集方式**：
- 检查已完成里程碑的后续状态：是否有 CI 失败、是否有回退提交、是否有未修复的 Issue
- 统计"完成后出现问题的里程碑"占总完成里程碑的比例
- 注意：对于只读 Track，只能通过 CI 状态和 Git 历史推断，不能运行测试

```
变更失败率报告：
  已完成里程碑总数：6 个
  其中出现问题的：2 个
    - 里程碑 B：完成后第 3 天出现 CI 失败，已修复
    - 里程碑 E：完成后第 7 天发现回归问题，未修复
  变更失败率：33%（2/6）

  评估：失败率偏高（超过 25%），建议：
    1. 检查里程碑完成时的验收标准是否足够严格
    2. 考虑在完成前增加自动化检查
    3. 关注里程碑 E 的未修复回归问题
```

**解读方式**：
- **低失败率**（低于 15%）：项目交付质量稳定，里程碑完成后的回溯问题少
- **中等失败率**（15%-25%）：有一定质量风险，建议检查验收标准是否充分
- **高失败率**（超过 25%）：交付质量存在问题——"做完了"但"没做好"。建议在 Plan 阶段增加质量保障措施
- 如果失败率持续上升，即使合并频率在增加，也说明项目在"以牺牲质量为代价加快速度"

#### 指标四：恢复时间

**含义**：从发现偏差到纠正偏差的时间。这是响应能力的指标——问题不可避免，但恢复速度决定了影响范围。

**采集方式**：
- 当 Track 发现偏差后，记录"偏差发现时间"到"偏差纠正时间"
- 偏差的发现时间：Track 报告的时间戳
- 偏差的纠正时间：下一次 Track 时检查该偏差是否已被解决
- 如果是 CI 失败，记录"CI 失败时间"到"CI 通过时间"

```
恢复时间报告：
  偏差 1：CI 失败（发现于 2026-08-28，修复于 2026-08-29）→ 恢复时间 1 天
  偏差 2：里程碑 B 未按计划完成（发现于 2026-08-25，纠正于 2026-08-30）→ 恢复时间 5 天
  偏差 3：范围偏移（发现于 2026-08-20，未纠正）→ 恢复时间：进行中，已 11 天

  平均恢复时间：3 天（基于已纠正的偏差）

  评估：偏差 3 的恢复时间已超过 11 天，说明范围偏移问题未被有效处理
  建议：如果恢复时间持续超过 7 天，建议用户重新评估该偏差是否值得纠正
```

**解读方式**：
- **快速恢复**（1-2 天）：项目对偏差的响应灵敏，问题不会长期堆积
- **中等恢复**（3-7 天）：偏差有一定延迟，但仍在可控范围内
- **慢速恢复**（超过 7 天）：偏差可能已被忽视或遗忘——长期未纠正的偏差往往意味着"它已经不重要了"，或者"它已经变成了一个新常态"
- 如果某个偏差的恢复时间持续增长，检查它是否真的被当作"偏差"处理——有时偏差会悄悄变成"新的计划"

### 2. 关注"计划 vs 实际"的偏差模式，而非绝对速度

四个指标的价值不在于"快还是慢"，而在于"是否与计划一致"：

```
偏差模式分析：
  计划中的里程碑交付节奏：每周 2 个
  实际合并频率：最近两周平均每周 1.5 次合并
  偏差：实际交付节奏比计划慢 25%

  计划中的前置时间：每个里程碑 5 天
  实际平均前置时间：7.5 天
  偏差：实际前置时间比计划多 50%

  关键判断：项目在按计划推进，但速度比预期慢
  建议：检查计划中的估计是否合理，还是实际执行中遇到了未预料的阻塞
```

**关键原则**：可预测性 > 速度。

- 一个"稳定地每周交付 1 个里程碑"的项目，比一个"有时每周交付 3 个、有时 3 周交付 0 个"的项目更健康
- 可预测的交付节奏意味着：你可以可靠地规划下一步、设定合理的期望、避免"突然发现项目延期了"
- 当四个指标的数据积累到 2 轮以上，就可以开始做"趋势分析"——不是看"快不快"，而是看"方向对不对"

### 3. 建立证据等级：自动化证据 > 客观证据 > 声称完成

四个指标的可靠性取决于证据来源。按优先级排列：

| 证据等级 | 说明 | 示例 |
|---------|------|------|
| **自动化证据** | 由 CI/CD 系统自动生成，无需人工判断 | CI 通过、测试覆盖率报告、自动化部署日志 |
| **客观证据** | 可验证的文件存在性、Git 提交历史 | 合并提交、文件变更记录、Issue 关闭 |
| **声称完成** | 自我报告的状态，不可独立验证 | 用户说"做完了"、状态标记为"完成" |

在采集四个指标时：
- 优先使用自动化证据——"CI 通过了"比"测试文件存在了"更可靠
- 如果只有"声称完成"的数据，标记为"低可信度"，并在报告中注明
- 如果证据等级发生变化（如"原本只有声称完成，后来有了自动化证据"），在报告中记录这个变化——这本身就是一种进度信号

```
证据等级报告：
  合并频率：客观证据（Git 合并记录）✅
  前置时间：客观证据（Git 提交时间戳）✅
  变更失败率：自动化证据（CI 通过/失败状态）✅
  恢复时间：混合证据（CI 状态 + 主观判断）⚠️ 部分依赖推测

  整体可信度：高（三个指标有客观/自动化证据支撑）
  建议：若恢复时间能通过 CI 日志自动检测，可信度可进一步提升
```

### 4. 生成指标趋势报告，而非单次快照

四个指标的单次数据点意义有限，但趋势线有诊断价值：

```
四次 Track 报告的指标趋势：

           第 1 次    第 2 次    第 3 次    第 4 次
合并频率    5 次/周    6 次/周    4 次/周    3 次/周    ⬇ 下降
前置时间    4 天       5 天       7 天       9 天       ⬆ 上升
失败率      10%        15%        20%        25%        ⬆ 上升
恢复时间    2 天       2 天       3 天       5 天       ⬆ 上升

综合诊断：
  四项指标同时变差，说明项目整体健康度在下降
  可能的原因：在制品过多、外部依赖增加、或者项目范围在扩大
  建议：暂停新任务的启动，先完成当前任务，再评估整体状况
```

**趋势分析的核心原则**：
- 一个指标变差 + 一个指标变好 = 可能是权衡（如"加快了速度但牺牲了质量"）
- 多项指标同时变差 = 系统性问题，需要全面检查
- 多项指标同时变好 = 系统在改善，保持当前方向
- 单个指标突变 = 检查是否有特定事件导致（如"某次大变更导致失败率飙升"）

### 5. 将指标融入 Track 报告，而非单独展示

四个指标不是独立的仪表盘，而是 Track 报告的有机组成部分：

```
## Track 报告摘要

### 健康度概览
- 合并频率：3 次/周（稳定，与计划一致）
- 前置时间：5 天（稳定，与计划一致）
- 变更失败率：15%（可接受，但建议关注）
- 恢复时间：3 天（中等，但最近一次偏差恢复较慢）

### 偏差模式
- 计划 vs 实际：项目在按计划节奏推进
- 约束识别：当前约束在"测试"环节（测试队列堆积）
- 在制品：2 个里程碑进行中（正常范围）

### 建议
- 当前项目健康度良好，建议继续推进
- 关注测试队列的堆积，避免测试成为新的约束
- 下一次 Track 重点关注：测试前置时间是否在增长
```

将四个指标融入 Track 报告的好处：
- 用户不需要额外查看"仪表盘"——指标就在报告中
- 指标与偏差分析、约束诊断、WIP 检测形成互补——它们回答不同的问题
- 每次 Track 报告都包含指标数据，随着时间的推移自然形成趋势分析的基础

## 不适用场景

- **一次性交付项目**：如果项目是"做完了就交付，不持续更新"的类型（如"写一本电子书"），合并频率和恢复时间没有意义。此时应关注前置时间和完成质量。
- **库/工具项目**：库项目的"交付"不是部署，而是发布。合并频率可能不反映实际交付节奏，建议用"发布频率"替代"合并频率"。
- **探索性项目**：如果用户明确表示"这是探索性项目，不关心交付速度"，四个指标的健康度分析不适用。探索性项目更关注"学到了什么"而非"做得多快"。
- **单次 Track 报告**：如果只有一次 Track 数据，没有趋势分析的基础。四个指标需要至少 2 次数据点才能做趋势判断。第一次 Track 时，只报告绝对值，不做趋势分析。
- **用户明确表示"不需要量化"**：如果用户说"我不看数据，我相信感觉"，不要强行展示指标。量化指标是为"需要数据辅助判断"的用户准备的，不是强制要求。
- **没有 CI/CD 基础设施的项目**：如果项目没有自动化测试和 CI 流程，变更失败率和恢复时间难以客观采集。此时只报告合并频率和前置时间两个指标，并在报告中注明"其余指标因缺少自动化证据，暂不采集"。
