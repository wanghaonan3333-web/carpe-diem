# 行为卡：架构可视化

> 触发条件：Plan 阶段进入"架构、组件、数据流"章节，开始描述系统架构时

## 问题本质

大多数人在描述架构时，会本能地从"技术细节"开始——"我们用 React 做前端、用 Go 做后端、用 PostgreSQL 存数据"。但问题是：**在没有先画出系统全貌之前，这些细节没有上下文**。

你无法在"系统边界是什么"都不清楚的情况下讨论"用什么框架"。更常见的情况是：架构讨论变成了"技术选型辩论"——每个人都在争论自己熟悉的技术栈，而不是先对齐"系统和服务器的关系是什么、用户和系统的交互方式是什么"。

问题的根源是：**你跳过了"大局"直接进入了"细节"**。架构描述需要从宏观到微观逐层展开，每一层只关注该层的细节，不跨层。先回答"系统是什么、外部依赖有哪些、用户如何交互"，再回答"系统内部由哪些模块组成、模块之间如何通信"，最后才回答"每个模块的具体实现方式"。

## 触发条件

用户正在执行以下任一操作时触发：

- **场景一：Plan 阶段进入"架构"章节时，用户直接开始讨论技术选型**。如果用户说"我们用 React 还是 Vue"、"后端用 Go 还是 Python"，但还没有画出系统边界、外部依赖、用户角色的全貌图，说明讨论跳过了"大局"直接进入了"细节"。

- **场景二：架构描述中缺少"系统上下文"——即系统边界、外部依赖、用户角色**。如果架构描述只包含"内部模块"和"技术栈"，但没有说明"系统依赖哪些外部服务、有哪些用户角色、系统的职责边界是什么"，说明架构图不够完整。

- **场景三：架构图无法版本化或无法审查**。如果架构图是用画图工具手绘的 PNG/JPG，团队成员无法在代码审查中看到架构图的变更历史，也无法在 Pull Request 中 Diff 架构图的变更，说明架构图需要转为文本格式。

## 行为指导

### 1. 从系统上下文图开始，先画全貌再深入细节

在讨论任何技术选型或模块设计之前，先完成"系统上下文图"——它是架构描述的第一层，也是最重要的一层。系统上下文图包含：

- **系统边界**：当前项目/系统作为一个整体，它的边界在哪里？什么属于系统内部，什么属于外部？
- **外部依赖**：系统依赖哪些外部服务、API、数据库、第三方工具？每个依赖的用途是什么？
- **用户角色**：系统有哪些类型的用户？每个用户角色和系统的交互方式是什么？

系统上下文图不需要任何技术细节——它只是一个"方框和箭头"的图，方框代表系统或外部实体，箭头代表交互关系。它的价值在于让所有人在讨论细节之前，先对齐"我们到底在做什么、和谁打交道"。

判断标准：如果系统上下文图看不出"系统是做什么的"，说明图太抽象了——需要补充"系统核心职责"的说明。如果系统上下文图看起来像"两个方框和一个箭头那么简单"，说明要么系统确实很简单，要么你忽略了某些外部依赖或用户角色。

### 2. 第二层：画容器/服务图，描述系统内部的运行单元

在系统上下文图完成后，进入第二层——"容器/服务图"。这一层描述的是系统内部由哪些可独立部署的运行单元组成：

- **进程/服务**：系统包含哪些可独立运行的服务、进程或应用？每个服务的职责是什么？
- **数据存储**：系统使用哪些数据存储？每个存储的用途是什么？
- **通信方式**：服务之间如何通信？（HTTP、消息队列、事件流、共享数据库等）

"容器"在这里不是指 Docker 容器，而是指"一个独立的运行单元"——一个 Web 应用、一个后台服务、一个数据库、一个消息队列等。每个容器都有明确的职责边界和通信协议。

判断标准：所有在系统上下文图中识别出的"外部依赖"和"用户角色"，在容器图中是否都有对应的交互路径？如果某个外部依赖没有对应的容器来处理它的交互，说明容器图不完整。

### 3. 第三层：画组件图，描述每个容器内部的模块结构

在容器图完成后，进入第三层——"组件图"。这一层描述的是每个容器内部由哪些模块/组件组成：

- **模块划分**：每个容器内部有哪些逻辑模块？模块的职责是什么？
- **接口定义**：模块之间如何交互？每个模块对外提供什么接口？
- **依赖关系**：模块之间的依赖关系是什么？是否存在循环依赖？

注意：组件图只关注"逻辑组件"，不关注"代码实现细节"——你不需要在这一层讨论"是用函数还是类、是用什么设计模式"。组件图回答的是"这个容器内部由哪些逻辑单元组成"，而不是"这些逻辑单元具体怎么实现"。

判断标准：如果容器内部只有一个组件，说明要么这个容器确实太简单了，要么你跳过了组件划分直接进入了代码层。对于大多数容器，至少应该有"核心逻辑"和"接口/适配器"两个组件的划分。

### 4. 第四层保留给代码层，由实现阶段处理

第四层——"代码层"——描述的是每个组件的具体实现细节（类、接口、函数、数据结构等）。但在 Plan 阶段，**建议跳过这一层**，把代码层留给实现阶段（开发 Agent 在编码时自行处理）。

原因：代码层变化太快，在 Plan 阶段过度细化代码结构会导致"计划永远跟不上变化"。Plan 阶段只需要关注前三层（上下文、容器、组件），确保架构的大局和模块划分是清晰的。代码层在实现阶段根据实际需求动态调整。

例外情况：如果项目涉及复杂的算法、数据结构或协议设计，可以在 Plan 阶段用伪代码或流程图补充说明，但不需要完整的代码层图。

### 5. 使用文本格式生成架构图，确保可版本化、可 Diff 审查

所有架构图应使用文本格式生成（如 PlantUML、Mermaid），而不是用画图工具手绘的图片格式。理由：

- **可版本化**：文本格式的架构图可以像代码一样提交到 Git 仓库，每次修改都有清晰的变更记录
- **可 Diff 审查**：在 Pull Request 中，评审者可以看到架构图的"差异"——哪些模块被添加、哪些被删除、哪些关系发生了变化
- **可自动生成**：可以从代码自动生成部分架构图，保证架构文档与实际代码一致
- **可协作**：团队成员可以直接修改文本，不需要特定的画图工具

建议的实践：
- 在项目的 `docs/` 目录下创建 `architecture/` 子目录，存放所有架构图源文件
- 每个架构图文件以 `-context`、`-container`、`-component` 后缀命名，明确层级
- 在架构图文件中添加注释，说明每个图层的"关注点"和"不关注什么"

## 不适用场景

- **极小型项目（单人、单模块、无外部依赖）**：如果用户的项目是一个"单文件脚本"或"单人开发的简单工具"，没有外部依赖、没有多服务划分、没有复杂的用户角色，那么四层架构描述过于冗余——一句"这是一个单文件命令行工具，读取 JSON 文件，输出 CSV"就够了。建议根据项目复杂度跳过 Container 或 Component 层，只保留 Context 层。

- **纯设计讨论阶段（尚未确定系统边界）**：如果用户还在"要不要做这个项目"的可行性讨论阶段，系统边界本身还不确定，此时画架构图为时过早。先完成"项目定位"和"核心挑战诊断"，再进入架构描述。

- **用户不需要架构文档，只需要"能跑就行"**：如果用户明确说"我不需要架构文档，先做出来再说"，并且团队很小（1-2 人）、项目生命周期短，那么完整的架构可视化可能过度工程化。但即使如此，仍然建议至少画一张"系统上下文图"——它不需要花太多时间，但能避免"做到一半发现依赖了某个不存在的 API"。

- **已有清晰、维护良好的架构图**：如果用户已经有一套清晰的架构图（无论是否使用文本格式），并且团队在持续维护它，那么不需要再重新画一套。此卡适用于"架构描述缺失"或"架构描述混乱"的场景，不适用于"已有良好架构文档"的场景。
