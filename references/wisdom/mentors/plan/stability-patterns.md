# 行为卡：架构稳定性设计模式

> 触发条件：Plan 阶段进入"架构、组件、数据流"章节，设计系统架构时，特别是涉及外部依赖和分布式场景

## 问题本质

大多数人在设计架构时，只考虑"正常情况"——用户正常操作、服务正常响应、网络正常连接。但问题是：**在软件系统中，一切可能出错的事最终都会出错**。数据库变慢、第三方 API 超时、网络抖动、某个服务崩溃——这些不是"意外"，而是"常态"。

如果你只在"一切正常"的假设下设计架构，那么当任何一个依赖出问题时，你的系统就会：等待它直到超时（耗尽线程池）、把错误传递给下游（引发级联故障）、或者在最坏的情况下——整个系统崩溃。

问题的根源是：**你把"正常运行"当成了"默认状态"，但软件系统的默认状态其实是"部分故障"**。一个好的架构不是"不出故障"的架构——因为没有系统能做到——而是"在故障发生时，能优雅地降级、快速恢复、不把故障扩散到其他部分"的架构。

## 触发条件

用户正在执行以下任一操作时触发：
- Plan 阶段进入"架构"章节，系统涉及多个服务、外部 API 调用或分布式组件
- 架构描述中包含了"外部依赖"（第三方 API、数据库、消息队列、其他服务），但没有讨论"如果这些依赖挂了怎么办"
- 用户说"这个外部服务应该很稳定，不太可能出问题"——这是最危险的信号，说明没有考虑故障场景
- 架构图中服务之间的调用是"直连"的，没有考虑超时、降级、隔离等保护机制

## 行为指导

### 1. 识别系统中的"脆弱集成点"——所有外部调用都是潜在故障点

在架构审查时，标记所有"脆弱集成点"——即系统与外部依赖的交互点。每个脆弱集成点都需要考虑以下问题：

- **超时**：如果这个依赖不响应，系统最多等多久？无限等待是最危险的——它会耗尽线程池、阻塞请求队列，最终拖垮整个系统。
- **降级**：如果这个依赖挂了，系统能否提供"降级方案"？比如：缓存数据、返回默认值、提示用户稍后再试，而不是直接报错。
- **隔离**：如果这个依赖挂了，故障会不会扩散到其他部分？比如：一个服务的慢查询不应该阻塞其他服务的请求。

标记方法：在架构图上，用红色标注所有"脆弱集成点"，并在每个集成点旁边标注"如果它挂了，我们怎么办"。

### 2. 用"断路器"保护对依赖的调用——快速失败比无限等待更好

为了防止依赖故障引发的级联效应，对每个脆弱集成点增加"断路器"机制：

- **正常状态**：请求正常发送到依赖，断路器关闭
- **故障状态**：当连续 N 个请求超时或失败时，断路器"打开"——不再发送请求到依赖，而是立即返回降级响应
- **恢复状态**：经过一段时间后，断路器"半开"——允许少量请求通过测试依赖是否恢复
- **恢复成功**：依赖恢复正常，断路器关闭
- **恢复失败**：断路器重新打开，继续等待

操作建议：
- 断路器阈值不要设得太高——3-5 次连续失败就触发，而不是 50 次。触发太晚等于没有保护。
- 断路器的恢复时间不要设得太短——至少 30 秒，让依赖有足够时间恢复。
- 在每个脆弱集成点，同时配置"超时"和"断路器"——超时防止单个请求无限等待，断路器防止大量请求涌入已经出问题的依赖。

### 3. 用"舱壁隔离"防止故障扩散——一个模块出问题不能拖垮整个系统

"舱壁"的核心思想是：**把系统分隔成独立的隔离区域，一个区域的故障不会扩散到其他区域**。具体做法：

- **线程池隔离**：不同服务的调用使用独立的线程池。A 服务的线程池耗尽，不会影响 B 服务的调用。
- **连接池隔离**：不同数据库使用独立的连接池。数据库 A 的连接耗尽，不会影响数据库 B 的查询。
- **进程隔离**：核心功能和非核心功能运行在不同的进程/容器中。非核心功能崩溃，核心功能继续运行。
- **用户隔离**：高价值用户和普通用户使用不同的资源池。普通用户的流量高峰不会影响高价值用户的服务质量。

判断标准：如果系统中的一个模块出问题，是否会导致整个系统不可用？如果是，说明隔离不足——需要增加舱壁。

### 4. 为每个外部依赖设置"超时 + 重试 + 幂等"三件套

每个外部调用都应该配置三件套：

- **超时**：设置合理的超时时间。不是"等多久都可以"，而是"最多等 3 秒，超过就降级"。超时时间应该比"正常响应时间"的 99 分位值略高，但不能无限长。
- **重试**：在超时或失败后，是否重试？重试的次数和间隔要合理。不要"失败就立即重试"——这通常会让问题更严重。应该用"指数退避"（第一次等待 1 秒，第二次 2 秒，第三次 4 秒……）。
- **幂等**：重试是否安全？如果重试会重复执行操作（如重复扣款、重复发送通知），那重试就是危险的。需要确保操作是"幂等"的——重复执行和一次执行的结果相同。

判断标准：如果某个外部调用的重试不是幂等的，那你需要先解决幂等性问题，再配置重试策略。否则，宁可"不重试"也不要"重试但不安全"。

### 5. 设计"优雅降级"路径——降级不是"什么都不做"，而是"做得少但做得对"

当依赖出问题时，降级方案不是"系统报错让用户重试"，而是"系统在有限的能力范围内继续工作"。

具体降级策略：
- **缓存降级**：如果依赖不可用，使用缓存数据（即使不是最新的）
- **功能降级**：关闭非核心功能，保留核心功能正常运行
- **默认值降级**：如果依赖不可用，返回安全的默认值而不是报错
- **异步降级**：如果同步调用失败，把请求放入队列，等依赖恢复后再处理

在架构设计阶段，对每个脆弱集成点明确"降级方案"——而不是"如果它挂了，我们再想怎么办"。降级方案应该在设计时就确定，而不是在故障发生时临时决定。

### 6. 用"健康检查 + 限流"构建第一道防线

在系统入口处设置健康检查和限流机制，防止异常流量进入系统内部：

- **健康检查**：系统对外暴露健康检查端点（如 `/health`），让负载均衡器、监控系统知道系统是否正常工作。健康检查应该检查系统的关键依赖（数据库、消息队列、核心服务），而不是"返回 200"。
- **限流**：在系统入口处限制请求速率。当请求量超过阈值时，直接拒绝（返回 429 Too Many Requests），而不是让请求进入系统内部被慢慢处理。限流应该基于"用户"或"IP"做隔离，防止一个用户的异常流量影响其他用户。

在架构图上，标注"健康检查端点"和"限流位置"——它们应该在系统的最外层，而不是在系统内部。

## 不适用场景

- **用户做的是单进程、无外部依赖的本地工具**：如果系统不依赖任何外部服务（没有 API 调用、没有数据库、没有消息队列），稳定性设计模式几乎不需要。单进程工具只需要关注"不要崩溃"和"处理异常"。
- **用户处于 Discover 或 Validate 阶段，尚未进入架构设计**：稳定性设计是 Plan 阶段架构章节的内容，在 Discover 和 Validate 阶段不需要考虑。如果用户还在探索方向，应该先完成方向验证再考虑架构。
- **用户做的是原型验证或一次性脚本**：如果项目目的是"快速验证想法是否可行"，稳定性设计是过度设计。原型结束后会被丢弃，不需要考虑断路器、舱壁隔离等机制。等原型验证通过后，进入正式开发时再启用稳定性设计。
- **用户的项目是极简的单服务架构**：如果系统只有一个服务、一个数据库、没有外部依赖（除了基础设施），只需要配置基本的超时和重试即可，不需要完整的稳定性模式。舱壁隔离和断路器在"多依赖、多服务"的场景下才有真正的价值。
