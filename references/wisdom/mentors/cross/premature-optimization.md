# 行为卡：过早优化

> 触发条件：用户在不确定方向时，把时间花在性能、扩展性、通用性上，而不是验证核心价值

## 问题本质

在还不确定方向是否正确时，把时间花在性能、扩展性、通用性上，而不是验证核心价值。过早优化的陷阱在于：每个"优化"决定单独看都合理——"架构设计好一点，以后扩展容易"、"先考虑性能，后面不用改"——但这些"合理"的决定累积起来，导致你在应该验证方向的时候，把大量时间花在了可能永远不会用到的优化上。

问题的根源是：**你把"未来可能发生的问题"和"今天必须解决的问题"混为一谈**。在不确定方向时，你的首要任务是"验证方向是否正确"，而不是"为未来做好准备"。大多数"优化"在方向改变后都会变成浪费——如果你三个月后换了一个方向，今天花两周做的"高性能架构"就一文不值。

## 触发条件

用户正在执行以下任一操作时触发：

- **场景一：用户说"我先把这个架构搭好"或"以后扩展会很难"**。如果用户在做架构设计时，考虑的是"以后需要什么"而不是"现在需要什么"，说明他正在为"可能永远不存在的未来"付出时间成本。

- **场景二：在 Validate 阶段讨论技术选型时，用户倾向于选择更复杂的框架或技术栈"为未来做准备"**。如果用户说"先用这个框架，以后扩展方便"——但还没有验证过核心需求是否存在，说明他正在把"技术偏好"和"产品需求"混为一谈。

- **场景三：用户把"代码质量"和"过度设计"混为一谈**。如果用户认为"不加抽象层、不做接口设计就是代码质量差"，说明他混淆了"好的代码"和"过度设计的代码"。好的代码是简单、可读、能解决问题的代码——不是"为未来准备了三个抽象层"的代码。

- **场景四：用户说"先把性能优化好，不然以后改起来麻烦"——但此时还没有任何用户**。如果用户在没有用户压力的情况下优化性能，说明他正在用"未来可能的问题"来证明"今天的投入"。没有用户，就没有"性能问题"——只有"假设的性能问题"。

## 行为指导

### 1. 问"这个优化解决的是现在的问题还是未来的问题？"

每次你要做"优化"时，先问自己这个问题。如果答案是"未来的问题"，停下来。未来可能根本不会来——你的方向可能改变、你的用户可能不喜欢你的产品、你可能在三个月后完全换一个方向。花时间解决未来的问题，等于在赌"方向不变"。

实际做法：在代码注释或文档中标注"这个设计在 X 条件下需要重构"，然后继续做当前最重要的事。标注不等于实现——知道"以后要改"和"现在就要改"是两回事。

### 2. 用"最简可行方案"替代"最佳方案"

"最佳方案"往往是"最复杂的方案"。实际上，你需要的不是"最佳方案"，而是"此刻够用的方案"。

具体做法：
- 先问"当前最少的方案是什么"——不是"最好的方案"，而是"最少的方案"
- 实现这个最少的方案，然后继续验证
- 只有当用户数量和系统负载告诉你"不够用了"时，才考虑优化

判断标准：如果你需要花超过 1 天的时间来讨论"哪个方案更好"，说明这两个方案都足够好——选一个实现，然后继续前进。

### 3. 标记"知道以后要改"但不需要现在做

把"知道以后要改"的事情记下来，但不要现在做。这需要一种"有意识的克制"——知道问题存在，但选择不在今天解决。

具体做法：
- 在代码注释中写 TODO 注释，标注"当用户量达到 X 时，需要替换为 Y 方案"
- 在文档中记录"已知的设计约束"和"未来需要重构的模块"
- 把这些"待优化"项放入一个"技术债清单"，而不是"当前迭代"
- 然后继续做当前最重要的事

关键区别：
- **"需要现在做"**：这个问题如果不解决，今天的核心功能无法完成
- **"知道以后要改"**：这个问题如果今天不解决，核心功能不受影响，但未来可能需要改
- 区分这两者，是避免过早优化的核心能力

### 4. 80/20 法则：20% 的工作解决 80% 的问题

在大多数情况下，用 20% 的工作量就能解决 80% 的问题。剩下的 80% 的优化工作，属于"锦上添花"——在验证阶段之前，不值得做。

如何运用 80/20 法则：
- 对着你的"优化清单"，问自己"哪个优化能带来最大的收益"
- 找到那个"投入最小、收益最大"的优化，只做这一个
- 其他优化项标记为"以后再说"
- 如果选不出"哪个收益最大"，说明所有优化的收益都不明显——不要在此时做任何优化

如果你发现自己在做"最后 20% 的完美"，停下来，问自己"这 20% 的完美能帮助我今天验证核心假设吗？"如果答案是否定的，切换到"最低可行方案"模式。

### 5. 等用户告诉你需要优化

在验证阶段，用户是你最好的"优化信号"。不要自己去猜测"哪里需要优化"，而是等用户告诉你：

- 用户说"太慢了" → 优化性能
- 用户说"这个功能不好用" → 优化体验
- 用户说"我需要这个功能" → 优化功能
- 用户没有抱怨 → 不需要优化

"等用户告诉你"不是被动的，而是主动的：你主动把产品放到用户面前，观察他们的真实反应。如果用户没有抱怨，说明"不够好"的程度还不够——先解决"有没有"的问题，再解决"好不好"的问题。

### 6. 重构比预先设计更容易

很多人害怕"先做出来，后面再改"，因为他们认为"重构很难"。但实际上，重构比预先设计更容易，因为重构时你拥有真实的信息：

- 重构时，你知道用户真正需要什么，不需要猜测
- 重构时，你有真实的代码和用户行为数据可供参考
- 重构时，你只需要解决"现在的问题"，而不是"未来可能的问题"
- 重构时，你的改动有明确的检验标准——用户是否因此受益

预先设计的问题在于：你是在"信息不足"的情况下做决策。你不知道用户会怎么用、不知道哪个功能会火、不知道哪个模块需要扩展。在这种情况下做出的"优化"决策，大概率是错的。

## 不适用场景

- **安全/合规领域**：在安全、合规、隐私等领域，不能"先做出来再优化"。安全设计必须从第一天开始，因为安全漏洞可能导致数据泄露、法律风险、用户信任丧失。在这些领域，"提前设计"是必要的预防措施，不属于"过早优化"。

- **基础设施层**：如果用户正在构建基础设施（如数据库、消息队列、网络协议），那么"性能、扩展性、通用性"是核心功能，不是"优化"。基础设施的"正确性"和"可扩展性"是产品的一部分，需要在设计阶段考虑——这类产品在方向确定后，优化本身就是核心价值。

- **核心 API 设计**：如果用户正在设计对外公开的 API（如 REST API、SDK、库的公共接口），那么"好的设计"是必须的——因为 API 一旦发布，修改成本极高。API 的兼容性和一致性需要从一开始就考虑，这属于"必要设计"而非"过早优化"。

- **用户已有明确的 PMF 和真实用户量**：如果用户已经验证了产品-市场匹配，并且有真实的用户在使用产品，那么"优化性能、扩展性、通用性"就不再是"过早优化"，而是"必要的工程投入"。这套策略适用于验证阶段和早期阶段，不适合已确认 PMF 后进入规模化阶段的场景。
