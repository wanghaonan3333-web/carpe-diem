# 行为卡：持续验证

> 验证不是一次性的"做完就结束"的活动——它应该成为贯穿项目始终的节奏
> 蒸馏日期：2026-09-01

## 问题本质

当你完成 Validate 阶段并得到一个"PASS"结论后，你很容易认为"验证已经做完了，现在可以安心推进了"。这个想法是危险的。

问题在于：**验证是一个"时间快照"，而用户和市场是持续变化的**。

- 用户在 Validate 阶段说的"我需要这个"——三个月后可能已经找到了替代方案
- 用户在 Validate 阶段愿意付的价钱——半年后可能因为预算变化而不愿意了
- 你在 Validate 阶段验证的假设——随着产品迭代，新的假设不断出现，它们没有被验证过

更常见的情况是：项目在推进过程中遇到了"小问题"——用户反馈说"这个功能不太对"、用户说"我其实想要的是另一个东西"——但你因为已经通过了 Validate，就忽略了这些信号，继续按原计划执行。等你发现方向错了，已经浪费了几周甚至几个月。

## 关键洞察

### 验证是习惯，不是事件

如果你把验证看作"Validate 阶段做的事"，那么 Plan 和 Track 阶段你就不会主动去验证新假设。你会默认"已经验证过了"，然后埋头执行。

正确的思维是：**验证是贯穿项目始终的节奏，而不是某个阶段的"检查点"**。

就像你不需要"一次性吃饱"来维持一生的能量，你也不需要"一次性验证完"来确保整个项目方向正确。验证应该是"持续的小口进食"——每周做一点，而不是每三个月做一次大的。

### 为什么一次性验证不够

| 一次性验证的误区 | 持续验证的真相 |
|----------------|--------------|
| "Validate 阶段已经验证过了" | 验证的是"当时的假设"，不是"现在的现实" |
| "Plan 阶段不需要再验证" | Plan 阶段会产生新的假设（优先级、范围、技术方案），它们也需要验证 |
| "Track 阶段只需要看数据" | 数据告诉你"发生了什么"，但不告诉你"为什么"。需要回到用户那里去理解 |
| "等下次 Validate 再做验证" | 下次 Validate 可能就是"三个月后，发现方向错了" |

### 验证的"保质期"

每个验证结论都有"保质期"——在特定时间窗口内有效。过了保质期，你需要重新验证：

| 验证内容 | 典型保质期 | 为什么有保质期 |
|---------|-----------|--------------|
| 用户痛点（核心需求） | 6-12 个月 | 用户的生活和工作会变化，新的解决方案会出现 |
| 付费意愿（定价） | 3-6 个月 | 市场环境、竞争格局、用户预算会变化 |
| 功能优先级（什么最重要） | 1-3 个月 | 用户使用产品后，优先级会发生变化 |
| 技术可行性（能实现吗） | 3-6 个月 | 新技术、新工具、新方案会出现 |
| 竞品格局（谁在竞争） | 1-3 个月 | 竞品在快速迭代，竞争格局可能随时改变 |

**关键原则：你的验证计划里应该包含"下次验证时间"——就像食品包装上的保质期。**

## 对 Carpe Diem 用户的启发

### Validate 阶段

**核心行为：在完成 Validate 阶段时，不要只记录"结论"，还要记录"下次验证时机"。**

当你完成一个假设的验证并得到结论后，在验证记录中加上以下内容：

```
验证结论：PASS（用户愿意为离线笔记功能付费）
验证日期：2026-09-01
验证方法：落地页 + 预付款（3 人付款）
下次验证时机：2026-12-01（3 个月后）
触发重新验证的条件：
  - 用户付费率下降超过 20%
  - 主要竞品发布了类似功能
  - 用户反馈中出现了新的核心需求
```

**具体做法：**

1. 为每个验证结论设置"过期时间"。根据验证内容的性质设定 1-6 个月不等的保质期。
2. 设置"触发重新验证的条件"。当这些条件被触发时，即使还没到过期时间，也应该重新验证。
3. 在 Validate 阶段的输出文档中，单独列出"待重新验证项"列表。

**关键原则：**

- **每个 PASS 结论都是一个"暂时有效的假设"，不是"永久真理"。** 在 Validate 结束时，标注"这些结论将在 X 时间后过期"。
- **验证的"保质期"取决于验证内容的稳定性。** 核心用户需求（6-12 个月）比功能优先级（1-3 个月）更稳定。给不同的验证内容设置不同的保质期。
- **不要等到"出问题了"再验证。** 设置定期验证节奏——比如每 4 周安排一次"验证检查"。

### Plan 阶段

**核心行为：在 Plan 阶段的每个里程碑中，加入"验证检查点"。**

在你规划里程碑时，不只是规划"要做什么功能"，还要规划"什么时候验证这些假设是否仍然成立"。

**具体做法：**

1. 在每个里程碑的描述中，加入"验证检查"项：
   ```
   里程碑 1：完成首版离线笔记功能
   [验证检查] 联系 3 个首批用户，验证"离线笔记"仍然是他们的核心需求
   [验证检查] 检查是否有新的竞品出现，影响我们的价值主张
   ```

2. 在里程碑的验收标准中，加入"验证未过期"条件：
   ```
   验收标准 1：离线笔记功能完成并上线
   验收标准 2：与 3 个用户确认核心需求未变
   验收标准 3：竞品检查完成，无重大变化
   ```

3. 在每个里程碑结束时，花 2 小时做一次"验证健康检查"：
   - 上次验证的结论是否仍然有效？
   - 项目过程中出现了哪些新假设？它们是否被验证了？
   - 用户反馈中是否有与原有验证结论矛盾的地方？

**验证检查的"5 分钟版本"：**

如果你觉得"每个里程碑都做验证检查"太麻烦，至少做这个 5 分钟检查：

```
1. 最近一次和用户交流是什么时候？(如果超过 2 周，需要安排一次)
2. 最近有用户说过"这个功能不是我们想要的"吗？
3. 最近有新的竞品出现吗？
4. 我们有没有在推进一个"假设正确但没验证过"的方向？
   - 如果有，写下这个假设，标注"待验证"
```

**关键原则：**

- **不要在 Plan 阶段关闭验证通道。** Plan 不是"验证已经结束，现在开始执行"——Plan 是"验证过的假设指导执行，同时持续验证新假设"。
- **每个里程碑都应该至少包含一次"与真实用户的接触"。** 即使只是 15 分钟的对话，也足以让你知道"方向是否还在正确的轨道上"。
- **把"验证检查"和"功能开发"放在同一个优先级。** 如果验证检查被推迟，说明你的团队认为"验证"不如"开发"重要——这是危险的信号。

### Track 阶段

**核心行为：在 Track 阶段保持"用户验证节奏"——每周至少和 1-2 个真实用户交流。**

Track 阶段最容易出现的问题就是"只看数据，不问用户"。数据告诉你"发生了什么"，但只有用户告诉你"为什么发生"。

**具体做法：**

1. **建立"用户对话节奏"**：
   - 每周至少和 1-2 个真实用户交流
   - 交流形式不限：15 分钟电话、微信对话、当面访谈、邮件交流都可以
   - 关键在于"保持节奏"，而不是"每次都很深入"

2. **在 Track 阶段关注"验证过期的信号"**：
   - 用户活跃度下降 → 可能是"产品价值"验证过期
   - 用户付费率下降 → 可能是"定价"验证过期
   - 用户推荐行为下降 → 可能是"满意度"验证过期
   - 新用户注册下降 → 可能是"需求"验证过期
   - 用户反馈中出现新的需求方向 → 可能是"优先级"验证过期

3. **设置"验证报警器"**：
   - 当某个关键指标下降超过 20% 时，触发"重新验证"流程
   - 当用户反馈中出现"我们其实想要的是 X"时，记录新的假设
   - 当竞品发布重大更新时，检查原有验证结论是否仍然有效

4. **在 Track 的定期回顾中加入"验证健康度"检查**：
   ```
   验证健康度检查（每 2 周一次）：
   ✅ 最近一次和用户交流的时间：____
   ✅ 最近两周接触的用户数：____
   ✅ 现有验证结论中，还有多少未过期：____
   ✅ 本周是否出现了新的假设：____（如有，记录在"待验证"列表）
   ✅ 是否有验证结论被用户行为否定：____
   ```

**"用户对话"的 15 分钟模板：**

如果你不知道和用户聊什么，用这个模板：

```
1. "最近用我们的产品感觉怎么样？"（打开话题）
2. "有没有遇到什么让你觉得'这个功能不太对'的地方？"（发现问题）
3. "如果现在可以改一个功能，你会改什么？"（验证优先级）
4. "你最近有没有遇到什么新的问题，是我们当前产品没有解决的？"（发现新假设）
```

**关键原则：**

- **Track 阶段不是"只看指标"的阶段，而是"用指标发现问题，用用户验证理解问题"的阶段。** 指标是报警器，用户是诊断工具。
- **"没有新闻就是好新闻"是危险的验证策略。** 如果用户没有主动联系你，不代表他们满意——可能只是因为他们懒得给你反馈。你需要主动去问。
- **你不需要很多用户，但需要"正确的节奏"。** 每周和 1-2 个用户交流，比每个月和 20 个用户交流更有效。节奏比规模重要。
- **当用户反馈与指标矛盾时，优先相信用户的行为数据。** 用户说"我很喜欢"但活跃度下降，那么活跃度下降是更可靠的信号。

### 适合所有阶段的验证节奏

下面是一个"持续验证"的通用节奏，适合从 Validate 到 Track 的全过程：

| 频率 | 做什么 | 为什么 |
|------|-------|-------|
| **每周** | 至少和 1-2 个用户交流（15 分钟即可） | 保持对用户需求的感知 |
| **每两周** | 做一次"验证健康度检查" | 确保验证结论没有过期 |
| **每月** | 回顾一次"待验证假设"列表 | 确保没有新的假设被忽略 |
| **每季度** | 对核心假设做一次"全面重新验证" | 确保大方向仍然正确 |

## 反向提醒

- **不要为了验证而验证。** 持续验证不是"每周都要做用户访谈"的形式主义。验证的目的是"发现方向是否偏了"，而不是"完成验证指标"。如果项目进展顺利且没有新的不确定因素，可以减少验证频率。
- **持续验证不等于"没有决策"。** 如果你每周都验证，但从不根据验证结果调整方向，那验证只是自我安慰。持续验证的价值在于"持续调整"，而不是"持续确认"。
- **注意"验证疲劳"。** 如果你每周都和用户交流，但每次都得到同样的答案，说明你可能已经验证充分了，可以降低频率。不要因为"应该验证"而做无意义的重复验证。
- **持续验证不适用于所有场景。** 对于短期项目（1-2 周的项目）、明确的技术任务、或者"做出来再说"的探索性项目，持续验证的节奏可能过于沉重。根据项目性质调整验证密度。
- **"用户说"仍然是态度信号，不是行为信号。** 持续的用户对话会产生很多"用户说"的反馈。这些是"发现问题的线索"，不是"验证结论的证据"。当你发现用户说了一个新问题时，需要设计一个行为信号的验证实验来确认，而不是直接把"用户说"当成验证结论。
- **不要因为"持续验证"而忽略了"深度验证"。** 每周 15 分钟的用户对话是"扫描"，不是"诊断"。当你发现了一个值得深入的问题时，需要安排一次完整的验证实验（写假设验证卡、设计验证方法、收集行为信号、得出 PASS/PIVOT/REJECT 结论），而不是停留在"每周聊一聊"的层面。
