# 行为卡：持续发现

> 触发条件：产品上线后认为"已经验证过了，不需要再验证了"

## 问题本质

当产品通过 Validate 阶段并上线后，最常见的错误思维是："验证已经做完了，产品已经上线了，现在只需要开发和交付就行了。"

但问题在于：**用户和市场不会因为你"验证过了"就停止变化**。你在 Validate 阶段的验证结果只是一个"时间快照"——它告诉你"验证完成时用户想要什么"，但用户的需求会变，竞争格局会变，你的理解也会变。

更危险的是：当你停止发现时，你不再主动了解用户的需求变化，而是"被动接收反馈"——等用户抱怨、等用户流失、等数据下滑。等到你发现问题时，已经浪费了几个月的时间。

问题的根源是：**你把"发现"当作"阶段"，而不是"习惯"**。发现是持续的活动，不是一次性的事件。它需要贯穿整个产品生命周期，而不是只在 Validate 阶段做一次。

持续发现的核心任务是：**在产品上线后，保持与用户的持续接触，持续更新对用户需求的理解，让发现结果驱动路线图——而不是让"已经开发完成的功能"驱动路线图。**

## 触发条件

用户在以下场景中应该激活此卡：

- 用户说"我们已经验证过了"或"产品上线了不需要再验证了"——认为发现阶段已经结束，不再需要主动了解用户
- 用户说"我们只需要按计划执行就行"——路线图已经定好，不再需要根据用户反馈调整
- 用户说"用户反馈已经够多了，不需要再做什么发现了"——把"被动接收反馈"当作"持续发现"
- 产品上线后，团队的节奏是"开发→发布→开发→发布"，没有"发现→验证→学习→再发现"的循环

## 行为指导

### 1. 建立持续发现的节奏——而不是"等用户反馈"

持续发现不是"等用户来找你"，而是"你主动去找用户"。你需要建立固定的节奏，让发现成为团队的习惯，而不是"有时间的时候才做"。

操作方法：
- 设定一个固定的发现节奏：每周或每双周
  - 每周：安排 2-3 次用户访谈或观察
  - 每双周：安排一次"发现同步"——团队一起回顾最近的发现成果
- 在发现节奏中，做的不是"验证假设"，而是"了解用户"：
  - 用户最近遇到了什么问题？
  - 用户在使用产品时，有什么新的场景出现？
  - 用户对产品的理解有没有变化？
- 发现节奏不需要"大"——每周 2 次 30 分钟的用户交流，比每季度一次 2 天的用户调研更有效
- 关键：让发现成为"定期的事"，而不是"有需要才做的事"

### 2. 维护机会解法树——而不是"功能列表"

大多数团队的"产品规划"就是一张"功能列表"——用户说想要什么，就加上去。但功能列表的问题是：你只知道"用户想要什么"，不知道"用户为什么想要这个"。

操作方法：
- 用"机会解法树"替代"功能列表"：
  - 树的根是"核心问题"——用户想要解决什么问题？
  - 树的分支是"机会"——用户希望以什么方式解决这个问题？
  - 树的叶子是"解法"——我们可能用什么功能来实现这个解法？
- 例如：
  - 核心问题：用户需要更好地管理他们的项目进度
  - 机会：用户希望"不用打开多个工具就能看到进度"
  - 解法：在群聊中集成进度提醒 / 做一个每日进度汇总 / 让用户一键分享进度
- 维护机会解法树的好处：
  - 看到"什么功能可以解决什么机会"
  - 避免"一个功能看起来不错"就加进去——先看它解决了什么机会
  - 当多个功能对应同一个机会时，可以合并；当一个机会没有解法时，创造新解法

### 3. 区分"探索"和"交付"——两个不同的节奏

产品上线后，团队很容易陷入"只做交付"的模式——规划功能、开发、测试、发布——然后重复。但持续发现需要"探索"的节奏和"交付"的节奏并行。

操作方法：
- 明确区分两种活动：
  - **探索**：了解用户需求、发现新机会、验证假设。产出是"洞察"和"可测试的假设"
  - **交付**：设计、开发、测试、发布功能。产出是"可用的功能"
- 两种节奏的关系：
  - 探索在前面，交付在后面——先知道"做什么"，再知道"怎么做"
  - 探索和交付是"并行"的，不是"串行"的——探索为下一轮交付提供输入，而不是等探索完成才开始交付
- 用"探索时间"保护团队不被交付淹没：
  - 每个开发周期（如两周）中，安排 1-2 天用于探索活动
  - 探索活动不产出"代码"，但产出"下一个周期应该做什么"的决策依据

### 4. 每次发现活动产出可测试的假设——而不是"用户说"

"用户说"不是"发现"的产出——"发现"的产出应该是"可测试的假设"。

操作方法：
- 每次发现活动（访谈、观察、数据分析）后，写下你的"发现"和"假设"：
  - 发现：我们观察到的事实（如"用户在注册后第三天开始流失"）
  - 假设：基于这个发现，我们推测的问题原因（如"用户注册后没有体验到核心价值"）
- 把假设写成可测试的形式：
  - 不是"用户可能觉得注册流程太复杂"
  - 而是"如果把注册流程从 5 步减少到 3 步，注册转化率会提升 10%"
- 假设的优先级：
  - 高影响 + 高不确定性 → 先测试
  - 高影响 + 低不确定性 → 可以开始设计
  - 低影响 → 暂缓

### 5. 发现与开发周期并行，而不是串行

很多团队的错误是：先把发现做完，再开始开发——但发现是"永远做不完"的，因为用户需求一直在变。正确的做法是：让发现和开发并行，发现为开发提供持续的输入。

操作方法：
- 建立"发现→开发"的循环：
  - 周期 1 的前两周做发现 → 产出"下一个周期做什么"的假设
  - 周期 1 的后两周做开发 → 实现基于发现确定的优先级
  - 同时，在开发周期中继续做发现 → 为下一个周期提供输入
- 这样，发现和开发是"流水线"的关系：
  - 发现 → 产出假设 → 开发 → 交付功能 → 测量结果 → 发现新的问题
- 不要让开发"等待"发现——如果你在开发周期中，发现还没有完成，就用已有的信息做决策，而不是停下来等
- 不要让发现"等待"开发——发现活动不应该因为"正在开发"而停止

### 6. 让发现结果驱动路线图——而不是"已经做的功能"

路线图应该反映"我们接下来要验证什么假设"和"我们接下来要解决什么用户问题"，而不是"我们接下来要开发什么功能"。

操作方法：
- 把路线图从"功能列表"改为"目标列表"：
  - 不是："下个月做搜索功能"
  - 而是："下个月让用户能更快地找到历史记录——可能是搜索，也可能是标签，也可能是分类"
- 把发现结果作为路线图调整的依据：
  - 如果发现结果显示"用户真正需要的是标签而不是搜索"——调整路线图
  - 如果发现结果显示"用户的核心痛点不是找到记录，而是不知道记录了什么"——重新定义问题
- 定期（每个月或每个里程碑）回顾：
  - 最近的发现让我们对用户需求的理解有什么变化？
  - 基于这个变化，我们的路线图需要调整吗？
  - 我们正在做的功能，是否仍然在解决"用户最关心的问题"？

## 不适用场景

- **纯维护模式**：如果产品已经进入"只维护不发展"的模式（如只修复 bug、不新增功能），持续发现不适用——不需要主动了解用户需求变化，只需要确保产品正常运行
- **已明确退出的项目**：如果用户已经决定退出或放弃项目，持续发现不适用——不需要了解用户需求，需要的是"如何优雅退出"
- **一次性项目**：如果项目是一次性的（如活动页面、营销工具），生命周期很短，不需要"持续发现"——只需要按需求完成即可
- **纯兴趣项目**：如果用户明确说"我做这个是出于兴趣，不需要考虑用户需求"，那么持续发现不适用——兴趣项目的价值在于"做自己喜欢的东西"，而不是"持续了解用户需求"
