# Carpe Diem 智慧蒸馏指南

> 目标：把外部经验转成在正确场景下触发、可执行、可反驳且可维护的行为卡。
> 最后更新：2026-08-31

## 一、先说结论

智慧蒸馏不是“收集更多观点”，也不是“把一本书压缩成一张卡”。一张候选卡只有依次通过以下门槛，才进入运行时：

`候选规则 → 来源核验 → 忠实转译 → 去重分工 → 场景测试 → 接受并路由`

卡片数量不是完成指标。宁可拒绝一张重复或失真的卡，也不要为了凑阶段数量而收录。

## 二、两层模型

### 研究层：可追溯

研究层必须保留证据，供维护者审核，不在普通对话中自动加载。每条候选规则至少记录：

- `evidence_id`：稳定编号；
- 来源类型、作者/组织、标题、版本或发布日期；
- 精确定位：章节、页码、文档段落或 URL；
- 原始主张的短摘要，不用二手名言代替原文；
- 转译成什么行为，以及转译中删除了什么；
- 适用前提、反例和核验状态；
- 核验人及日期。

核验状态只允许：

- `verified-primary`：已检查一手来源；
- `verified-multiple`：反模式已由多个独立案例交叉验证；
- `needs-primary-source-check`：只有线索，禁止包装成确定事实；
- `rejected`：失真、重复、不可操作或风险不可控。

### 运行层：不露来源

行为卡使用 Carpe Diem 自己的语言，不靠人名、公司名或权威背书说服用户。这里的“不露来源”只约束运行时表达，不允许删除研究层的出处。

运行卡仍须满足：

- **具体**：由可观察信号触发，而不是泛泛解释概念；
- **可操作**：给出下一步动作和停止条件；
- **有边界**：说明何时不该用、何时升级给专业人员；
- **不伪造精度**：来源没有给出普适阈值时，不擅自写成 `10%`、`20%`、`24h` 等硬标准。

## 三、最小蒸馏单元

一个来源通常只提取一到两条会改变决策的规则。行为卡不要求固定四个触发、六个步骤或四个边界；只写足以改变行为的内容，避免为满足格式而填充。

推荐结构：

```markdown
# 行为卡：名称

> 触发信号：一句可观察的条件
> 证据编号：WD-xxx（仅维护用，运行时不复述来源）

## 问题本质
## 触发条件
## 行为指导
## 不适用场景
```

每一条指导都应能回答：触发了什么信号、用户现在做什么、产出什么证据、何时停止或改道。

## 四、完整工作流

### 1. 研究与建档

优先使用一手材料：官方文档、原始论文、作者原文、真实系统的公开手册。书籍可用时记录版本和章节；只能找到二手摘要时标记待核验。

不要使用“唯一一本”“大多数成功项目”“被无数团队验证”等无法审计的表述。工程案例只能证明该机制在那个上下文中工作过，不能自动升级为普适规律。

### 2. 写候选规则

把原始主张改写成条件化规则：

`当 <可观察信号> 出现，在 <适用前提> 下，尝试 <动作>，用 <证据> 判断是否继续。`

如果转译改变了原意、删掉了关键前提或加上了来源没有支持的数字，退回研究层。

### 3. 去重与分工

新增前必须与现有卡做重叠检查。标题不同不代表行为不同。比较以下四项：

- 是否由同一个用户信号触发；
- 是否给出相同的第一步；
- 是否产出相同的决策证据；
- 是否导向相同的继续/停止决定。

三项以上相同，默认合并。保留两张时必须写出明确分工。例如：

- `test-card`：把假设写成可判定的测试卡；
- `experiment-design`：在测试卡已存在后，选择成本最低且证据有效的实验；
- `gonogo-decision`：实验结束后审计证据并作继续、转向或停止决定。

### 4. 场景测试

每张候选卡至少通过四类测试：

1. **正向场景**：触发后是否给出更好的下一步；
2. **近邻场景**：相似卡是否会抢占，路由能否区分；
3. **反向场景**：不适用时是否明确不加载；
4. **风险场景**：安全、法律、财务、隐私或真实收费是否给出升级和披露边界。

验收关注行为差异，不只检查标题是否齐全。

近邻卡和风险边界应沉淀为机器可读回归样例。本项目当前判例位于 [`references/wisdom/mentors/routing-acceptance-cases.json`](../references/wisdom/mentors/routing-acceptance-cases.json)，校验器会检查卡片存在、主辅卡预算和禁止选择集合，单元测试会锁定关键分工。

### 5. 单写者集成

多人并行时，研究者或卡片作者只写自己的卡片和证据包。`README.md`、`SKILL.md`、`manifest.json`、总结文档只由一名集成者修改，避免共享索引冲突、重复文件和版本漂移。

### 6. 运行时路由

阶段只用于缩小候选集合，不等于自动加载该阶段全部卡片。

- 每轮最多加载一张主卡；只有确有互补作用时再加载一张辅卡；
- 必须有对话或状态中的具体触发信号；没有强信号就不加载；
- 优先级：安全/授权边界 > 阶段门槛 > 明确触发 > 辅助优化；
- 行为卡补充阶段指南，不能覆盖阶段转换、授权或 Track 只读边界；
- 读取索引后只打开被选中的卡，不预读整阶段。

## 五、验收清单

### 单卡

- [ ] 有证据编号，研究层能定位到一手来源或明确标为待核验；
- [ ] 原始主张、转译规则、适用前提三者一致；
- [ ] 没有无来源的普适数字和绝对化断言；
- [ ] 与近邻卡有明确分工，或已合并；
- [ ] 正向、近邻、反向、风险场景通过；
- [ ] 触发条件可从真实对话或状态中观察；
- [ ] 指导包含动作、证据和停止/改道条件。

### 集成

- [ ] 索引链接存在，manifest 收录所有运行文件；
- [ ] 无内容完全相同的重复卡；
- [ ] 中英文 SKILL 路由一致；
- [ ] 一轮路由不超过两张卡；
- [ ] 结构校验、单元测试和智慧卡校验全部通过；
- [ ] 版本、README 和变更记录一致。

## 六、维护原则

- 新卡先进入候选区，不能因为已经写完就自动接受；
- 来源更新、规则被反例推翻或产品边界变化时，重新核验；
- 低触发率不代表应删除，但长期与其他卡同时触发且不改变建议，优先合并；
- 真实运行反馈优先用于改路由和边界，不用于反向篡改来源主张；
- 发布前由与作者不同的人做最终忠实度和风险审核。
