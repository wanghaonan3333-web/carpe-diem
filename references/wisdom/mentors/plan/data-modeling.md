# 行为卡：数据建模

> 触发条件：Plan 阶段进入"架构、组件、数据流"章节，用户开始设计数据库 schema 或数据模型

## 问题本质

数据模型是系统的骨架——它决定了系统能做什么、不能做什么、改起来有多痛苦。好的数据模型让新功能自然而然地融入现有结构，坏的数据模型让每次改动都像在拆墙。

大多数人在设计数据模型时，习惯从"数据库怎么存"的角度出发——"用户表要有这些字段"、"订单表要关联用户表"、"这个字段放这里方便查询"。但问题在于：**数据模型解决的是"业务关系"，不是"存储方式"**。如果你从"数据库怎么存"开始设计，你的模型会反映数据库的约束而非业务的真实结构。

问题的根源是：**你把"存储方便"当成了"设计目标"，但一个好的数据模型应该让业务概念清晰可见，而不是让数据库性能最优**。存储优化可以后续做，但模型结构一旦定下来，改动的成本很高——因为所有代码、查询、接口都依赖于它。

## 触发条件

用户正在执行以下任一操作时触发：
- Plan 阶段进入"架构"章节，开始设计数据库 schema 或数据模型（关系型或非关系型）
- 讨论中直接讨论"这个字段用什么类型"、"这张表放哪个数据库"，而非先讨论"业务实体之间的关系"
- 数据模型设计围绕"技术实现"展开：如"这个字段冗余一下可以避免 JOIN"、"这样设计方便分库分表"
- 不同模块使用了相同的字段名但含义不同，或相同的业务概念在不同模块中有不同的命名

## 行为指导

### 1. 从业务概念出发而非从技术出发——先用业务语言描述数据关系，再考虑技术实现

在设计数据模型之前，先用业务语言回答这三个问题：

- **系统中有什么业务实体？** 用户、订单、商品、支付记录……这些是业务实体，不是数据库表。
- **实体之间的关系是什么？** 一个用户有多个订单，一个订单包含多个商品，一个商品属于一个分类。这些关系应该用业务语言描述，而非用外键描述。
- **每个实体的核心属性是什么？** 订单有"下单时间"、"总金额"、"状态"——这些是业务属性。"订单的数据库主键是什么"是技术问题，不是业务问题。

具体做法：先画出"业务实体关系图"（实体-关系图），用业务术语标注实体和关系，然后再映射到数据库 schema。不要在画图的时候考虑"这个字段怎么存"——这会在后续的 schema 设计阶段解决。

判断标准：给你一个不懂技术的人看你的实体关系图，他应该能理解"这个系统在管理什么"和"这些概念之间有什么关系"。

### 2. 规范化到够用即可——过度规范化和高性能一样有害

数据库规范化（消除冗余、避免数据不一致）是好的，但规范化不是越彻底越好。规范化的边际收益递减：

- **第一范式（1NF）到第三范式（3NF）**：大部分系统到这里就够了。消除重复组、消除部分依赖、消除传递依赖。
- **超过第三范式**：只有在特定场景下才有必要。比如，在多对多关系特别复杂、需要避免异常更新的场景下才需要更高的范式。

过度规范化的代价：
- **查询复杂度爆炸**：一个简单的"查看订单详情"需要 JOIN 8 张表
- **性能问题**：过多的 JOIN 导致查询变慢
- **开发效率下降**：每个新功能都需要了解多张表的关系链

具体做法：先设计到第三范式，然后根据实际查询模式，有选择地引入冗余（反范式化）。但注意——**反范式化应该是"特意为之"的优化，而不是"因为懒得设计"的默认行为**。

### 3. 为查询建模而非为存储建模——数据模型服务于"怎么用"，而非"怎么存"

数据模型的设计应该由"业务场景"驱动，而非"存储空间"驱动。问自己：

- **最常用的查询是什么？** 如果 80% 的查询是"按用户查最近订单"，你应该确保这个查询路径是高效的。如果因此需要增加一个索引或冗余字段，应该做。
- **最常用的数据变更是什么？** 如果 80% 的数据变更在"更新订单状态"，你应该确保这个更新操作是原子、快速、安全的。
- **数据的生命周期是什么？** 数据是"写入后很少修改"（如日志）还是"频繁更新"（如用户状态）？不同的生命周期需要不同的模型设计。

具体做法：在设计数据模型时，先列出"核心查询场景"和"核心变更场景"，然后针对这些场景优化模型。不要为了"可能有一天会用到"的场景而设计复杂的模型——等那天真的来了，再根据实际需求调整。

### 4. 预留扩展点但不做过度设计——为变化留空间，但不为还没发生的变化做准备

好的数据模型能在需求变化时优雅地适应，而不是"一改就崩"。但预留扩展点和过度设计之间的界限很清晰：

- **合理的扩展点**：预留了"扩展字段"（如 JSON 字段）、预留了"类型字段"（如 `type` 枚举）、预留了"状态字段"（如 `status` 状态机）。这些字段在初期可能只有少数几个取值，但未来可以扩展。
- **过度设计**：为了"可能有一天会支持多租户"而提前设计租户隔离、为了"可能有一天会国际化"而提前设计多语言表、为了"可能有一天会分库分表"而提前设计分区键。

判断标准：如果你不确定某个扩展点将来会不会用到，就不要做。**等需求真的来了，再做扩展**。大多数"提前做的扩展"最终都没有被用到，反而增加了系统的复杂度和维护成本。

### 5. 命名一致性比创造性更重要——好的命名让模型自解释，坏的命名让每个查询都需要注释

命名是数据模型中最容易被忽视的细节。一致的命名规则可以让新成员迅速理解模型，而不一致的命名则让每个查询都需要猜测。

- **表名用复数还是单数？** 选一个，全系统一致。推荐用复数（`users`、`orders`），因为表是"集合"。
- **主键命名统一**：所有表的主键要么都叫 `id`，要么都叫 `{table_name}_id`。不要混用。
- **外键命名统一**：外键字段名应该清晰表达关联关系。`user_id` 比 `uid` 好，`order_id` 比 `ord_id` 好。
- **布尔字段用肯定句式**：`is_active` 比 `not_active` 好，`is_deleted` 比 `deleted` 好。否定句式让查询逻辑复杂化。
- **时间字段统一时区**：所有时间字段要么都用 UTC，要么都用当地时区并在字段名中标注（如 `created_at` 表示 UTC，`created_at_local` 表示当地时区）。

具体做法：在项目开始前定义一个"数据模型命名规范"文档，所有人遵守。不要等到有 20 张表之后再统一命名——那时改的成本太高了。

### 6. 数据完整性由数据库而非应用层保障——数据库约束是最后一道防线，不能依赖应用层代码

最常见的错误是"数据完整性靠应用层代码保障"——"我们的代码不会插入脏数据"、"ORM 会帮我们校验"。但问题是：**代码有 bug，ORM 有边界情况，多人协作时总会有人绕过规范**。

数据库层面的约束是最后一道防线：
- **非空约束（NOT NULL）**：如果某个字段必须有值，用数据库的非空约束，而不是让应用层代码来保障。
- **唯一约束（UNIQUE）**：如果某个字段的值必须唯一（如邮箱、用户名），用数据库的唯一约束，而不是在应用层先查后插。
- **外键约束（FOREIGN KEY）**：如果两个表之间的引用关系必须完整，用外键约束。虽然外键会影响写入性能，但数据完整性比微小的性能差异更重要。
- **检查约束（CHECK）**：如果某个字段的值必须在特定范围内（如状态值只能是 `pending`、`paid`、`cancelled`），用检查约束。

具体做法：在数据模型设计阶段，就明确每个字段的约束条件。不要等到上线后发现脏数据了再去补约束——补约束的代价比一开始就设计好要大得多。

## 不适用场景

- **原型阶段**：如果项目处于 Discover 或 Validate 阶段，目的是"快速验证想法是否可行"，数据建模是过度设计。原型只需要"能存数据就行"，不需要考虑模型、约束、扩展点。等原型验证通过后，再重新设计数据模型。
- **使用无 schema 数据库的快速迭代项目**：如果使用 MongoDB、Firebase Firestore 等无 schema 数据库，且项目处于快速迭代阶段，数据建模原则可以简化。无 schema 数据库的优势就是灵活——不需要在设计阶段就确定所有字段。但注意：即使使用无 schema 数据库，业务实体关系图仍然有价值——它帮助你理解数据之间的关系，只是不需要在数据库层面强制约束。
- **一次性数据处理脚本**：如果项目是"一次性的数据迁移、数据清洗、报表生成"，数据建模不需要。一次性脚本用完即弃，不需要考虑模型的可维护性和扩展性。
- **纯缓存层或消息队列**：如果项目不涉及持久化数据存储（如 Redis 缓存、Kafka 消息队列），数据建模原则不适用。缓存和消息队列的数据结构由使用场景决定，不需要像持久化存储那样考虑模型设计。
