# 行为卡：ADR 增强——未解决问题与采用策略

> 触发条件：Plan 阶段进入"架构决策"章节，用户正在编写或评审 ADR 时

## 问题本质

大多数 ADR（架构决策记录）只记录了"我们做了什么决定"和"为什么这么做"。但有两个关键问题被忽略了：

1. **未解决的问题**：任何决策都不可能一次性解决所有问题。但大多数人在写 ADR 时，会把"决策"和"完成"混淆——签了 ADR 就以为问题解决了，结果到实现阶段才发现一堆没讨论过的遗留问题。
2. **采用策略**：一个决策好不好，不只看它本身对不对，还看它能不能被顺利落地。但大多数 ADR 只写"选什么"，不写"怎么推"——结果就是：决策在文档上是正确的，但团队要么不知道怎么落地，要么落地方式完全偏离了决策初衷。

这两个缺失的字段，是 ADR 从"记录决策"升级为"引导落地"的关键。

## 触发条件

用户正在执行以下任一操作时触发：
- Plan 阶段进入"架构决策"章节，用户开始编写 ADR，但模板中只有"背景、决策、后果、替代方案"四个字段
- 用户评审 ADR 时，发现"决策看起来没问题，但不知道具体怎么落地"
- 用户发现同一个问题在多个 ADR 中反复出现，但每个 ADR 都把它当作"已解决"来处理
- 实现阶段发现 ADR 中有一个"默认假设"被推翻了，但 ADR 没有记录"如果这个假设不成立怎么办"

## 行为指导

### 1. 在 ADR 中增加"未解决问题"字段

在 ADR 的"后果"和"替代方案"之后，增加一个字段：

> **未解决问题：** 这个决策暂时没有回答的问题，以及什么情况下才需要回答它们。

这个字段应该包含三类内容：
- **已知的未知**：你知道这个问题还没解决，但你认为现在不需要解决。例如："API 的速率限制策略待定——首版先用简单的每分钟 100 次限制，后续根据实际使用情况调整。"
- **边界条件**：在特定情况下这个决策可能不成立。例如："如果单日用户量超过 10 万，当前的数据库分片策略可能需要重新设计。"
- **待验证的假设**：你在做决策时依赖的假设，但这些假设还没有被验证。例如："假设用户主要在桌面端使用——需要首版上线后验证移动端流量占比。"

判断标准：如果你的 ADR 没有"未解决问题"字段，说明你还没有把"决策"和"完成"区分开。一个好的 ADR 不是"所有问题都解决了"的文档，而是"在已知的限制下做出了最佳选择"的文档。

### 2. 在 ADR 中增加"采用策略"字段

在"未解决问题"之后，增加一个字段：

> **采用策略：** 这个决策如何从文档落地到实际代码或流程中。

这个字段应该回答：
- **谁负责落地？** 具体的人或团队
- **什么时候落地？** 在哪个里程碑、哪个阶段执行
- **怎么落地？** 是一次性切换、渐进式迁移、功能开关控制，还是新旧并行？
- **回滚方案？** 如果落地后发现决策有问题，如何回退？

示例：
> - 采用策略：在里程碑 2（第 3-4 周）由后端团队实施，采用"功能开关 + 渐进式迁移"策略——先对 10% 的用户开启，观察一周后逐步提高到 100%。如有问题，关闭功能开关回退到旧方案。
> - 不写成：计划在下一版中实施。（没有具体时间、负责人和策略）

### 3. 用"未解决问题"来区分 ADR 的决策边界

不是所有问题都需要在 ADR 中解决。区分三个层次：

- **本 ADR 必须解决的问题**：如果这些问题不解决，决策就无法落地。例如：选择数据库类型——如果不选，无法开始开发。
- **本 ADR 明确不解决的问题**：把这些写进"未解决问题"字段，明确推迟。例如：缓存策略——首版先不做缓存，上线后再根据性能数据决定。
- **本 ADR 没意识到的问题**：这是最危险的。如果多个 ADR 的"未解决问题"中有重复的主题，说明你有一个系统性的盲区。

操作建议：在 ADR 评审时，专门花 5 分钟检查"未解决问题"列表——如果其中一个问题被三个以上 ADR 同时列为"未解决"，这说明这个问题应该作为一个独立的 ADR 来处理，而不是在各个 ADR 中反复推迟。

### 4. 用"采用策略"来检验决策的可行性

一个看似正确的决策，如果"采用策略"写不清楚，说明决策本身可能有问题：

- **如果"采用策略"包含"同时修改 10 个模块"**：说明这个决策的影响范围太大，应该考虑更渐进的方式。
- **如果"采用策略"是"找时间统一改"**：说明没有真正落地计划，这个决策大概率会被遗忘。
- **如果"采用策略"是"直接全量切换"**：说明没有考虑风险，应该加一个"灰度验证"阶段。
- **如果"采用策略"写不出来**：说明决策还在"理论正确"阶段，没有考虑实际操作——可能这个决策并不适合当前项目状态。

判断标准：只有当"采用策略"能写出具体的人、时间、方式和回滚方案时，这个决策才算是"可执行的"。如果你写不出来，说明这个决策需要重新审视。

### 5. 为每个 ADR 设置"决策保质期"

ADR 一旦被"接受"，并不意味着它永远正确。在"未解决问题"中，标注每个假设的"保质期"：

> - 假设 A（有效期至里程碑 3）：用户量不会超过 1 万
> - 假设 B（有效期至首版上线）：移动端流量占比 < 20%
> - 假设 C（有效期至下个季度）：第三方 API 保持免费

当保质期到达时，需要重新审视这个 ADR 是否仍然有效。如果假设被验证为真，ADR 继续有效；如果假设被推翻，ADR 需要更新或废弃。

### 6. 编写 ADR 时先写"未解决问题"，再写"决策"

这个顺序提醒很重要：**先列出你还不确定的事情，再决定选什么。**

大多数人在做决策时，会先有一个"默认答案"，然后去找支持这个答案的理由。如果你先写"未解决问题"，你会发现自己对决策的假设——比如"假设数据库写入压力不大"、"假设用户能接受 3 秒加载时间"——这些假设正是你需要验证的。

操作建议：
1. 先列出所有"未解决问题"——你对这个决策还不确定的事情
2. 再决定"采用策略"——如何落地和验证
3. 最后写"决策"——在当前已知信息下，什么是最好的选择

这个顺序能显著减少"决策后才发现遗漏问题"的情况。

## 不适用场景

- **用户做的是个人项目，不需要多人协作**：如果项目只有一个人开发，不需要正式的 ADR 模板。你可以用简单的笔记来记录决策，不需要"未解决问题"和"采用策略"字段。
- **用户处于 Discover 阶段，尚未进入 Plan 阶段**：ADR 是 Plan 阶段的工具，在方向探索阶段不需要。如果用户还在做方向评估，应该先完成 Discover 阶段再考虑 ADR 模板。
- **用户做的是极小规模的项目**（如一个简单的 CLI 工具、一个单页应用）：如果项目复杂度很低，架构决策很少，引入完整的 ADR 模板是过度设计。这种情况下，只需要一个简单的决策日志就够了。
- **用户已经在使用比 ADR 更完善的决策记录方式**：如果用户已经有自己的决策记录系统（如 RFC 文档、设计文档、Notion 数据库），不需要强行切换到 ADR 模板。任何能记录"未解决问题"和"采用策略"的系统都可以。
