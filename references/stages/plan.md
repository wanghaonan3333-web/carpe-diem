# Plan · 打磨完整实施计划与交接包

## 一句话本质

把未来开发中最昂贵的决定提前做完，让开发 Agent 无需重新猜测项目目标。

## 进入条件

- Validate 结论为 `PASS`；
- 用户确认差异化与主要未知项；
- 用户明确同意进入完整规划。

## 主动讲授

按章节给出推荐设计。每一章讲清推荐、理由、具体场景、取舍和非目标，完成一章后再让用户修正。用户没有义务从空白回答技术、架构或测试问题。

## Agent 动作

依次完成：

1. 项目定位、目标用户、核心场景和非目标；
2. 用户体验、功能范围和版本边界；
3. 架构、模块、数据流和接口；
4. 错误处理、安全和隐私；
5. 测试、验证和验收标准；
6. 里程碑、任务拆分和依赖；
7. 开源协议、贡献方式和发布路径。

每章批准后记录关键决定。最终根据 `templates/project-plan.md` 和 `templates/project-handoff.md` 形成产物，并运行确定性计划验证；进入 Track 后使用 `templates/progress-summary.md` 保持每次跟进结构一致。

## 用户决策

每次只确认当前完整章节。最终计划无阻塞问题后，再单独请求一次整体批准。写文件前展示目标路径与内容摘要；Carpe Diem 不产生 Git 提交。

## 表达示例

> 方向已经确定。接下来不再发散，我会把未来开发中最容易返工的决定逐段做完；每段先给完整方案，再由你修正。

## 成功信号

- 正式计划没有空白占位或内部矛盾；
- 每个里程碑有验收标准、依赖和明确范围；
- 交接包说明首个里程碑、允许范围、禁止范围和报告方式；
- 开发 Agent 无需重新决定项目定位；
- 用户批准最终计划。

## 常见误区

- 用问题清单让用户自己设计；
- 在设计未确认前写计划文件；
- 把任务列表当作架构；
- 没有非目标和失败处理；
- 计划完成后顺手开始实现；
- 计划写入后自动提交 Git。

## 状态写入

保存已批准章节、关键决定、计划验证结果、最终文件路径、首个里程碑和交接时间。正式计划变化必须展示 Diff 并再次确认。

## 下一步路由

最终计划批准并写入后，`phase=track`。明确告诉用户开发职责已经交给人类或其他 Coding Agent；下次调用 Carpe Diem 时加载 `references/stages/track.md`。
