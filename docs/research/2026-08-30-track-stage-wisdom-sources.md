## 核心发现

1. **Track 阶段的核心矛盾不是"进度慢"，而是"进度不可知"**。现有 Carpe Diem Track 阶段已经设计了"有证据完成/声称完成/未完成/无法判断"四类状态，但缺少的是：**流动可视化**（Kanban 的 WIP 限制和队列可视化）、**约束识别**（Theory of Constraints 的瓶颈定位）、**指标驱动**（Accelerate 的四个关键指标）、**反馈闭环**（XP 的持续集成和真实用户反馈）。

2. **Track 阶段最需要的不是"更多度量"，而是"更有信号意义的度量"**。Nicole Forsgren 的研究表明，吞吐量（部署频率、前置时间）和稳定性（恢复时间、变更失败率）四个指标比"代码行数"或"任务完成数"更有预测力。Carpe Diem 的 Track 阶段应优先采集这些信号。

3. **项目案例的追踪机制比人物的抽象理论更适合直接蒸馏**。Kubernetes 的 KEP 状态机、Rust 的铁路模型（edition + stability）、Mozilla 的发布火车——这些是运行多年的实际追踪系统，有明确的状态转换规则和成功/失败模式。

## 人物研究

### 1. Gene Kim — The Phoenix Project / DevOps Handbook

**核心著作**：
- *The Phoenix Project: A Novel About IT, DevOps, and Helping Your Business Win*（IT Revolution Press, 2013）
- *The DevOps Handbook*（IT Revolution Press, 2016）
- *The Unicorn Project*（IT Revolution Press, 2019）

**核心智慧**：

| 概念 | 说明 | 对 Carpe Diem Track 阶段的价值 |
|------|------|-------------------------------|
| **Three Ways（三大原则）** | 流动（Flow）→ 反馈（Feedback）→ 持续学习（Continuous Learning） | Track 阶段应遵循"采集流动证据→收集反馈→沉淀学习"的循环，而不是单向汇报 |
| **Value Stream Mapping（价值流图）** | 绘制从想法到交付的完整流程，识别等待时间和浪费 | Track 阶段可以生成"计划→实施→验证→反馈"的价值流图，识别瓶颈环节 |
| **Deployment Pipeline（部署管道）** | 将代码从提交到生产的自动化管道 | Track 阶段应检查"CI 管道是否通过"作为客观证据，而非仅依赖文件存在 |
| **Improvement Kata（改善套路）** | 持续改进的标准化方法：目标→现状→瓶颈→下一步 | Track 阶段的"发现偏差→给出建议"可以借鉴改善套路的结构 |
| **Unicorn Project 的"五大理念"** | 自治、聚焦、流动、创新、质量 | 对 Track 阶段的"不越界开发"和"不监督式催促"原则的支持 |

**对 Carpe Diem Track 阶段的启发**：

1. **价值流图作为偏差诊断工具**：当 Track 发现进度偏差时，不是简单报告"慢了"，而是生成价值流图，指出"哪个环节拖延了"——是规划阶段的问题？开发阶段的问题？还是测试/验证阶段的问题？
2. **部署管道作为证据源**：除了 Git 提交和文件存在性，Track 阶段还可以读取 CI/CD 管道状态（如 GitHub Actions 的 passing/failing 状态），将其作为"有证据完成"的客观来源。
3. **改善套路的结构化建议**：Track 阶段的"给出建议"可以借鉴 Improvement Kata 的四步结构：`当前状态 → 目标状态 → 瓶颈分析 → 最可能的下一步`。

**可蒸馏规则**：
- Track 阶段识别进度偏差时，定位到"哪个环节"（规划/开发/测试/验证/部署）出了问题
- 读取 CI/CD 管道状态作为客观证据源
- 建议输出使用"当前状态 → 目标状态 → 瓶颈 → 下一步"结构

**不可泛化边界**：Gene Kim 的框架主要面向大型 IT 组织和 DevOps 转型，不适用于个人小型项目或非服务型项目；部署管道假设有 CI/CD 基础设施，没有 CI/CD 的项目需要调整证据来源。

### 2. Nicole Forsgren — Accelerate

**核心著作**：
- *Accelerate: The Science of Lean Software and DevOps*（IT Revolution Press, 2018）
- 基于 State of DevOps Report 系列研究（2014-2019）

**核心智慧**：

| 概念 | 说明 | 对 Carpe Diem Track 阶段的价值 |
|------|------|-------------------------------|
| **Four Key Metrics（四个关键指标）** | 部署频率、变更前置时间、变更失败率、服务恢复时间 | Track 阶段最核心的量化指标框架 |
| **ELITE / HIGH / MEDIUM / LOW 分级** | 基于四个指标将团队分为精英/高/中/低绩效 | Track 阶段可以设定"项目健康度"分级 |
| **Westrum 组织文化模型** | 病态型→官僚型→生成型组织文化，影响软件交付绩效 | Track 阶段识别"文化偏差"——如"隐藏问题"的倾向 |
| **Lean Product Development** | 小批量、短周期、快速反馈 | 支持 Carpe Diem 的"先做核心功能"和"逐章确认"策略 |
| **可预测性指标** | 不是"更快"，而是"可预测的交付速度" | Track 阶段应关注"计划 vs 实际"的偏差模式，而非速度本身 |

**对 Carpe Diem Track 阶段的启发**：

1. **四个关键指标适配到 Track 阶段**：
   - **部署频率**（或合并频率）：项目团队的代码合并频率
   - **变更前置时间**：从计划到可验证证据的时间
   - **变更失败率**：已完成的里程碑中，出现回归问题的比例
   - **恢复时间**：从发现偏差到纠正的时间
   
   但 Carpe Diem 是只读 Track，不修改工作区，所以"变更失败率"和"恢复时间"只能通过观察 CI 状态和 Git 历史来推断。

2. **可预测性 > 速度**：Track 阶段的核心不是判断"项目快不快"，而是判断"项目是否在按预期节奏推进"。如果计划预测 2 周完成一个里程碑，实际用了 2 周，这是好的。如果实际用了 1 周，但并不比"用了 3 周"更好——关键是偏差模式的识别。

3. **区分"证据等级"**：Accelerate 的研究表明，基于自我报告的数据（如"声称完成"）失真率很高。Track 阶段的"有证据完成"应优先使用自动化证据（CI 通过、测试覆盖、Git 合并），而非文件存在性。

**可蒸馏规则**：
- Track 阶段采集"部署频率/合并频率"和"变更前置时间"作为量化指标
- 关注"计划 vs 实际"的偏差模式，而非绝对速度
- 证据等级优先：自动化证据 > 客观证据（文件存在） > 声称完成

**不可泛化边界**：Accelerate 的四个指标是为服务型组织设计的，不适用于一次性交付或库/工具项目；ELITE 分级标准基于大型组织统计，不代表个人项目健康度；State of DevOps Report 数据可能存在幸存者偏差（只收集了愿意分享数据的组织）。

### 3. David J. Anderson — Kanban

**核心著作**：
- *Kanban: Successful Evolutionary Change for Your Technology Business*（Blue Hole Press, 2010）
- *Essential Kanban Condensed*（Lean Kanban University Press, 2016）

**核心智慧**：

| 概念 | 说明 | 对 Carpe Diem Track 阶段的价值 |
|------|------|-------------------------------|
| **Visualize Workflow（可视化工作流）** | 将工作流程显式化，让阻塞和瓶颈可见 | Track 阶段的"进度报告"应可视化——不仅报告"完成了什么"，也报告"正在做什么"和"卡在什么" |
| **WIP Limit（在制品限制）** | 限制同时进行的工作数量，防止多任务导致的吞吐量下降 | Track 阶段可以检测"在制品过多"——同一时间在多个里程碑上推进，但一个都没完成 |
| **Manage Flow（管理流动）** | 关注吞吐量和前置时间，而非资源利用率 | Track 阶段应关注"里程碑完成率"，而非"开发 Agent 是否忙碌" |
| **Make Policies Explicit（显式策略）** | 将工作规则显式化，让决策可追溯 | Track 阶段应检查"是否遵循了 Plan 阶段制定的规则" |
| **Feedback Loops（反馈回路）** | 每日站会、回顾会议、服务交付审查 | Track 阶段的"下一阶段建议"应包含反馈回路 |
| **Cumulative Flow Diagram（累积流图）** | 显示各阶段工作数量的堆积图，识别瓶颈 | Track 阶段可以生成简化的"累积里程碑图"——显示"已规划/进行中/已完成"随时间的变化 |

**对 Carpe Diem Track 阶段的启发**：

1. **WIP 限制检测**：Carpe Diem 的 Track 阶段可以检测"在制品数量"——如果同时在推进多个里程碑，但都没有完成，这可能表明"缺乏聚焦"。Track 报告应指出"当前在制品过多"并建议减少聚焦范围。
2. **累积流图代替"进度百分比"**：与其报告"80% 完成"这种主观判断，不如生成累积流图——显示"已规划→进行中→已验证完成"三个状态随时间的推移。这符合 Carpe Diem 的"不引入主观百分比"原则。
3. **前置时间作为进度指标**：记录从"里程碑开始"到"有证据证明完成"的时间，作为流动效率的指标。如果前置时间持续增长，说明系统存在问题。

**可蒸馏规则**：
- Track 报告包含"在制品数量"检测——是否在同时推进太多里程碑
- 用"状态分布"替代"完成百分比"：已规划 / 进行中 / 已验证完成
- 记录"里程碑前置时间"作为流动效率指标

**不可泛化边界**：Kanban 假设工作流是连续的、可分割的，不适用于高度耦合的单一交付；物理看板的精神需要适应电子化环境；部分 Kanban 实践（如服务等级协议）不适合 Carpe Diem 的"只读不干预"原则。

### 4. Eliyahu Goldratt — The Goal / Theory of Constraints

**核心著作**：
- *The Goal: A Process of Ongoing Improvement*（North River Press, 1984 / 3rd Revised Edition 2004）
- *Critical Chain*（North River Press, 1997）

**核心智慧**：

| 概念 | 说明 | 对 Carpe Diem Track 阶段的价值 |
|------|------|-------------------------------|
| **Theory of Constraints（TOC，约束理论）** | 任何系统的吞吐量受其最薄弱环节限制 | Track 阶段应识别"当前项目的最慢环节"，而不是平均报告所有环节 |
| **Five Focusing Steps（五步聚焦法）** | 识别约束→利用约束→服从约束→提升约束→重复 | Track 阶段的"诊断→建议"结构可以直接借鉴五步法 |
| **Drum-Buffer-Rope（鼓-缓冲-绳子）** | 用约束环节的节奏驱动整个系统 | 里程碑的计划节奏应由"最慢的环节"决定 |
| **Throughput Accounting（产出会计）** | 关注吞吐量（产出速率）而非成本或效率 | Track 阶段应关注"里程碑完成率"而非"开发 Agent 的工作量" |
| **Critical Chain Project Management（关键链项目管理）** | 考虑资源约束和不确定性，而不是只考虑任务依赖 | Plan 阶段的里程碑估计应考虑资源约束 |

**对 Carpe Diem Track 阶段的启发**：

1. **五步聚焦法作为偏差诊断框架**：当 Track 阶段发现进度偏差时，按五步法诊断：
   - 识别约束：哪个环节最慢？（架构设计？编码？测试？验收？）
   - 利用约束：这个环节是否在全力工作？
   - 服从约束：其他环节是否在等待这个环节？
   - 提升约束：如何提升这个环节的能力？
   - 重复：约束转移后，重新识别

2. **鼓-缓冲-绳子模型**：Track 阶段应识别项目的"鼓点节奏"——什么环节决定了整个项目的节奏。其他里程碑的进度应以这个节奏为参照。

3. **Plan 阶段的里程碑估计应包含缓冲**：Goldratt 的 Critical Chain 指出，任务估计中的人为"安全时间"往往被浪费（学生综合征、帕金森定律）。更好的做法是：将每个任务的估计时间缩短，但设置一个统一的"项目缓冲"。

**可蒸馏规则**：
- Track 阶段偏差诊断使用五步聚焦法：识别约束→利用→服从→提升→重复
- 识别项目的"鼓点节奏"——最慢环节决定整体节奏
- 里程碑建议包含"约束识别"——当前的最大瓶颈是什么

**不可泛化边界**：TOC 最初是为制造业设计的（工厂车间、物理生产线），软件开发的约束往往是认知约束（知识的获取、决策的明确）而非物理约束，识别方式不同；Critical Chain 需要精确的任务估计，这对 Carpe Diem 的"只读不干预"原则有挑战；五步法假设团队有能力"提升约束"，但 Carpe Diem 的 Track 只给出建议，不执行改进。

### 5. Kent Beck — XP / TDD

**核心著作**：
- *Extreme Programming Explained: Embrace Change*（Addison-Wesley, 1st Edition 1999 / 2nd Edition 2004）
- *Test-Driven Development: By Example*（Addison-Wesley, 2002）

**核心智慧**：

| 概念 | 说明 | 对 Carpe Diem Track 阶段的价值 |
|------|------|-------------------------------|
| **Continuous Integration（持续集成）** | 每天多次集成代码，每次集成都通过自动化测试 | Track 阶段应检查"集成频率"——如果长时间无集成，项目可能偏离轨道 |
| **Test-Driven Development（测试驱动开发）** | 先写测试再写代码，测试既是设计工具也是验证工具 | Track 阶段应检查"测试是否先于代码存在"——这是"有证据完成"的强信号 |
| **Pair Programming（结对编程）** | 两人一起编码，一人写代码一人审查 | 对 Carpe Diem 的启发：Track 阶段可以检查"代码审查是否已完成" |
| **Whole Team（全团队）** | 所有角色在同一个房间工作 | 对应 Carpe Diem 的"用户参与决策"原则 |
| **Informative Workspace（信息化工作空间）** | 工作空间应展示所有关键信息 | Track 报告本身就是"信息化工作空间"的数字版本 |
| **Small Releases（小发布）** | 频繁发布小版本，每次发布都有价值 | 支持 Carpe Diem 的"里程碑粒度"控制 |
| **Sustainable Pace（可持续节奏）** | 每周 40 小时，不加班 | Track 阶段可以检测"提交时间分布"——是否在深夜或周末有大量提交（可能表明节奏失控） |

**对 Carpe Diem Track 阶段的启发**：

1. **TDD 作为"有证据完成"的强信号**：如果项目遵循 TDD，Track 阶段可以检查"测试是否先于代码存在"——这是最可靠的"有证据完成"信号。Git 提交时间戳可以显示测试和代码的先后顺序。
2. **集成频率作为健康指标**：Track 阶段可以报告"最近一次的集成时间"——如果长时间没有集成（例如超过 1 周），说明项目可能处于"危险区"。
3. **可持续节奏检测**：通过分析 Git 提交的时间分布，Track 阶段可以检测"深夜提交"或"周末大量提交"的模式，这可能表明节奏失控或计划不合理。

**可蒸馏规则**：
- Track 阶段检查"集成频率"——最近一次集成距今时间
- 可选的"TDD 合规性检查"——测试提交是否先于代码提交
- 检测"深夜/周末提交"模式作为节奏失控的信号

**不可泛化边界**：XP 的实践（结对编程、全团队、客户现场）适用于小型、自组织团队，不适用于个人项目或分布式团队；TDD 不是所有项目的默认选择，一些项目（如原型、探索性工作）可能不适合 TDD；可持续节奏假设"避免加班"是项目优化目标，但 Carpe Diem 不应替用户判断什么节奏是"可持续"的。

### 6. Ryan Singer — Shape Up Hill Chart（补充）

*已在 Plan 阶段研究中详细分析，此处仅摘录与 Track 阶段最相关的部分。*

**核心智慧**：Hill Chart 将进度分为"上坡"（仍不确定怎么做）和"下坡"（知道怎么做，在执行）。

**对 Carpe Diem Track 阶段的启发**：
- 将现有"有证据完成/声称完成/未完成/无法判断"四类状态，扩展为"确定性等级"：上坡、下坡、已完成
- 报告"哪些进入下坡"而非"完成了多少任务"
- 如果里程碑长期停留在"上坡"状态，说明不确定性问题未被解决

## 项目案例研究

### 1. GitLab — OKR + 里程碑追踪

**核心机制**：

| 环节 | 说明 | 可蒸馏的机制 |
|------|------|-------------|
| **OKR 分层** | 公司级 OKR → 部门级 OKR → 个人级 OKR，逐层对齐 | Track 阶段可以展示"项目目标 → 里程碑 → 任务"的对齐链 |
| **里程碑（Milestones）** | 基于时间的分组，包含 Issues 和 Merge Requests | Carpe Diem 已有的里程碑机制，可强化时间和范围绑定 |
| **权重（Weight）** | 每个 Issue 有权重，反映工作量 | 里程碑的"工作量估计"参考 |
| **燃尽图（Burnup/Burndown）** | 每天自动更新，显示已完成 vs 剩余的图表 | Track 阶段的进度可视化参考 |
| **发布自动化** | 里程碑末尾自动创建发布版本 | 里程碑完成的自动化证据 |
| **价值流分析** | 从 Issue 创建到部署的完整时间追踪 | 前置时间追踪 |

**对 Carpe Diem Track 阶段的启发**：

1. **OKR 对齐链**：Track 阶段应确保每个里程碑能回指到"项目目标"——如果里程碑完成但不能推进项目目标，说明计划有问题。
2. **燃尽/燃起图**：虽然 Carpe Diem 不引入主观百分比，但可以借鉴 GitLab 的"已完成 vs 计划"的对比——显示"计划中的里程碑完成数" vs "实际完成数"。
3. **自动发布标记**：里程碑完成时，Track 阶段可以生成"发布标记"——记录完成时间、证据、偏差。这对应 Carpe Diem 的"状态写入"机制。

**可蒸馏规则**：
- Track 报告展示"里程碑 → 目标"的对齐链，确保每项工作都可回指目标
- 里程碑完成时生成"发布标记"，包含完成时间、证据引用、偏差记录
- 使用"计划完成数 vs 实际完成数"的对比，而非主观百分比

**不可泛化边界**：GitLab 的 OKR 机制是面向大型组织（数千人）设计的，个人项目不需要多层 OKR 对齐；权重系统需要长期校准，不适合一次性项目。

### 2. Kubernetes — KEP 追踪

**核心机制**：

| 环节 | 说明 | 可蒸馏的机制 |
|------|------|-------------|
| **KEP（Kubernetes Enhancement Proposal）** | 标准化提案格式，包含摘要、动机、设计、测试计划、毕业标准 | 比 ADR 更完整的追踪文档——从提出到毕业的全生命周期 |
| **KEP 状态机** | Provisional → Implementable → Implemented → Graduated → Stable | 清晰的状态转换路径，每个状态有明确的进入条件 |
| **KEP 追踪文件** | 每个 KEP 有独立的追踪文件，记录状态变化 | 每个里程碑或 ADR 的"状态追踪"文件 |
| **SIG 审查** | 专门的 SIG（Special Interest Group）审查和批准 | 里程碑的"审查关口" |
| **Stage 概念** | Alpha → Beta → GA -> Stable，每个阶段有不同承诺级别 | 里程碑的"成熟度"分级 |
| **KEP 模板中的"Graduation Criteria"** | 明确列出从当前状态到下一个状态的毕业条件 | 里程碑的"验收标准"——明确"什么算完成" |

**对 Carpe Diem Track 阶段的启发**：

1. **KEP 状态机作为里程碑状态模型**：Carpe Diem 的 Track 阶段可以将每个里程碑的状态定义为类似 KEP 的状态机：
   - `Proposed`：已提出，但未开始实施
   - `In Progress`：正在实施
   - `Implemented`：代码已提交，但未验证
   - `Verified`：有证据证明完成（测试通过、CI 通过）
   - `Accepted`：用户确认完成
   - `Stale`：长期未推进，需要重新评估

2. **毕业条件（Graduation Criteria）**：每个里程碑应有明确的"毕业条件"——从"实施中"到"已完成"的转换条件。这对应 Carpe Diem 的"验收标准"。

3. **Stale 状态检测**：KEP 有"stale"机制——如果长时间没有进展，自动标记为 stale。Track 阶段可以检测"长期未推进的里程碑"，建议重新评估。

**可蒸馏规则**：
- 里程碑状态模型：Proposed → In Progress → Implemented → Verified → Accepted → Stale
- 每个状态转换有明确的"毕业条件"（验收标准）
- 检测"长期未推进的里程碑"，标记为 stale 并建议重新评估

**不可泛化边界**：KEP 流程是为 Kubernetes 这种大型、多贡献者的开源项目设计的，个人项目不需要这么正式的状态机；KEP 的提案和审查流程可能过于正式，不适合小规模快速迭代。

### 3. Mozilla — Firefox 发布跟踪

**核心机制**：

| 环节 | 说明 | 可蒸馏的机制 |
|------|------|-------------|
| **Release Train（发布火车）** | 固定时间发布（Firefox 每 6-8 周发布一个版本），不等待特性 | 里程碑的固定时间约束——"到点开车，不等迟到的乘客" |
| **Nightly → Aurora → Beta → Release** | 四级渠道，代码逐级提升，每级有稳定性门槛 | 里程碑的"成熟度提升"通道 |
| **Feature Tracking（功能追踪）** | 每个功能在 Bugzilla 中标记其目标版本和当前状态 | 功能级别的追踪 |
| **Go/No-Go 决策** | 每次发布前做 Go/No-Go 决策，决定是否如期发布 | 里程碑的"放行/不放行"决策点 |
| **Release Notes 自动化** | 自动生成发布说明，记录每个版本的变更 | 里程碑完成时的"变更摘要" |
| **质量门禁（Quality Gate）** | 每个版本有明确的通过条件（测试通过率、崩溃率等） | 里程碑的"验收标准" |

**对 Carpe Diem Track 阶段的启发**：

1. **发布火车模型**：最核心的启示——"到点开车，不等迟到的特性"。如果某个里程碑不能在计划时间内完成，默认操作是"推迟该特性到下一个里程碑"，而不是"延长当前里程碑"。
2. **渠道提升模型**：代码改动的"成熟度"应按渠道提升：`开发 → 验证 → 验收 → 发布`。每个渠道有明确的门槛，达到门槛才能提升。这比"文件存在即完成"更可靠。
3. **Go/No-Go 决策点**：每个里程碑末尾应有明确的 Go/No-Go 决策——是"按计划推进到下一个里程碑"还是"暂停并重新评估"。这对应 Carpe Diem 的"用户决策"机制。

**可蒸馏规则**：
- 里程碑采用"发布火车"模型：固定时间，不等迟到的特性
- 变更按渠道提升：开发 → 验证 → 验收 → 发布，每个渠道有门槛
- 里程碑末尾设置 Go/No-Go 决策点

**不可泛化边界**：Mozilla 的发布火车是针对 Firefox 这种大规模、多平台、多语言的复杂产品设计的，个人项目不需要四层渠道；发布火车的固定节奏可能不适合需要快速迭代的早期项目。

### 4. Rust — 铁路模型与版本承诺

**核心机制**：

| 环节 | 说明 | 可蒸馏的机制 |
|------|------|-------------|
| **Edition（版本）** | 每三年发布一个 Edition（2015、2018、2021、2024），作为"版本快照" | 项目的"版本里程碑"设计 |
| **Stability Promise（稳定性承诺）** | 一旦稳定，永不破坏向后兼容 | Track 阶段的"不退化"检查 |
| **Train Model（火车模型）** | 每六周发布一个稳定版本 | 频繁的小版本发布节奏 |
| **RFC 追踪** | 每个 RFC 有明确的追踪状态：Proposed → Approved → Implemented → Stabilized | 完整的功能追踪生命周期 |
| **Feature Gates（特性门控）** | 新功能默认隐藏，通过特性标记启用 | 里程碑的"渐进式暴露" |
| **Stabilization Period（稳定化周期）** | 功能在稳定之前有一个"稳定化"阶段，只做 bug 修复和优化 | 里程碑的"稳定化"阶段 |

**对 Carpe Diem Track 阶段的启发**：

1. **Edition 机制**：项目可以定义一个"版本边界"——在当前版本中，优先保证稳定性和向后兼容；新功能留到下一个版本。这防止"第二系统效应"（Brooks）和"范围蔓延"。
2. **稳定性承诺**：Track 阶段应检查"是否有破坏向后兼容的变更"。如果项目有用户，向后兼容是核心承诺。
3. **Feature Gates**：对于阶段性交付的项目，新功能可以默认隐藏，到用户确认后再启用。这样"代码完成"和"功能可用"可以分离。

**可蒸馏规则**：
- 项目定义"版本边界"，当前版本优先保证稳定性和兼容性
- Track 阶段检测"是否引入了破坏向后兼容的变更"
- 新功能可通过"特性门控"分离"代码完成"和"功能可用"

**不可泛化边界**：Rust 的稳定性承诺和 Edition 机制是为编程语言设计的（语言稳定性是核心价值），不适用于短期原型或一次性项目；Feature Gates 需要基础设施支持，不适合简单项目。

### 5. Basecamp — 复盘 / Heartbeat

**核心机制**：

| 环节 | 说明 | 可蒸馏的机制 |
|------|------|-------------|
| **Heartbeat（心跳）** | 每个周期末尾的简短回顾，记录"什么做得好、什么做得不好、下次改进什么" | Track 阶段的"复盘"环节 |
| **Cool-Down（冷却期）** | 每个周期后有 2 周缓冲期，用于修复 bug、探索、学习 | 里程碑之间的"缓冲期" |
| **Betting Table（投注桌）** | 下一个周期开始时的决策会议 | 从 Track 到下一个 Plan 的过渡 |
| **No Backlog** | 不维护待办列表，每个周期重新选择 | 防止"计划膨胀" |
| **Pitch 回顾** | 回顾上一个周期的 pitch 提案，检查假设是否正确 | 对 Plan 阶段假设的验证 |

**对 Carpe Diem Track 阶段的启发**：

1. **Heartbeat 复盘的结构**：Track 阶段在里程碑结束时，可以输出"心跳报告"——记录：
   - 这个里程碑完成/未完成的内容
   - 与计划的主要偏差
   - 学到的经验
   - 下一个里程碑的建议

2. **Cool-Down 机制**：每个里程碑之间安排一段"缓冲期"——不做新功能，只做修复和优化。这对应 Carpe Diem 的"暂停/调整"路由。

3. **No Backlog 原则**：Track 阶段不应维护一个"待办列表"并报告"完成了 80% 的待办事项"。相反，Track 应该关注"当前里程碑完成的内容"和"下一个里程碑最值得做的事"。

**可蒸馏规则**：
- 里程碑结束时输出"心跳报告"：完成内容 / 偏差 / 经验 / 下一步建议
- 里程碑之间安排缓冲期
- 不维护"待办列表完成率"，只关注"当前里程碑完成内容"

**不可泛化边界**：Basecamp 的复盘机制假设团队在同一个周期内工作，不适用于异步开发的个人项目；Cool-Down 期是 Basecamp 的特定组织实践，不是通用规则。

| **P2** | Rust — 版本承诺 | 兼容性检查卡 | 检测是否破坏向后兼容 |

### 核心操作序列

基于以上智慧蒸馏，Track 阶段的核心操作序列建议为：

```
1. 读取现有证据（Git/测试/CI/Issue）—— 保持现有设计

2. 为每个里程碑评定确定性等级（Hill Chart）：
   - 上坡：仍有关键未知，进度不可信
   - 下坡：知道怎么做，进度可信
   - 已完成：有证据证明完成

3. 检测在制品数量（Kanban WIP）：
   - 当前有多少里程碑在"进行中"状态
   - 如果 > 3，建议减少聚焦范围

4. 识别约束环节（Theory of Constraints）：
   - 哪个环节最慢？（规划/架构/编码/测试/验收）
   - 这个环节是否是"鼓点节奏"？

5. 采集量化指标（Accelerate）：
   - 合并频率：最近 N 天的合并次数
   - 前置时间：从里程碑开始到完成的时间
   - 变更失败率：已完成里程碑中出问题的比例
   - 恢复时间：从发现偏差到纠正的时间

6. 检查里程碑状态（KEP 状态机）：
   - 每个里程碑的状态：Proposed / In Progress / Implemented / Verified / Accepted / Stale
   - 检测长期未推进的里程碑，标记为 Stale

7. 检查集成频率（XP）：
   - 最近一次集成距今多长时间
   - 如果超过 1 周，标记为"低集成频率"

8. 生成心跳报告（Basecamp Heartbeat）：
   - 完成内容
   - 与计划的偏差
   - 学到的经验
   - 下一个里程碑建议

9. 输出下一阶段建议
   - 继续 / 调整 / 暂停 / 结束
   - 包含"约束识别"和"下一步最值得做的事"
```

### 与现有 Track 阶段的兼容性

上述建议不改变 Carpe Diem Track 阶段的现有设计框架，而是补充。

| 现有设计 | 补充建议 | 兼容性 |
|---------|---------|--------|
| "有证据完成/声称完成/未完成/无法判断" | 增加"确定性等级"：上坡/下坡 | 可叠加——先确定"上坡/下坡"，再细分"有证据/声称" |
| "识别范围偏移、阻塞和新的关键决定" | 增加"约束识别"和"在制品检测" | 作为"识别范围偏移"的子步骤 |
| "给出继续、调整、暂停或结束的建议" | 增加"心跳报告"结构 | 作为"建议"的标准化格式 |
| "生成下一阶段开发交接建议" | 增加"OKR 对齐链"和"约束识别" | 作为"交接建议"的补充信息 |
| 不修改工作区 | 增加"只读采集CI状态" | 兼容——CI 状态是只读信息 |

## 综合推荐行动卡

### 卡1：确定性分级卡（Track 阶段）
```
触发条件：Track 阶段报告进度
来源：Ryan Singer — Hill Chart / Shape Up
动作：
  1. 对每个里程碑/任务，评定"确定性等级"
  2. 上坡 = 仍有关键未知，进度不可信（"还在弄清怎么做"）
  3. 下坡 = 知道怎么做，进度可信（"知道具体怎么做"）
  4. 已完成 = 有证据证明完成
  5. 报告"哪些进入下坡"而非"完成了多少任务"
停止条件：所有里程碑可报告确定性等级
输出：每个里程碑的确定性等级 + 上坡中的最大未知
不可泛化：不确定性是主观判断，应以客观证据为准
```

### 卡2：在制品检测卡（Track 阶段）
```
触发条件：Track 阶段报告进度，发现有多个里程碑同时推进
来源：David J. Anderson — Kanban
动作：
  1. 统计当前"进行中"的里程碑数量
  2. 如果 > 3，标记为"高在制品"
  3. 报告"同时推进 N 个里程碑，但可能没有一个先完成"
  4. 建议减少聚焦范围
停止条件：在制品数量 ≤ 3
输出：在制品数量 + 建议
不可泛化：WIP 限制的阈值因项目而异，3 是参考值不是固定值
```

### 卡3：约束诊断卡（Track 阶段）
```
触发条件：Track 阶段发现进度偏差（里程碑未按计划推进）
来源：Eliyahu Goldratt — Theory of Constraints
动作：
  1. 识别约束：哪个环节最慢？（规划/架构/编码/测试/验收/等待用户确认）
  2. 利用约束：这个环节是否在全力工作？是否有等待？
  3. 服从约束：其他环节是否在等待这个环节？
  4. 提升约束：如何提升这个环节的能力？（给出建议）
  5. 重复：约束转移后，重新识别
停止条件：当前约束已被识别，有明确的下一步建议
输出：当前约束环节 + 建议
不可泛化：软件开发中的约束往往是认知约束，识别难度高于物理约束
```

### 卡4：量化指标卡（Track 阶段）
```
触发条件：Track 阶段采集证据
来源：Nicole Forsgren — Accelerate
动作：
  1. 采集合并频率：最近 7 天的合并/提交次数
  2. 采集前置时间：从里程碑开始到完成的时间
  3. 采集变更失败率：已完成里程碑中出现回归问题的比例
  4. 采集恢复时间：从发现偏差到纠正的时间
  5. 报告"计划 vs 实际"的偏差模式
停止条件：有 2 次以上的数据点可做趋势分析
输出：四个量化指标 + 偏差模式
不可泛化：四个指标是为服务型组织设计的，库/工具项目需要调整
```

### 卡5：里程碑状态卡（Track 阶段）
```
触发条件：Track 阶段检查里程碑状态
来源：Kubernetes — KEP 状态机
动作：
  1. 检查每个里程碑的状态：
     - Proposed：已提出，未开始
     - In Progress：正在实施
     - Implemented：代码已提交，但未验证
     - Verified：有证据证明完成（测试通过、CI 通过）
     - Accepted：用户确认完成
     - Stale：长期未推进
  2. 检测长期未推进的里程碑（> 2 周无进展），标记为 Stale
  3. 检查状态转换是否有"毕业条件"（验收标准）
停止条件：所有里程碑可报告状态
输出：每个里程碑的当前状态 + Stale 检测结果
不可泛化：状态机适用于正式项目，快速原型不需要这么复杂的模型
```

### 卡6：心跳报告卡（Track 阶段）
```
触发条件：里程碑结束时
来源：Basecamp — Heartbeat / 复盘
动作：
  1. 记录这个里程碑完成的内容
  2. 记录与计划的主要偏差
  3. 记录学到的经验（什么做得好、什么做得不好）
  4. 给出下一个里程碑的建议
输出格式：
  ```
  ## 心跳报告：里程碑 {名称}
  - 状态：已完成 / 部分完成 / 未完成
  - 完成内容：{有证据证明完成的内容}
  - 偏差：{与计划不符的内容}
  - 经验：{学到的经验}
  - 下一步建议：{继续/调整/暂停/结束}
  ```
停止条件：报告已生成，偏差已记录
不可泛化：心跳报告不替代正式的项目计划，只作为 Track 阶段的输出
```

### 卡7：发布火车卡（Track 阶段）
```
触发条件：Track 阶段发现里程碑超期
来源：Mozilla — Release Train
动作：
  1. 检查里程碑是否超出计划时间
  2. 如果超期，建议：推迟未完成的功能到下一个里程碑，而不是延长当前里程碑
  3. 生成 Go/No-Go 决策建议：是否按计划推进到下一个里程碑
输出：超期检测结果 + Go/No-Go 建议
不可泛化：发布火车适用于有固定发布节奏的项目，不适用于探索性项目
```

## 研究结论

1. **Track 阶段最优先蒸馏的三大智慧**：Hill Chart 的确定性分级（让"到底做完了吗"更诚实）、Kanban 的 WIP 限制（防止同时推进太多任务）、Theory of Constraints 的约束识别（找到真正的瓶颈在哪里）。

2. **Accelerate 的四个关键指标可以作为 Track 阶段的量化框架**，但需要适配到只读场景——合并频率替代部署频率，前置时间从 Git 历史推算，变更失败率从 CI 状态推断，恢复时间从"发现偏差到纠正"的 Git 间隔计算。

3. **KEP 状态机是里程碑追踪的最佳参照**。它提供了从提出到完成的全生命周期状态模型，每个状态有明确的转换条件，比简单的"已完成/未完成"更有诊断价值。

4. **项目案例的追踪机制比人物的抽象理论更适合直接蒸馏**。Kubernetes 的 KEP 状态机、Mozilla 的发布火车、Rust 的铁路模型——这些是运行多年的工程实践，有明确的机制和结果。

5. **与现有 Carpe Diem Track 阶段完全兼容**。上述建议不改变现有设计框架，而是在现有"四类状态"、"范围偏移识别"、"建议"结构上叠加补充层。

6. **与 Plan 阶段研究一致**。本研究与[Plan 阶段研究](2026-08-30-plan-stage-wisdom-sources.md)的 Track 部分（Hill Chart 不确定性分级、不把任务完成数当进度）一致，并在此基础上补充了 Kanban、TOC、Accelerate 等 Track 阶段特有的智慧来源。
