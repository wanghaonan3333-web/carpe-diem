# 行为卡：API 契约设计

> 触发信号：Plan 阶段开始定义跨组件或外部调用契约
> 证据编号：WD-P9-01

## 问题本质

API 是调用者与实现之间的变更边界。重点不是从第一天套用某种 URL 版本号，而是让契约可理解、可验证，并在出现兼容性边界时有明确的变更策略。

## 触发条件

- 团队从数据库结构直接生成外部接口；
- 调用者无法仅凭契约判断正确用法和错误处理；
- 已有消费者，却没有兼容性、弃用或迁移约定；
- 协议选择压过了用户任务和契约语义。

## 行为指导

1. **从调用任务开始**：列出调用者要完成的动作、所需上下文和失败后如何恢复，再定义资源、命令和字段。
2. **先写可评审契约**：用 OpenAPI、schema、类型或示例请求/响应评审命名、错误、分页、幂等和权限边界，再实现。
3. **保持概念一致**：相同概念使用相同命名、错误结构和生命周期；不要让内部表字段泄漏成外部语义。
4. **让危险动作显式**：安全默认值、明确枚举、权限校验和可操作错误，避免魔法参数和静默破坏。
5. **为变更建立控制策略**：从第一个消费者起记录兼容承诺。只有存在独立升级节奏、第三方消费者或破坏性变更时，才选择显式版本化；内部同部署单元可用同步迁移。
6. **提供迁移证据**：破坏性变更需说明受影响消费者、兼容窗口、迁移步骤、验证和回滚方式。

## 不适用场景

- 一次性本地脚本无稳定调用者时，保持最小接口即可；
- Validate 原型只需足够支撑实验，不预建完整版本体系；
- 内部函数边界可借用契约原则，但不必照搬网络 API 治理；
- 安全和合规要求高于易用性时，先满足强制边界。
