# 行为卡：API 设计哲学

> 触发条件：Plan 阶段进入"架构、组件、数据流"章节，用户开始设计系统 API 接口

## 问题本质

API 是系统的公共接口——它是你与调用者（前端、其他服务、第三方开发者）之间的契约。好的 API 设计不会让使用者在文档和代码之间反复切换才能理解怎么用；坏的设计则让错误变得容易，让正确用法变得隐蔽。

大多数人在设计 API 时，习惯从"内部实现方便"的角度出发——"这个功能我后端好实现"、"这个数据结构我数据库里就有"。但问题是：**API 不属于你，它属于你的调用者**。调用者不关心你的数据库结构，也不关心你的内部实现，他们只关心"我想做这件事，API 能不能让我自然、简单地完成"。

问题的根源是：**你把"方便实现"当成了"好的设计"，但"好的 API"的标准是一个人在没有文档的情况下，看一眼就能猜对它怎么用**。如果调用者需要反复翻文档、查参数、试错才能用对，说明 API 设计有问题。

## 触发条件

用户正在执行以下任一操作时触发：
- Plan 阶段进入"架构"章节，开始设计系统 API 接口（REST、gRPC、GraphQL 等）
- 讨论中用户说"先实现功能，API 后面再统一"——这通常意味着 API 会在实现后被"拟合"到内部代码上，而非从调用者视角设计
- API 设计讨论集中在"用什么协议"（REST vs GraphQL vs gRPC）而非"调用者需要什么能力"
- 接口文档中只写了"参数和返回值"，没有描述"这个接口用来做什么"和"什么时候该用"

## 行为指导

### 1. 先设计 API 再实现——API 契约是架构的起点，不是实现后的副产品

不要在实现功能之后再去"梳理"API。API 应该在实现之前就被设计好，因为：

- **API 设计决定了系统的边界**：如果你先设计 API，你会被迫思考"系统对外提供什么能力"，而不是"系统内部有什么功能"。
- **API 是调用者的契约**：一旦定下来，修改的成本很高。先设计、评审、再实现，可以避免"代码写完了发现 API 很难用"的窘境。
- **API 设计需要时间思考**：在实现前，你可以自由地调整、重构、比较不同的设计方案。一旦开始编码，改 API 的成本就变成了"改代码 + 改测试 + 改文档"。

具体做法：在开始编写任何 API 代码之前，先用"接口定义"（如 OpenAPI 规范、Proto 文件、类型定义）描述 API 的输入和输出，然后让团队成员假装自己是调用者，看能不能正确使用。

### 2. 一致性比完美更重要——让你的 API 可预测，而非每个接口都"最优"

调用者使用 API 时，最大的认知负担不是"这个接口怎么用"，而是"这个系统和上一个接口的规则一样吗"。一致性是指：

- **命名风格一致**：如果某个操作用了 `create_` 前缀，所有创建操作都应该用 `create_`。不要一半用 `create_`，一半用 `new_`，还有一部分用 `add_`。
- **错误格式一致**：所有接口的错误返回格式应该完全相同。不要让调用者针对不同接口写不同的错误处理逻辑。
- **分页一致**：所有列表接口的分页方式、参数名、返回格式应该一致。
- **认证方式一致**：不要在不同接口使用不同的认证机制。

**一致性优先于"这个接口的命名更准确"**。一个"一致性但不完美"的 API，比一个"每个接口都最优但风格不一致"的 API 更容易使用。调用者不需要记忆不同接口的"特例"。

### 3. 好的 API 让正确用法显而易见——设计应引导调用者做正确的事

API 设计的一个重要原则是：**调用者应该凭直觉就能用对，而不是靠文档才能用对**。具体做法：

- **用类型系统约束错误用法**：如果某个参数只能是特定值，用枚举而非字符串。如果某个字段是必填的，不要设为可选让调用者猜。
- **默认值应该安全**：如果调用者没有提供某个参数，默认值应该是最安全的选择（而不是最方便的选择）。比如，删除接口的默认行为应该是"返回错误，要求明确确认"而非"直接删除"。
- **避免"魔法参数"**：不要出现"传 0 表示删除，传 1 表示归档，传 2 表示转移"这样的参数设计。应该用明确的枚举值或独立的接口。
- **错误信息应该指导修复**：当调用者传错参数时，返回的错误信息应该告诉他们"应该传什么"，而不是"你传错了"。

判断标准：找一个不了解这个系统的人，不给文档，只给 API 定义，看他能不能正确调用所有接口。如果他需要问问题，说明 API 设计不够直觉。

### 4. 为调用者设计而非为内部实现设计——API 是面向调用者的接口，不是面向数据库的视图

最常见的 API 设计错误是"把内部数据结构直接暴露为 API"。比如：数据库表有 `user_id`、`created_at`、`updated_at`、`is_deleted` 字段，API 就直接返回这些字段。

好的 API 设计应该从调用者的视角出发：
- **业务概念优先**：API 返回的数据应该对应"业务对象"，而不是"数据库记录"。如果调用者需要"用户信息 + 最近订单 + 通知数"，你应该提供一个接口返回这些聚合数据，而不是让调用者分别调用三个接口再自行组合。
- **隐藏内部实现细节**：调用者不需要知道你的数据是怎么存储的，也不需要知道 `is_deleted` 这样的实现字段。API 应该只暴露"调用者需要知道"的信息。
- **为常用场景设计便捷接口**：如果 80% 的调用者都需要"先查 A 再根据 A 的结果查 B"，你应该提供一个合并接口，而不是让每个调用者都自己实现这个流程。

### 5. 版本化从第一天开始——哪怕只有一个调用者，也要有版本管理

API 一旦被使用，修改就会破坏现有调用者。因此，版本管理不是"等 API 稳定了再说"的事，而是从第一个版本开始就要做的事。

- **在 URL 或请求头中标注版本**：如 `/v1/users`、`/v2/users`，或通过 `Accept: application/vnd.yourapp.v1+json` 请求头。
- **向后兼容是默认规则**：在同一个版本内，不能随意改字段名、改类型、改语义。如果要改，必须开新版本。
- **弃用策略要明确**：在 API 文档中标注弃用状态，并告知调用者过渡期（如"v1 在 2026-01-01 后不再支持"）。
- **版本之间的映射要简单**：不要试图让一个版本兼容所有历史版本。每个版本应该有清晰的边界，过期的版本应该被移除。

即使你只有前端一个调用者，版本化也值得做——它让你可以逐步升级前端，而不是"前端和后端必须同时改"。

### 6. 好的文档是 API 的一部分——文档不是"写完了再补"的东西

文档不是 API 的附属品，而是 API 的组成部分。一个没有文档的 API 等于一个不存在的 API。

- **文档与代码同源**：使用 OpenAPI 规范、gRPC 的 Proto 注释等工具，让文档从代码中自动生成。不要手动维护一份独立的文档——它一定会过时。
- **文档包含"为什么"和"什么时候"**：不只是写"这个参数是什么"，还要写"什么时候用这个接口"、"什么情况下用这个参数"、"有什么注意事项"。
- **提供可运行的示例**：在文档中给出"请求示例"和"响应示例"——最好是完整的、可直接复制的代码片段。
- **文档要包含错误说明**：列出所有可能的错误状态码和错误信息，以及调用者应该如何修复。

判断标准：如果一个新开发者加入团队，只看 API 文档就能独立完成一个特性的开发，说明文档合格了。

## 不适用场景

- **内部一次性脚本**：如果系统只是内部团队用的一次性迁移脚本、数据处理脚本，没有外部调用者，API 设计原则几乎不需要。一次性脚本用完即弃，不需要考虑版本化、一致性、文档化。
- **纯前端项目**：如果项目不涉及服务端 API（如纯静态页面、无后端的单页应用），API 设计哲学不适用。前端内部的模块间接口（函数调用、组件 Props）有自己的设计原则，但不需要版本化、文档化等 API 层面的管理。
- **原型验证阶段**：如果项目处于 Discover 或 Validate 阶段，目的是"快速验证想法是否可行"，API 设计是过度设计。原型的目的不是"设计完美的接口"，而是"尽快验证假设"。等原型验证通过，进入 Plan 阶段正式开发时，再应用 API 设计原则。
- **项目只有一个服务且只有一个调用者（前端）**：如果系统只有一个后端服务和一个前端调用者，且短期内不会扩展，API 设计可以简化。不需要完整的版本化策略，但基本的命名一致性和调用者视角设计仍然适用。等引入第二个调用者或第三方开发者时，再启用完整的 API 设计原则。
