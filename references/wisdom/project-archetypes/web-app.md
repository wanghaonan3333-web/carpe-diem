# 项目类型模板：Web 应用

> 适用于 Web 应用类项目（SaaS、面向用户的产品、后台管理系统、内容平台）
> 创建日期：2026-08-30

## 问题本质

Web 应用解决的是"让用户通过浏览器完成一个完整的工作流"——从访问、理解、操作到获得结果。用户的核心诉求不是技术架构，而是**能用、好用到离不开**。Web 应用与 CLI 工具的根本区别在于：用户不需要先有命令行使用能力，任何人都可以访问；但复杂度也大幅上升——需要处理身份认证、数据持久化、前端交互、部署运维、用户反馈循环等。

对于 Carpe Diem 用户来说，Web 应用是最常见的项目方向，但也是最容易低估复杂度的类型——MVP 的实际工作量往往是预估的 2-3 倍。

## 典型特征

### 目录结构

```
project-name/
├── frontend/                    # 前端
│   ├── src/
│   │   ├── app/                 # 页面路由和布局
│   │   ├── components/          # 可复用组件
│   │   ├── lib/                 # API 客户端、工具函数
│   │   └── styles/              # 全局样式
│   ├── public/
│   └── package.json
├── backend/                     # 后端
│   ├── src/
│   │   ├── routes/              # API 路由
│   │   ├── services/            # 业务逻辑
│   │   ├── models/              # 数据模型
│   │   ├── middleware/          # 中间件（认证、日志、限流）
│   │   └── db/                  # 数据库迁移和种子
│   ├── tests/
│   └── package.json / pyproject.toml
├── docs/
│   ├── architecture.md
│   ├── api.md
│   └── deployment.md
├── scripts/                     # 部署、CI、数据迁移脚本
├── docker-compose.yml           # 本地开发环境
├── README.md
└── Makefile
```

### 技术栈选择

- **前端框架**：React（生态最丰富）、Vue（上手最平缓）、Svelte（编译型最小体积）、Solid（性能优先）。
- **后端框架**：FastAPI/Express/NestJS（API 服务）、Django/Rails（全栈框架）、Next.js/Nuxt（全栈+SSR 一体化）。
- **数据库**：PostgreSQL（通用首选）、SQLite（原型/单用户）、Supabase/Firebase（BaaS 降低后端门槛）。
- **部署**：Vercel（前端+Serverless）、Railway/Fly.io（全栈一键部署）、Docker + VPS（自托管）。
- **认证**：Auth.js/NextAuth（前端生态）、Supabase Auth（BaaS 方案）、Clerk（托管认证）。

### 依赖关系模式

- **前后端分离**：前端通过 API 与后端通信，不直接依赖后端技术栈。这意味着前端和后端可以独立开发、部署、扩展。
- **BaaS 降低后端门槛**：对于只有前端经验的用户，Supabase/Firebase 提供数据库、认证、存储、Serverless 函数，无需自建后端。
- **ORM 层**：业务逻辑不直接操作 SQL，通过 ORM（Prisma/Drizzle/SQLAlchemy）访问数据库，便于切换数据库和测试。
- **渐进式后端**：从"All-in-One 框架"开始（Next.js/Nuxt），在用户量增长后逐步分离出独立后端服务。

## 对 Carpe Diem 各阶段的启发

### Discover 阶段

Web 应用类项目通常从"让一个现有流程变得更容易"出发。引导用户关注：

- **你或你身边的人在哪些流程上花了大量时间**？这些流程是否涉及"收集信息→做出判断→执行操作"的三步？这是 Web 应用最擅长的场景。
- **目标用户规模**：Web 应用需要至少几百人的目标用户群体才能验证方向。如果用户群太小（如"我和我的两个朋友"），考虑 CLI 工具或脚本方案。
- **技术门槛考量**：Web 应用需要前后端、数据库、部署、域名等全套能力。如果用户只有单一技术栈经验（如"只会前端"或"只会 Python 脚本"），评估是否可以通过 BaaS 降低后端门槛。
- **关键信号**：当用户说"我每次都要花 30 分钟做 XX 流程"或"我们团队没有一个统一的 XX 工具"时，就是 Web 应用的机会。
- **竞争评估的侧重点**：Web 应用领域几乎不存在"没有竞品"的情况。评估重点不是"有没有人做"，而是"现有方案在哪些场景下仍然让用户痛苦"。

### Validate 阶段

验证 Web 应用方向时，应关注：

- **替代方案成本**：用户目前用什么方式解决这个问题？Excel、邮件、手工作业、还是什么都不做？"什么都不做"是最大的竞争对手——用户可能没有足够强的动机去改变现有习惯。
- **付费意愿验证**：Web 应用（尤其是 SaaS）的可持续性依赖用户付费。在投入开发前，至少通过预注册页面、用户访谈或问卷验证用户是否愿意付费。（注意：口头承诺 ≠ 实际付费。）
- **技术可行性验证**：核心技术风险（如第三方 API 限制、浏览器兼容性、数据处理能力）是否可控？在 Discover 阶段就构建一个最小技术原型消除主要技术风险。
- **发布渠道验证**：目标用户在哪里能找到你的应用？是通过 Google 搜索、社交媒体推荐、还是产品目录（Product Hunt、Hacker News）？如果用户获取渠道不明确，Web 应用容易陷入"建好无人来"的困境。
- **PASS 标准**：至少有 10 个目标用户表达了"如果有这个工具我会用/会付费"的明确意愿；至少有一个核心问题目前没有好的解决方案；验证了技术可行性和发布渠道。

### Plan 阶段

规划 Web 应用时注意：

- **MVP 范围**：第一版只做一件事，但做得完整。一个 Web 应用 MVP 应该包含：注册/登录 → 核心功能 → 结果展示。不要在第一版实现"设置页面"、"通知系统"、"团队协作"等辅助功能。
- **部署优先于特性**：在写第一个功能之前，先确保应用可以部署到生产环境、有 HTTPS、有数据库备份、有错误日志。部署不是"以后再做的事"，而是 MVP 的一部分。
- **数据模型设计**：虽然 MVP 只需要 3-5 张表，但应该考虑未来扩展性（如用户从单用户扩展到多租户、数据量从千级到万级）。扩展性最差的设计是"把所有数据放在一个表里用 type 字段区分"。
- **前端迭代策略**：Web 应用的前端是最容易修改的部分，MVP 阶段不需要完美的 UI 设计。先使用组件库（Shadcn/ui、Radix UI、Chakra UI）保证基础可用性，等验证 PMF 后再做定制化设计。
- **非目标**：第一版不需要：自定义域名、多语言、深色模式、PWA、SSR、监控告警、数据分析、用户邀请、团队空间。这些功能在用户量达到 100 以上之前不应该进入路线图。

## Prompt 模式

当用户用 Coding Agent 开发 Web 应用时，以下 Prompt 模式被验证有效：

- **「先画界面，再写代码」**：让 Agent 先用 HTML/CSS 输出一个页面的布局骨架（或使用 ASCII 线框图），用户确认 UI 结构后再实现交互逻辑。避免 Agent 写了一个功能完整的页面但布局完全不符合用户预期。
- **「用数据流描述代替技术选型」**：告诉 Agent "用户填写表单 → 数据保存到数据库 → 页面显示成功消息" 比 "帮我用 React + Express + PostgreSQL 写个表单" 更有效。Agent 可以基于需求推荐技术栈，而不是用户预设技术栈。
- **「分步提交，逐页确认」**：Web 应用的页面数量多，一次性让 Agent 全部实现会导致大量返工。每次只让 Agent 实现一个页面或一个功能，确认后再继续。每页用时不超过一轮对话。
- **「给出一个真实用户场景的完整流程」**：描述一个用户从进入网站到完成目标的完整步骤（如：打开首页→点击注册→填写邮箱→验证→进入仪表盘），Agent 能据此理解页面之间的导航关系。
- **「先定义 API，再实现前后端」**：让 Agent 先输出 API 接口定义（请求/响应格式、错误码），用户确认后再分别实现前后端。API 是前后端之间唯一的契约。

## 验证策略

- **端到端流程验证**：核心用户流程（注册、登录、完成核心操作）必须通过 E2E 测试覆盖。这是 Web 应用最重要的验证层级，因为前端和后端的组合错误最容易被遗漏。
- **API 契约测试**：使用 OpenAPI/Swagger 或 tRPC 的自动验证，确保前端期望的接口格式与后端提供的接口一致。接口变更时自动通知双方。
- **状态管理验证**：用户刷新页面后状态是否保持？浏览器回退按钮是否正常工作？多个标签页打开同一应用时数据是否一致？
- **安全验证**：至少验证：XSS（跨站脚本）、CSRF（跨站请求伪造）、SQL 注入、权限绕过、敏感数据泄露（密码、Token 是否明文传输或存储）。
- **响应式与跨浏览器验证**：在 Chrome、Safari、Firefox 和移动端浏览器上验证核心流程。一个浏览器可用不代表所有浏览器可用。
- **性能基线**：首次加载时间（LCP）、交互响应时间（FID）、API 响应时间——不是每个应用都需要高性能，但应该有一个基线以防止回归。
- **非理想状态覆盖**：验证网络错误、空数据、加载中、权限不足、404 等所有非理想状态。这些状态占据了用户实际体验的 30% 以上。

## 常见陷阱

- **过早优化技术栈**：第一版就用微服务、Kubernetes、Redis 缓存、消息队列等"企业级"技术。Web 应用 MVP 阶段，单体架构 + 单一数据库 + 简单部署是最快的选择。技术栈升级应当由用户增长驱动，而非预先设计。
- **前端状态管理过于复杂**：在只有 3-5 个页面时就引入 Redux/Zustand 等全局状态管理库。大多数 Web 应用在初期根本不需要全局状态——React 的 `useState` + `useContext` 绰绰有余。
- **忽略非理想状态**：只实现了"快乐路径"（happy path），没有处理网络错误、空数据、加载中、权限不足、404 等状态。这些状态占据了用户实际体验的 30% 以上。
- **数据库 Schema 设计过度**：第一版就设计 20+ 张表、复杂的关联关系和索引策略。Web 应用 MVP 只需 3-5 张核心表，更多表等数据模型验证后再添加。
- **部署流程复杂**：需要手动 SSH 登录、设置环境变量、执行数据库迁移、构建前端。Web 应用的一键部署（Vercel、Railway、Fly.io 等）是验证期的最佳选择，自建服务器等验证 PMF 后再考虑。
- **过早引入 SEO 优化**：在还没有用户时就做 SSR、SSG、动态 Meta 标签、Sitemap 等 SEO 优化。SEO 在有至少 100 个活跃用户之前都不应该成为优先级。
- **认证拖到后面做**：认证和授权是 Web 应用的基础设施，应在第一版就完成。很多人拖到最后才做，导致为每个新功能临时补权限逻辑，反而更耗时。

## 反向提醒

这个模板不适合：
- **单用户工具**：如果工具只有你自己用，不需要 Web 界面。CLI 工具或本地脚本更快更简单。
- **批量处理任务**：Web 应用天然适合"用户交互→即时反馈"的场景。如果用户需要上传大量数据、等待长时间处理、再下载结果，Web 应用不一定是最好的交付方式——考虑 CLI 工具或后台任务 + 通知。
- **纯内容展示**：个人博客、文档站、作品集等静态内容网站，不需要 Web 应用的完整后端。使用静态站点生成器（Hugo、Astro、Next.js SSG）更高效，不需要认证、数据库和 API。
- **高度敏感数据系统**：如医疗记录、银行交易、法律文件管理系统。Web 应用的安全合规成本（HIPAA、SOC2、PCI-DSS）极高，不适合作为个人或小团队的初始项目类型。
- **需要原生设备能力**：如果应用需要访问摄像头、蓝牙、NFC、本地文件系统、后台通知等原生能力，Web 应用能力有限。考虑跨平台应用（Electron、Tauri）或原生应用。
