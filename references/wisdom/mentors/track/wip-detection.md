# 行为卡：WIP 检测

> 统计"正在做什么"和"卡在什么"，而非只报告"完成了什么"
> 蒸馏日期：2026-09-01

## 问题本质

大多数进度报告只回答一个问题："完成了什么？"但这个问题遗漏了一个关键信号——**正在同时推进多少件事**。

"同时推进 10 个里程碑，每个完成 10%"的进度，看起来和"集中推进 1 个里程碑，完成了 100%"一样，都报告"完成了 1 个里程碑"。但前者的真实状态是：**10 个任务都没有完成，没有一件事真正交付了**。多个任务之间的上下文切换、任务阻塞、等待时间，都被"平均进度"掩盖了。

问题的根源是：**"任务完成了"是一个好信号，但"做了多少任务"不是好指标**。如果 10 个任务都在进行中但没有一个完成，真正的原因不是"做得不够快"，而是"做得太多了"。

当同时推进的任务超过一定数量时，真实的吞吐量会急剧下降：
- 每个任务之间的上下文切换消耗大量时间
- 没有一个任务能集中精力推进到完成
- 阻塞的任务没有及时被发现，因为它被其他"正在进行"的任务掩盖了

## 触发条件

在以下任一场景中触发：

- Track 阶段开始报告里程碑进度，发现多个里程碑同时处于"进行中"状态
- 用户报告"感觉一直在做，但好像没完成什么"
- 多个里程碑长期没有进展，但每个都在"进行中"
- Plan 阶段规划了过多并行任务，用户不确定是否合理
- 用户问"为什么做了这么久还没做完"

## 行为指导

### 1. 统计当前"进行中"的里程碑数量

在 Track 报告开始时，第一件事是统计"正在进行中"的里程碑数量：

```
在制品检查：
  - 进行中里程碑：4 个
  - 其中最近一周有进展的：2 个
  - 其中已超过一周无进展的：2 个
  - 建议：当前在制品数量偏高，建议集中推进 1-2 个里程碑至完成
```

统计标准：
- **"进行中"**：只要有证据表明"开始做了但还没有完成"（有 Git 提交、有代码变更、有相关文件修改），就算"进行中"
- 已经完成但还在等待验证的，不算"进行中"——"进行中"是指"还没有完成"
- 已经规划但还没有开始做的，不算"进行中"——"进行中"是指"已经开始做了"

### 2. 如果在制品数量超过 3，标记为"高在制品"

当同时推进的里程碑超过 3 个时，将其标记为"高在制品"状态，并给出明确建议：

```
高在制品预警：
  - 当前在制品数量：4 个
  - 风险：任务越多，单个任务的完成速度越慢——不是"做得慢"，而是"做太多"
  - 建议：选择 1-2 个最关键的里程碑，集中推进到完成，其余暂停
```

为什么是 3？
- 对于个人项目，同时推进 1-2 个里程碑是合理的
- 3 个以上时，上下文切换成本开始超过并行收益
- 注意：这个阈值不是固定的——如果项目规模大、里程碑粒度小，阈值可以适当上调；如果项目是个人副业项目，阈值应该更严格

### 3. 报告"状态分布"，替代"完成百分比"

不要用"完成了 60%"这种主观数字，而是用"状态分布"来展示进度：

```
推荐的状态分布报告：
  里程碑 A：进行中（推进中，有近 3 天的提交记录）
  里程碑 B：进行中（阻塞——等待上游 API 文档）
  里程碑 C：已规划（未开始）
  里程碑 D：已完成（有证据：测试通过，CI 通过）
  里程碑 E：已完成（有证据：合并到主分支）

汇总：
  - 已完成：2 个
  - 进行中（有进展）：1 个
  - 进行中（阻塞）：1 个
  - 已规划（未开始）：1 个
  - 在制品数量：2 个（推进中 + 阻塞）
  - 建议：先处理阻塞的里程碑 B——其他任务推进再多，如果 B 不完成，整体也无法交付
```

这种报告方式的好处：
- 一眼看出"哪些在推进、哪些卡住了、哪些还没开始"
- 区分"有进展的进行中"和"阻塞的进行中"——这两个状态需要不同的应对策略
- 不需要主观判断"完成了多少"，只需要客观判断"处于什么状态"

### 4. 识别阻塞和瓶颈

在统计状态分布时，特别注意"阻塞"状态：

- **什么是阻塞**：某个里程碑超过 3 天没有进展，且不是因为"没有时间做"（而是因为"需要等待某个条件"）
- **常见的阻塞原因**：等待外部依赖、等待用户反馈、等待技术方案确定、等待某个工具就绪
- **如何处理阻塞**：在 Track 报告中明确标出阻塞项，并建议用户：
  - 如果阻塞可以消除，给出消除阻塞的步骤
  - 如果阻塞无法短期内消除，建议将阻塞的里程碑暂停，先推进其他
  - 如果阻塞持续超过 1 周，建议用户决定"是否继续等待还是换方案"

同时，识别导致"在制品堆积"的环节：

```
瓶颈分析：
  - 大部分里程碑卡在"等待用户确认"环节
  - 建议：下次 Plan 阶段，为"用户确认"预留更明确的截止时间
  - 或：考虑在用户确认前，先推进不需要确认的部分
```

### 5. 用"前置时间"衡量流动效率

记录每个里程碑从"开始"到"有证据证明完成"的时间，作为流动效率的指标：

```
前置时间追踪：
  里程碑 A 前置时间：3 天（从开始到完成）
  里程碑 B 前置时间：12 天（从开始到完成）
  里程碑 C 前置时间：还在进行中，已 8 天

  趋势：最近两个里程碑的前置时间在增长（3 天 → 12 天）
  建议：如果前置时间持续增长，说明流动效率在下降——可能的原因：
    1. 在制品过多，导致每个任务的完成时间变长
    2. 任务复杂度在增加，需要更细的粒度拆分
    3. 外部依赖在增加，需要更早识别依赖
```

前置时间的趋势比绝对值更有价值：
- 如果前置时间在持续增长，说明系统有问题——不是"这个任务变难了"，而是"整体流动效率在下降"
- 如果前置时间保持在稳定水平，说明系统在健康运转
- 如果前置时间在缩短，说明系统在改善——是好的信号

### 6. 给出修改建议：减少在制品数量

当在制品数量超过阈值时，Track 报告应给出具体建议：

```
建议操作：
  1. 暂停低优先级的进行中里程碑（标记为"暂停"状态）
  2. 集中精力完成 1-2 个最关键的里程碑
  3. 在下一轮 Track 中，检查"暂停"的里程碑是否应该重新激活或取消
  4. 在 Plan 阶段，控制并行任务的数量——优先完成，而非同时开始
```

注意：不要替用户做决定。Track 报告只给出建议，由用户决定"暂停哪个、继续哪个"。

## 不适用场景

- **单任务项目**：如果项目只有一个里程碑，在制品数量永远为 1，WIP 检测没有意义。此时"前置时间"更适合作为进度指标。
- **高度耦合的单一交付**：如果项目是一个不可分割的交付物（如"写一本书"），无法拆分为多个并行里程碑，WIP 检测不适用。此时应关注"章节完成度"而非"在制品数量"。
- **探索性工作**：如果用户在做探索性研究（如"调研三个方案，每个方案试一下"），那么同时推进多个方向是正常的——此时 WIP 检测不适用，因为"并行探索"是探索阶段的核心策略。
- **维护性工作**：修复 bug 和日常维护属于"即时响应"的工作模式，不适用"在制品限制"的概念。修复 bug 应该快速响应并快速完成，而不是"限制同时修复的 bug 数量"。
- **团队协作项目**：WIP 限制的"3 个"阈值是针对个人项目设计的。如果多个开发者在同一项目上工作，在制品数量会自然增加，需要根据团队规模和任务粒度调整阈值。
