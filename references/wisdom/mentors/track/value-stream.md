# 行为卡：价值流

> 从"想法"到"交付"的全流程成像——绘制每个环节，量化等待时间，定位偏差在哪一环

## 问题本质

大多数进度报告只看一个数字：**"做完了多少"**。但"做完了多少"掩盖了一个惊人的事实——**一个项目的大部分时间，不是在"做"，而是在"等"**。

代码在等审查、审查结果在等部署、部署在等环境就绪、修复在等审批——你看到的"2 周完成一个功能"，实际加工时间可能只有 3 天，剩下的 11 天全部是等待时间。

问题的根源是：**你只看到了"工作"的时间，没有看到"工作之间"的时间**。

一个典型的项目流程：

```
想法 → 讨论 → 规划 → 设计 → 审查 → 编码 → 审查 → 测试 → 验收 → 部署
```

在每个箭头处，都有一段时间——**工作完成了，但下游还没准备好**。这些"箭头上的时间"（等待时间）不会出现在任何进度报告中，但它们占据了一个项目 60-90% 的实际历时。

**价值流**的核心逻辑是：**不要只看"每个环节做了多久"，要看"整个过程花了多久"——把"等待时间"也画出来**。你不需要精确到分钟，只需要看到"工作在哪一环停了多久"。

当你能看到等待时间后，你会发现：

1. **大多数"慢了"的原因不是"做得慢"，而是"等得久"**——一个环节做完了，但下一个环节还没开始
2. **瓶颈不在你最忙的地方，而在"堆积最多"的地方**——如果测试队列积压了 5 个任务，测试就是瓶颈，不是编码
3. **消除等待时间比加快加工时间更有效**——减少 2 天等待时间比把编码速度提升 20% 更立竿见影

## 触发条件

在以下任一场景中触发：

- **Track 阶段发现进度偏差，需要定位"问题出在哪个环节"**——"整体慢了"需要变成"具体哪个环节慢了"
- **用户说"感觉一直在做，但好像没完成什么"**——"在做"和"在完成"之间可能隔着大量的等待时间
- **用户说"代码写完了，但还在等测试/审查/部署"**——这是典型的"等待时间"信号，说明价值流中有环节在堆积
- **用户说"不知道哪个环节拖了后腿"**——"感觉处处都是瓶颈"通常意味着"没有真正定位到瓶颈"
- **多个里程碑卡在同一个环节**——如果每次 Track 都发现同一个环节在阻塞，说明这个环节是系统的瓶颈，需要重点诊断

## 行为指导

### 1. 绘制完整的价值流——从"想法"到"交付"的每个环节

价值流分析的第一步是**画出流程**。不是"画个大概"，而是"画出每个环节、每个决策点、每条等待线"：

```
价值流模板（通用流程）：

  触发 → 分析 → 规划 → 设计 → 审查 → 编码 → 审查 → 测试 → 验收 → 部署

  各环节定义：
    触发：需求来源（用户反馈、市场信号、内部提案）
    分析：需求拆解、可行性评估、优先级判定
    规划：任务拆分、时间估算、资源分配
    设计：架构设计、接口设计、数据模型设计
    审查：设计审查、方案确认
    编码：实际的代码编写
    审查：代码审查、同行评审
    测试：单元测试、集成测试、验收测试
    验收：用户验收、产品确认
    部署：发布上线、监控验证
```

**流程画像的两个关键原则**：

1. **流程是"你实际的流程"，不是"你想要的流程"**——不要画一个理想的流程（"我们应该是这样的"），要画真实的流程（"我们实际上是怎么做的"）。如果你们做了流程中没有的步骤（如"临时审批"、"领导签字"），把它加进去；如果流程中有但你们从来不做的步骤（如"正式的设计审查"），把它去掉。
2. **流程要反映"工作流"，不是"组织架构"**——不要按"谁负责什么"来画（"开发部做这个，测试部做那个"），要按"工作经过什么环节"来画（"代码写完后经过审查，然后进入测试"）。关注的是工作的流动，不是人的分工。

**如果项目没有固定的流程**：
- 不是"项目没有流程"，而是"流程是隐式的"——开发者可能在心里有一个流程（"想法→写代码→测试→部署"），但从来没有写出来
- 帮助用户把隐式流程显式化：问"一个想法从产生到交付，经历了哪些步骤？"
- 对于高度不确定的项目，流程可能每次都不一样——此时价值流分析不适用（见"不适用场景"）

### 2. 区分"加工时间"和"等待时间"——把"箭头上的时间"拆出来

在画完流程后，对每个环节，区分两种时间：

```
时间拆解示例：

环节：代码审查
  - 加工时间：实际审查代码的时间（30 分钟）
  - 等待时间：提交审查后等待审查者开始的时间（2 天）
  - 总历时：30 分钟 + 2 天 ≈ 2 天

环节：部署
  - 加工时间：实际部署操作的时间（10 分钟）
  - 等待时间：等待部署环境就绪的时间（1 天）
  - 总历时：10 分钟 + 1 天 ≈ 1 天

环节：测试
  - 加工时间：实际执行测试的时间（4 小时）
  - 等待时间：等待测试环境就绪、等待测试数据准备好的时间（3 小时）
  - 总历时：4 小时 + 3 小时 ≈ 7 小时
```

**时间拆解的关键问题**：

| 问题 | 目的 |
|------|------|
| 这个环节实际花了多少时间在"做"？ | 确认加工时间——真正在创造价值的时间 |
| 工作完成后，等了多久才进入下一个环节？ | 确认等待时间——最大的浪费来源 |
| 等待的原因是"下游没准备好"还是"工作质量不合格被退回"？ | 确认等待类型——前者是"系统瓶颈"，后者是"质量缺陷" |
| 这个等待时间是否可以被量化？ | 如果不能量化，说明对这个环节的认知不够清晰 |

**加工时间 vs 等待时间的解读**：

| 加工时间占比 | 信号 | 健康度 |
|-------------|------|--------|
| **> 50%** | 价值流较健康，大部分时间在真正工作 | 良好——但"较健康"不意味着"不需要改进" |
| **20-50%** | 有大量等待时间，需要关注瓶颈环节 | 一般——等待时间的主要来源是关键改进点 |
| **< 20%** | 严重——大部分时间在等待，只有极少时间在真正工作 | 危险——需要立即干预，识别并消除最大的等待时间来源 |

**核心洞察**：在大多数项目中，**加工时间只占 10-30%**，等待时间占 70-90%。这意味着，你不需要通过"写得快 20%"来缩短交付周期——通过消除等待时间，你可以缩短 50-70% 的交付周期。

### 3. 量化各环节的延迟——找到"时间黑洞"环节

在区分了加工时间和等待时间后，对每个环节量化延迟，找到"时间黑洞"：

```
延迟量化分析：

| 环节 | 加工时间 | 等待时间 | 总历时 | 延迟占比 | 累计延迟 |
|------|---------|---------|--------|---------|---------|
| 触发 → 分析 | 1 天 | 3 天 | 4 天 | 75% | 4 天 |
| 分析 → 规划 | 0.5 天 | 1 天 | 1.5 天 | 67% | 5.5 天 |
| 规划 → 设计 | 2 天 | 2 天 | 4 天 | 50% | 9.5 天 |
| 设计 → 审查 | 1 天 | 1 天 | 2 天 | 50% | 11.5 天 |
| 审查 → 编码 | 3 天 | 2 天 | 5 天 | 40% | 16.5 天 |
| 编码 → 审查 | 1 天 | 2 天 | 3 天 | 67% | 19.5 天 |
| 审查 → 测试 | 2 天 | 1 天 | 3 天 | 33% | 22.5 天 |
| 测试 → 验收 | 1 天 | 3 天 | 4 天 | 75% | 26.5 天 |
| 验收 → 部署 | 0.5 天 | 2 天 | 2.5 天 | 80% | 29 天 |

总计：加工时间 12 天，等待时间 17 天，总历时 29 天
等待时间占比：59%
```

**延迟量化分析的核心问题**：

1. **哪个环节的延迟占比最高？**——找到"时间黑洞"环节。在上例中，"验收→部署"的延迟占比为 80%，是最大的时间黑洞
2. **哪个环节的等待时间绝对值最大？**——"触发→分析"等待 3 天，"测试→验收"等待 3 天，是等待时间最长的两个环节
3. **哪个环节的等待时间最"不必要"？**——"编码→审查"等待 2 天，但审查本身只需要 1 天——如果能在提交后立即审查，可以节省 2 天
4. **哪些环节的等待时间可以立即消除？**——不需要大改流程，只需要调整"谁先做"的顺序或增加并行

**延迟量化的三个原则**：
- 不需要精确到分钟——"3 天"和"2 天"的差异足以判断哪个环节是瓶颈，不需要精确到"3 天 2 小时"
- 如果无法量化，用"大/中/小"或"长期/短期/当天"等粗略分类——不要因为没有精确数据就放弃分析
- 关注"相对值"而非"绝对值"——"这个环节的等待时间是加工时间的 3 倍"比"这个环节等待了 2 天"更有信息量

### 4. 定位偏差环节——找到"瓶颈在哪里"和"为什么在那里"

在量化了延迟后，定位偏差的具体环节。偏差有两种类型：

```
偏差定位分析：

类型一：等待型偏差——工作做完了，但下游没准备好

  环节：测试
  现象：代码审查完成后，测试队列积压了 3 个任务
  原因：测试资源不足（只有一个测试人员）
  偏差类型：⏳ 等待型——"等下游"

  环节：部署
  现象：测试通过后，等待部署环境就绪
  原因：部署环境需要审批，审批流程耗时 2 天
  偏差类型：⏳ 等待型——"等环境"

类型二：质量型偏差——工作做完了，但质量不合格被退回

  环节：编码 → 审查
  现象：30% 的代码审查不通过，需要返工
  原因：编码过程中没有中间检查点，问题集中暴露在最终审查
  偏差类型：🔄 质量型——"等返工"

  环节：测试 → 验收
  现象：20% 的测试用例在验收阶段发现回归缺陷
  原因：测试覆盖不完整，没有覆盖边界条件
  偏差类型：🔄 质量型——"等修复"
```

**偏差定位的四个关键问题**：

1. **哪个环节的前置队列最长？**——如果某个环节前排着长队，说明这个环节的吞吐量低于上游的产出量，这是瓶颈
2. **哪个环节的等待时间最长？**——如果某个环节的等待时间远高于加工时间，说明这个环节的"启动速度"太慢
3. **哪个环节的返工率最高？**——如果某个环节的产出经常被退回，说明这个环节的质量标准与下游预期不匹配
4. **哪个环节的偏差在持续扩大？**——如果上次 Track 和这次 Track 发现同一个环节在恶化，说明这个环节的问题是系统性的，不是偶发的

**等待型偏差 vs 质量型偏差的处理方式**：

| 偏差类型 | 典型表现 | 处理方式 |
|---------|---------|---------|
| **等待型** | 工作完成了，但卡在"等下游" | 增加瓶颈资源、优化排队策略、减少单批大小 |
| **质量型** | 工作完成了，但被退回返工 | 提升上游质量标准、增加中间检查点、改进验收标准一致性 |

### 5. 识别浪费类型——不只是"慢了"，而是"哪种浪费"

价值流分析不仅回答"哪里慢了"，还回答"哪种浪费"——不同类型的浪费有不同的根因和解决方式：

```
浪费类型识别：

类型一：等待浪费
  表现：工作完成了，在等下一个环节
  根因：下游环节的吞吐量小于上游环节的产出量
  常见场景：
    - 代码写完了，在等审查（审查者太忙）
    - 测试做完了，在等部署（部署流程太复杂）
    - 功能开发完了，在等验收（验收者不在）
  解决方向：增加瓶颈资源、减少单批大小、消除不必要的审批

类型二：半成品浪费
  表现：工作开始了但没有完成，堆积在中间环节
  根因：在制品过多，同时推进太多任务
  常见场景：
    - 同时开了 5 个分支，没有一个合并
    - 测试队列积压了 3 个功能
    - 3 个功能同时处于"等待验收"状态
  解决方向：限制在制品数量、集中推进少数任务（参考"WIP 检测"卡）

类型三：返工浪费
  表现：工作完成了但被退回修改
  根因：质量标准不一致、上游验证不足
  常见场景：
    - 代码审查不通过，需要重新修改
    - 验收测试发现回归缺陷，需要修复
    - 设计在实现阶段被推翻，需要重新设计
  解决方向：提升上游质量标准、增加中间检查点、建立"完成定义"的共识

类型四：流程浪费
  表现：做了不创造价值的事
  根因：流程中存在不必要的步骤
  常见场景：
    - 需要多个审批才能部署（但审批从不拒绝）
    - 需要填写详细的状态报告（但没人看）
    - 需要参加每日站会讨论（但内容不相关）
  解决方向：消除不必要的步骤、简化流程、自动化重复工作

类型五：技能浪费
  表现：人在做低于其能力的事
  根因：分工不合理、自动化不足
  常见场景：
    - 开发者在手动运行测试（应该自动化）
    - 高级工程师在做简单的配置变更（应该交给工具或新人）
    - 团队成员在等待"被分配任务"（应该主动认领）
  解决方向：自动化重复工作、合理分配任务、授权团队自我管理
```

**浪费识别的核心原则**：
- 不要试图一次识别所有浪费——"找到最大的一个浪费并消除它"比"找到所有浪费但什么都没做"更有效
- 浪费是"相对的"，不是"绝对的"——某个环节的"等待"可能对另一个环节的"稳定"是必要的。不要为了消除等待而增加不稳定
- 浪费识别需要团队共识——"我认为这是浪费"和"他认为这是必要的"可能都有道理。在识别浪费时，最重要的是理解"为什么要这么做"

### 6. 生成价值流报告——把"哪里在等"画出来，把"哪里在浪费"标出来

将以上分析汇总为价值流报告，作为 Track 报告的组成部分：

```
## 价值流报告

### 当前价值流画像

[触发] → [分析] → [规划] → [设计] → [审查] → [编码] → [审查] → [测试] → [验收] → [部署]
   ⏳3天    ⏳1天    ⏳2天    ⏳1天    ⏳2天              ⏳2天    ⏳1天    ⏳3天    ⏳2天
   [1天]    [0.5天]  [2天]    [1天]    [3天]             [1天]    [2天]    [1天]    [0.5天]

图例：[加工时间] ⏳等待时间

### 关键指标

| 指标 | 当前值 | 说明 |
|------|--------|------|
| 总历时 | 29 天 | 从想法到交付的总时间 |
| 加工时间 | 12 天 | 实际创造价值的时间 |
| 等待时间 | 17 天 | 不创造价值的时间 |
| 效率比 | 41% | 加工时间/总历时，理想值 > 50% |
| 最大瓶颈 | 验收→部署（80% 延迟占比） | 等待时间最长的环节 |

### 瓶颈定位

**瓶颈环节：验收 → 部署**
- 等待时间：3 天（加工时间 0.5 天，延迟占比 80%）
- 等待原因：部署环境需要审批，审批流程耗时 2 天
- 影响：每个功能在最后一个环节等待 3 天，占整个流程 10% 的时间
- 建议：将部署审批从"事前审批"改为"事后审计"——部署后自动通知审批者，审批者可以在部署后 24 小时内提出异议

**次要瓶颈：触发 → 分析**
- 等待时间：3 天（加工时间 1 天，延迟占比 75%）
- 等待原因：需求来源不固定，需要等待"收集到足够多"才启动分析
- 建议：改为"有需求就启动分析"，不需要等待"收集到足够多"

### 浪费识别

| 浪费类型 | 环节 | 浪费成本 | 建议 |
|---------|------|---------|------|
| 等待浪费 | 验收→部署 | 3 天/功能 | 改为事后审计 |
| 等待浪费 | 触发→分析 | 3 天/功能 | 改为即时启动 |
| 半成品浪费 | 测试队列 | 3 个功能积压 | 限制在制品数量 |
| 流程浪费 | 部署审批 | 2 天/功能 | 审批从不拒绝，可以取消 |

### 改进建议

1. **短期（本周）**：将部署审批从"事前审批"改为"事后审计"，消除验收后的 3 天等待
2. **中期（本月）**：建立"即时启动"机制，需求来源不再等待收集，而是随时启动分析
3. **长期（本季度）**：优化测试流程，减少返工率，从 20% 降低到 10% 以下
4. **持续**：每次 Track 检查价值流效率比，目标从 41% 提升到 60% 以上
```

## 不适用场景

- **探索性项目**：如果项目没有固定的流程（每个阶段做不同的事，流程本身在变化），价值流分析没有意义——价值流分析的前提是"有可重复的流程"，探索性项目的特点是"没有可重复的流程"。此时应该关注"学到了什么"而非"流程效率如何"。

- **单环节项目**：如果项目只有一个环节（如"写一篇博客"——只有"写作"这一个环节），没有"等待"和"流动"的概念。价值流分析的前提是"多环节协作"，一个环节的项目不需要分析价值流。

- **个人项目**：个人项目没有"等待他人"的问题（等待时间是自己决定的），价值流分析的核心假设——"工作完成了但下游没准备好"——不成立。个人项目关注"效率"而非"流动"。

- **流程高度不确定的项目**：如果项目每次做的方式都不一样（如"做一个一次性的内部工具"），流程画像没有意义——每次的流程不同，分析结果无法复用。此时应该关注"这次的瓶颈是什么"而非"流程的效率如何"。

- **用户明确表示"不需要流程优化"**：如果用户说"我知道流程有问题，但我不想改"或"我知道效率不高，但能做就行"，价值流分析不适用。价值流分析的核心假设是"用户愿意改进流程"——如果用户不关心流程效率，分析结果只是数据，没有行动价值。
