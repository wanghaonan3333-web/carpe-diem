# 行为卡：Code Review

> 触发条件：团队开始协作，或用户说"我们做 CR 但没什么效果"

## 问题本质

Code Review 做得不好会变成形式主义或人身攻击——审查者随便看看就通过，或者对每一行代码都吹毛求疵。无论哪种极端，都浪费了团队的时间，却没有提升代码质量。

问题的根源是：**你把 Code Review 当成了"检查代码"的工具，而不是"帮助团队成长"的工具**。好的 CR 不是"找错误"，而是"分享知识、建立共识、提升整体代码质量"。如果 CR 只关注"找 bug"，那它和"测试"的功能重叠了——CR 的独特价值在于"知识传递"和"设计一致性"。

## 触发条件

用户正在执行以下任一操作时触发：

- **场景一：团队开始协作，代码提交需要审查，但审查流程不明确**。如果团队刚开始合作，但还没有建立 CR 的规范和标准，说明 CR 很可能变成"随意看看"或"形式主义"。

- **场景二：用户说"我们做 CR 但没什么效果"或"CR 就是走个过场"**。如果 CR 已经变成了"必须做但没价值的流程"，说明审查者没有认真对待，或者提交者没有提供足够的上下文。

- **场景三：CR 讨论变成了"个人喜好"之争——"我觉得这个命名不好"、"这个格式不符合我的偏好"**。如果 CR 评论集中在代码风格、命名偏好、个人喜好上，说明 CR 没有聚焦在"代码质量"上，而是变成了"个人品味"的较量。

- **场景四：CR 审查者经常说"这个代码我看不懂"或"这个逻辑太复杂了"**。如果审查者无法理解提交的代码，说明提交者没有提供足够的上下文，或者代码本身太复杂——这两个都是需要解决的问题。

## 行为指导

### 1. 每次 PR 应小而专注（< 200 行）

大 PR 是 CR 的头号杀手。当 PR 超过 400 行时，审查者很难仔细阅读每一行代码——他们会"扫一眼"而不是"认真看"。结果就是：大 PR 中的 bug 更容易被漏掉，CR 的质量大幅下降。

具体做法：
- 每次 PR 控制在 200 行以内（包括测试代码）
- 一个 PR 只做一件事——修复一个 bug、添加一个功能、重构一个模块
- 如果改动太大，拆分成多个小 PR，依次提交和审查
- 小 PR 的另一个好处是：审查周期短，反馈快，代码合并更快

### 2. 审查者先看整体设计再读细节

CR 的审查顺序应该是：先理解"这段代码想做什么"，再检查"它做得怎么样"。如果审查者不理解整体设计就直接看细节，很容易陷入"找错别字"的陷阱。

具体做法：
- 第一步：查看 PR 的标题和描述——理解这个 PR 想解决什么问题
- 第二步：查看改动的文件列表——理解改动范围
- 第三步：阅读关键文件（核心逻辑、接口定义、数据模型）
- 第四步：检查细节（边界条件、错误处理、测试覆盖）
- 第五步：确认整体质量——这段代码是否容易维护、是否与现有设计一致

### 3. 评论针对代码而非作者

CR 的目标是"让代码更好"，而不是"让作者感觉自己很差"。好的 CR 评论聚焦于代码本身，而不是代码的作者。

具体做法：
- 说"这个函数有 100 行，太长了吧"——比说"你怎么写这么长的函数"好
- 说"这里可能有个边界条件没处理"——比说"你忘了处理边界条件"好
- 说"这个命名可以更明确一些"——比说"这个命名太差了"好
- 用"我们"替换"你"——"我们是不是应该考虑..."比"你应该..."好

### 4. 区分"必须改"和"建议改"

不是所有 CR 评论都需要被采纳。审查者需要明确区分"不改就不合并"和"改了更好但不改也行"。

具体做法：
- "必须改"：代码有 bug、安全漏洞、性能问题、设计缺陷——这些需要修改后才能合并
- "建议改"：命名优化、格式调整、代码风格——这些可以改，但不是必须的
- 在评论中明确标注"建议"或"必须"——让提交者知道哪些需要优先处理
- 提交者有权决定是否采纳"建议改"——如果不同意，说清楚理由即可

### 5. 作者有责任解释设计决策

CR 不是"提交代码→审查者打分"的单向流程，而是"提交者解释理由→审查者反馈→双方达成共识"的双向对话。

具体做法：
- 提交者在 PR 描述中写清楚：这个改动解决了什么问题、为什么这么设计、考虑了哪些替代方案
- 如果审查者不理解某个设计决策，提交者有责任解释——而不是"代码已经写了，你自己看"
- 如果审查者和提交者无法达成一致，可以引入第三方（如技术负责人）决策
- 最终目标是"达成共识"，而不是"谁说服谁"

### 6. 建立 CR 检查清单

一个 CR 检查清单可以帮助审查者不遗漏关键点，也可以帮助提交者自检。

建议的检查清单：
- [ ] 代码是否可读？命名是否清晰？
- [ ] 是否有测试覆盖（单元测试、集成测试）？
- [ ] 边界条件是否处理了（空值、异常、边界值）？
- [ ] 错误处理是否正确？错误信息是否清晰？
- [ ] 性能是否可接受？是否有不必要的循环或查询？
- [ ] 是否有安全漏洞（注入、越权、数据泄露）？
- [ ] 代码是否与现有设计一致？（遵循相同的模式、使用相同的工具）
- [ ] 文档是否更新了？（如果改动影响了 API 或用户界面）

## 不适用场景

- **单人项目**：如果用户是独自开发，没有其他人可以审查代码，那么 CR 的自然不适用。但即使是单人项目，也可以使用"自我审查"——在提交代码前，以"审查者"的视角重新阅读自己的代码，或者使用工具（如 linter、静态分析）来辅助检查。

- **原型阶段**：如果用户正在快速验证想法，代码质量不是首要关注点。在原型阶段，速度和验证结果比代码质量更重要。原型代码可以"先写出来，后面再重构"——但需要明确标注"这是原型代码"，并在转入正式开发时重写或重构。

- **紧急修复**：如果用户正在处理线上故障或紧急安全漏洞，没有时间走完整的 CR 流程。紧急修复可以"先合并，后补 CR"——在修复完成后，补写 CR 记录，确保团队知道发生了什么、为什么这么修复、以及如何避免类似问题。

- **微小改动**：如果用户做的是"修改一个拼写错误"、"调整一个注释"、"格式化代码"这类微小改动，CR 的价值不大。对于这类改动，可以直接提交，或者使用"批量提交"的方式——每周集中一次 CR 审查所有微小改动。
