# 实战模式：AI Agent 的上下文工程

> 来源：Anthropic 工程博客、LangChain 最佳实践、OpenAI Cookbook
> 蒸馏日期：2026-08-30

## 问题本质

给 AI Agent 提供太多或太少上下文都会导致输出质量下降。上下文过长会触发注意力稀释（attention dilution）——模型在数万 token 中「迷失在中间」；上下文过短则信息不足，Agent 产生幻觉或需要反复追问。如何高效地组织、裁剪和管理上下文，是让 Agent 稳定产出的核心工程挑战。

## 关键洞察

- **结构化上下文比长篇大论更有效**：用明确的段落分隔（如 `## 任务目标`、`## 已知约束`、`## 输出格式`）引导模型注意力，而非一段自然语言描述。结构化让模型在推理时更容易定位关键信息。
- **关键信息放在开头和结尾（位置偏差）**：模型注意力存在显著的 U 型曲线——开头（primacy bias）和结尾（recency bias）的内容召回率最高，中间部分易被忽略。因此最重要的指令、约束和示例应放在 System Prompt 的开头，关键输出格式说明放在最后。
- **用示例替代抽象描述**：一个具体的输入输出对（few-shot example）胜过三段规则描述。示例告诉模型「怎么做」，而抽象描述只告诉模型「做什么」。示例应覆盖边界情况和典型情况，具体而非泛化。
- **定期清理和更新上下文**：Agent 在多轮对话中积累的上下文会逐渐退化——过时的中间结果、废弃的推理路径、重复的指令会稀释有效信息。引入显式的上下文压缩（context compression）或摘要轮次（summarization turn），在关键节点重置上下文窗口。
- **分层上下文架构**：将上下文分为全局层（任务不变信息，如角色定义、全局约束）、会话层（当前会话状态、中间结果）和即时层（当前请求的输入）。全局层写入 System Prompt，会话层存为工具调用结果，即时层是用户消息。层次分离让上下文的增删改查可预测。

## 对 Carpe Diem 用户的启发

### Discover 阶段

当用户用 AI Agent 探索市场或用户需求时，上下文工程直接决定了调研质量。在 Discover 阶段引导用户：
- 为 Agent 设置清晰的「角色+目标」System Prompt，而非泛泛的「帮我分析市场」
- 用结构化模板（如 PEST 分析框架、用户画像模板）而非自由描述来引导 Agent 输出
- 关键约束（目标市场、时间窗口、数据来源）放在 Prompt 开头，数据来源清单放在结尾
- 每次调研迭代后，让 Agent 输出摘要以压缩上下文，避免历史调研细节稀释后续分析

### Validate 阶段

验证假设时需要 Agent 保持对前一阶段结论的准确记忆：
- 将 Discover 阶段的结构化结论（而非原始对话）作为 Validate 的上下文输入——上下文压缩在此发生
- 在验证 Prompt 中显式引用上一阶段的关键假设，用 `## 待验证假设` 和 `## 验证标准` 两个区块分隔
- 使用示例驱动的验证标准：提供一个「通过验证」的示例和一个「未通过验证」的示例，比描述阈值更有效
- 多轮验证中，定期让 Agent 输出「已验证结论」和「待验证条目」两个结构化列表，自动清理已完成的上下文

### Plan 阶段

制定行动计划时，上下文工程的挑战在于如何让 Agent 同时兼顾多个约束条件：
- 将所有约束（资源限制、时间窗口、依赖关系）放在 Prompt 开头，用 `## 硬约束` 和 `## 软约束` 分层表达
- 把输出格式模板放在 Prompt 末尾（利用 recency bias 确保格式正确）
- 如果计划较长，要求 Agent 先输出计划大纲（作为上下文压缩），再逐段展开
- 在 Plan 阶段开始时，显式重置上下文——用 `## 以下是当前状态摘要` 替换之前的完整对话历史，而非继续追加

## 反向提醒

- 上下文工程不是万能药：如果 Agent 的基座模型能力不足，再好的 Prompt 结构也无法弥补
- 过度结构化会扼杀 Agent 的创造性：在探索性任务（如头脑风暴）中，松弛的结构比严格的 Prompt 模板更有效
- 上下文压缩有信息损失风险：摘要轮次可能丢失关键细节，需在压缩后保留关键原文的引用路径
- 不要为所有场景使用同一套上下文模板：不同任务（分析 vs. 生成 vs. 决策）需要不同的上下文结构
- 上下文工程需要迭代验证：第一次写出来的 Prompt 结构几乎一定不是最优的，需要通过 A/B 测试或定性评估来优化
