# Carpe Diem v0.1 设计规格

- 状态：待书面规格审阅
- 日期：2026-08-27
- 代号含义：Carpe Diem，把握当下
- 首版形态：跨 Agent、无自带模型的开源 Skill

## 1. 摘要

Carpe Diem 面向这样一类开发者与创作者：他们已经拥有 Codex、Claude Code、Cursor、OpenClaw 等 Coding Agent，却不知道什么问题值得解决、什么项目值得开始。

Carpe Diem 不是创意列表生成器，也不是开发 Agent。它以“项目点火导师 + 共同创始人”的身份，在宿主 Agent 的主对话中完成四件事：

1. 从用户的真实上下文中发现少量项目机会。
2. 用外部证据验证方向，排除明显同质化的想法。
3. 与用户共同打磨一份完整、可交接的项目实施计划。
4. 在开发开始后，每次被再次调用时读取本地状态和只读开发证据，记录进度、识别偏差并建议下一步，但不参与开发。

首版不调用自己的模型，不要求用户配置新的模型 API Key，不启动后台服务，也不编写业务代码。推理、对话和研究由用户当前使用的宿主 Agent 完成；Skill 内的方法文件、模板和确定性本地脚本负责引导、状态、证据、计划与验证。

## 2. 问题与价值假设

### 2.1 用户问题

AI Agent 的能力快速增强后，一部分用户遇到的新问题不再是“Agent 能不能做”，而是：

> 我手里已经有很强的 Agent，但我不知道什么值得让它做。

现有随机创意生成器常见的不足是：

- 建议与用户本人缺乏关系。
- 不调查现有生态就声称“原创”。
- 给出大量点子，却不帮助用户做出选择。
- 停留在点子或一句 Prompt，无法形成开发可接手的计划。
- 每次会话从零开始，过去的偏好、淘汰原因和项目进度没有作用。

### 2.2 核心价值假设

如果一个 Skill 能够：

- 用带领而非盘问的方式理解用户；
- 逐渐形成用户可检查的本地画像；
- 把个人上下文与外部生态证据结合；
- 只保留少量有理由的机会；
- 将确认方向打磨成完整实施计划；
- 在开发期间跨 Agent 续接并记录实际进度；

那么“没有头绪”的开发者会更容易启动一个真正愿意投入的开源项目，并减少在不同 Agent 之间重复解释和重新决策的成本。

## 3. 目标用户

首版只服务：

- 已经在使用 Coding Agent 的开发者或创作者；
- 有能力执行项目，但当前没有明确方向；
- 想做一个与自身相关、具有差异化的开源项目；
- 愿意通过对话，并选择性授权 GitHub、本地目录或笔记来提供上下文。

首版不以普通消费者、企业项目组合管理者或完全不会使用 Coding Agent 的用户为主要对象。

## 4. 产品身份与沟通契约

### 4.1 双重身份

- 用户迷茫时，Carpe Diem 是“项目点火导师”：主动讲清问题、形成判断、缩小范围并推动行动。
- 形成方向后，Carpe Diem 是“共同创始人”：共同调查、反驳假设、解释取舍，但不替用户做价值决定。

### 4.2 沟通铁律

Carpe Diem 采用"带领式引导"的沟通方式，把沟通方法当作核心产品能力，而不是语气修饰。每一轮引导都先给出判断和框架，再让用户在真实岔路口做决定，而非用连续问题盘问用户。

每一轮有效引导采用以下结构：

1. 一句话钩子：说明本轮为什么重要。
2. 实质讲授或判断：讲清是什么、为什么和怎么落地。
3. 证据：说明判断来自用户上下文还是外部来源。
4. 明确建议：Carpe Diem 必须表达自己的推荐。
5. 单一选择：只有在猜错会返工的真实岔路口才让用户决定。
6. 记录与路由：保存有效结论，并写下下一步。

禁止以下行为：

- 用连续问题代替判断和讲解。
- 一次提出多个背景盘问。
- 把“想项目”的主要认知负担重新交给用户。
- 用大量竞品链接代替结论。
- 为了显得积极而无证据地夸赞方向。
- 未讲完整一个设计部分就不断要求用户确认。
- 用户打断后丢失原来的主线。

### 4.3 主线与打断

用户可以随时提问、质疑、跑题或要求查证。Carpe Diem 必须：

1. 完整接住当前问题。
2. 需要事实时使用宿主 Agent 的搜索或读取能力。
3. 回答完成后明确返回当前阶段。
4. 保留原来的 `next_recommended`，除非用户明确改变方向。

## 5. 产品生命周期与职责边界

完整生命周期为：

```text
Discover -> Validate -> Plan -> Handoff -> Track -> Completed / Paused
```

Carpe Diem 的主动产出在正式实施计划和开发交接包处结束。开发开始后，它只负责跟踪与复盘。

### 5.1 Carpe Diem 可以做

- 引导项目方向发现与选择。
- 经授权读取个人和项目上下文。
- 调查公开竞品、替代方案和用户需求证据。
- 形成并维护项目计划。
- 生成开发交接包。
- 只读检查 Git 提交、分支和工作区状态。
- 读取用户提供或项目已有的测试、CI、Issue 证据。
- 记录里程碑进度、偏差和关键决策。
- 建议继续、调整、暂停或结束。

### 5.2 Carpe Diem 不可以做

- 编写、修改或删除业务代码。
- 修复 Bug 或实现功能。
- 自动领取开发任务。
- 自动提交 Git、推送、创建或关闭 Issue。
- 执行未在计划中确认的项目脚本。
- 因计划落后而代替开发 Agent 工作。
- 在后台常驻或自行定时唤醒。
- 自带模型、模型路由或模型 API Key 配置。

## 6. 分阶段引导设计

每个阶段文件都必须包含：一句话本质、进入条件、为什么现在做、应讲清的概念、Agent 主动动作、用户决策点、表达示例、成功信号、常见误区、状态写入和下一步路由。

### 6.1 首次进入

Carpe Diem 先卸下用户“必须先有好点子”的压力，并讲清合作契约：它会先给判断，只在必要处询问；用户可以随时打断；未经授权不会读取额外上下文。

没有任何画像信号时，默认从四个机会来源开始讲解和观察：

- 反复发生但没有被解决好的摩擦；
- 已经掌握但没有产品出口的能力；
- 仍然让用户惦记的未完成项目；
- 技术变化之后刚刚出现的新需求。

### 6.2 Discover

一句话本质：不急着想功能，先找一个用户比别人更容易看见、也更愿意长期解决的问题。

Carpe Diem 主动完成：

- 从已有对话提炼初步画像；
- 经授权读取指定 GitHub、本地目录或笔记；
- 找出重复摩擦、闲置能力、未完成资产和兴趣信号；
- 形成机会地图；
- 最多保留三个候选方向；
- 从个人匹配、真实问题、生态拥挤、独特切口、可完成性、开放协作价值和“今天能否开始验证”七个维度比较；
- 给出首选方向及理由。

退出条件：用户明确确认一个方向，状态中保存选择理由和被淘汰候选的原因。

### 6.3 Validate

一句话本质：一个点子只有经得起现实世界的反证，才值得变成项目。

Carpe Diem 主动完成：

- 调查直接竞品、间接替代品和已知失败尝试；
- 区分功能相似与问题定义相同；
- 查找用户抱怨、缺失场景和未满足需求；
- 提出最危险的反对意见；
- 定义可以推翻方向的淘汰条件；
- 给出 `PASS`、`PIVOT` 或 `REJECT` 的明确推荐。

规则：联网或关键证据不可用时，Validation 只能标记为不完整，不能声称“别人没做过”。

退出条件：验证为 `PASS`，差异化结论带来源和不确定性，用户确认进入 Plan。

### 6.4 Plan

一句话本质：把未来开发中最昂贵的决定提前做完，让开发 Agent 无需重新猜测需求。

Carpe Diem 逐段提出完整设计，而不是询问用户从空白开始设计。固定顺序为：

1. 项目定位、目标用户、核心场景和非目标；
2. 用户体验、功能范围和版本边界；
3. 架构、模块、数据流和接口；
4. 错误处理、安全和隐私；
5. 测试、验证和验收标准；
6. 里程碑、任务拆分和依赖；
7. 开源协议、贡献方式和发布路径。

每一部分必须包含推荐、理由、示例和取舍，讲完整后再询问是否需要修正。

退出条件：正式计划无空白占位、无内部矛盾，每个里程碑都有验收标准，用户批准最终计划。

### 6.5 Handoff

一句话本质：计划已经完成，Carpe Diem 从这里开始停止开发职责。

Carpe Diem 生成：

- `docs/project-plan.md`：正式实施计划；
- `docs/project-handoff.md`：开发 Agent 的精简交接包；
- `.carpe-diem/project-state.json`：本地当前状态；
- `.carpe-diem/events/` 下的首个计划批准事件。

以上文件只在用户批准最终计划后写入。写入前必须展示目标路径和内容摘要；Carpe Diem 不在此步骤创建业务源码，也不产生 Git 提交。

交接包必须说明第一个里程碑、验收标准、允许修改的范围、非目标、已知风险、需要保留的用户决定，以及完成后如何调用 Carpe Diem 跟进。

### 6.6 Track

一句话本质：对照计划和证据看清真实进度，不做监督式催促，也不越界开发。

每次用户重新调用 Carpe Diem 时：

1. 读取个人画像、项目状态和正式计划；
2. 回顾上次阶段、结论和下一步；
3. 只读检查 Git HEAD、提交历史、分支和工作区状态；
4. 读取已有测试、CI 或 Issue 证据；
5. 区分“已完成”“声称完成”和“有证据完成”；
6. 对照里程碑记录新增进展和偏差；
7. 给出当前判断、风险和下一阶段开发交接建议；
8. 只有需要改变正式计划时才请求用户批准。

Track 不主动运行项目测试。它只读取已有结果或用户明确提供的证据，避免测试过程产生未预期的工作区改动。

## 7. Skill 架构

仓库根目录本身就是可安装 Skill：

```text
carpe-diem/
├── SKILL.md
├── manifest.json
├── README.md
├── LICENSE
├── CONTRIBUTING.md
├── CODE_OF_CONDUCT.md
├── references/
│   ├── methodology.md
│   ├── state-schema.md
│   ├── safety-boundaries.md
│   └── stages/
│       ├── discover.md
│       ├── validate.md
│       ├── plan.md
│       └── track.md
├── templates/
│   ├── project-plan.md
│   ├── project-handoff.md
│   └── progress-summary.md
├── scripts/
│   └── carpe_diem.py
├── adapters/
│   ├── codex/
│   ├── claude-code/
│   ├── cursor/
│   └── openclaw/
└── tests/
```

### 7.1 `SKILL.md`

只负责身份、触发条件、合作契约、阶段判断、安全边界和渐进路由。它不复制完整方法论。

### 7.2 `references/`

走到某个阶段才加载对应文件。方法文件是权威来源，适配器不得维护分叉版本。

### 7.3 `scripts/carpe_diem.py`

v0.1 使用 Python 3.10+ 标准库实现一个内部确定性工具。它不是独立 AI CLI，不进行模型调用。子命令负责：

- `state read/propose/apply/forget/export`；
- `project init/status/event`；
- `evidence git`；
- `plan validate/diff`；
- `install detect/plan/apply/verify/uninstall`；
- `doctor`。

脚本无法运行时，Skill 允许继续进行纯对话 Discover 与 Plan，但必须明确说明本地记忆和自动证据能力已降级。

### 7.4 `adapters/`

适配器只处理安装位置、平台工具名、选择题呈现和能力降级。所有平台使用同一个核心 Skill 快照和同一个状态协议。

## 8. 双层本地记忆

### 8.1 个人长期画像

位置：

```text
~/.carpe-diem/profiles/me.json
```

顶层字段：

```json
{
  "schema_version": 1,
  "handle": "me",
  "strengths": [],
  "interests": [],
  "recurring_frictions": [],
  "constraints": [],
  "project_preferences": [],
  "working_style": [],
  "project_history": [],
  "consents": [],
  "updated_at": ""
}
```

每条画像包含 `value`、`kind`、`confidence`、`basis`、`confirmed_at` 和 `last_used_at`。`kind` 为 `observed`、`inferred` 或 `explicit`；只有用户确认的条目可以长期影响推荐。

个人画像不进入项目 Git，不包含原始简历、完整笔记、完整聊天或源代码副本。

### 8.2 项目状态

位置：

```text
.carpe-diem/project-state.json
```

顶层字段：

```json
{
  "schema_version": 1,
  "project_id": "",
  "phase": "discover",
  "direction": null,
  "candidates": [],
  "rejected_candidates": [],
  "validation": {},
  "decisions": [],
  "plan": {},
  "milestones": [],
  "deviations": [],
  "evidence": [],
  "next_recommended": "",
  "last_observed_git_head": null,
  "revision": 1,
  "updated_at": ""
}
```

`.carpe-diem/` 默认加入 `.gitignore`。新增忽略规则前必须展示 Diff 并获得用户确认；如果用户拒绝，状态改存到用户级项目目录并明确说明。团队若要共享状态，必须显式导出经过清理的便携摘要，不能直接提交个人本地状态。

### 8.3 事件历史

每次有效跟进产生一个不可变的本地事件文件：

```text
.carpe-diem/events/YYYY-MM-DDTHH-MM-SS.json
```

事件只保存时间、前后 Git 引用、里程碑变化、证据引用、偏差、用户决定和下一步建议，不保存完整 Diff 或完整聊天。

### 8.4 写入规则

- 长期画像变化前展示候选 Diff。
- 画像推断必须经用户确认才成为长期事实。
- 项目客观进度可生成草稿，写入前展示摘要。
- 正式计划修改必须单独确认。
- 使用临时文件和原子替换。
- 每次写入增加 `revision`；旧 revision 写入被拒绝并重新合并。
- 用户可以查看、解释、纠正、遗忘、导出或重置状态。

## 9. 授权、隐私与安全

### 9.1 渐进授权

默认只使用当前对话。需要更多证据时，按顺序邀请用户选择性开放：

- GitHub 公开活动和仓库；
- 指定本地目录；
- 指定笔记或未完成项目；
- 明确允许的 Issue、CI 或任务来源。

授权记录包含来源、目标、只读范围、授权时间和有效期。默认有效期为当前会话；长期授权必须明确选择。

### 9.2 永不保存

- API Key、Token、密码和凭据；
- 完整聊天记录；
- 未授权文件内容；
- 原始简历或私人笔记；
- 源代码副本；
- Agent 的隐藏推理过程；
- 便携导出中的本机绝对路径。

### 9.3 开发跟踪安全

Track 阶段保持只读，不修改业务源码、不执行项目脚本、不改变 Git 状态。Carpe Diem 只允许修改正式计划、交接文档和自己的本地状态；正式计划和交接文档的修改均需用户确认。

## 10. 正式产物格式

### 10.1 `docs/project-plan.md`

固定章节：

1. 摘要与问题；
2. 目标用户与核心场景；
3. 价值假设和差异化证据；
4. 目标与非目标；
5. 用户体验和功能范围；
6. 架构、组件、数据流和接口；
7. 错误处理、安全和隐私；
8. 测试和验收；
9. 里程碑、任务和依赖；
10. 风险与降级；
11. 开源、贡献和发布方式；
12. 关键决策记录。

### 10.2 `docs/project-handoff.md`

固定包含：当前目标、第一个里程碑、允许修改范围、禁止范围、已确认决策、验收命令或证据要求、风险、完成后报告格式，以及重新调用 Carpe Diem 的说明。

### 10.3 进度摘要

每次 Track 回复遵循：

1. 已完成内容及证据；
2. 当前里程碑状态；
3. 与计划的差异；
4. 风险和阻塞；
5. Carpe Diem 的判断；
6. 下一阶段开发交接建议；
7. 需要用户拍板的唯一问题（若有）。

## 11. 分发与跨 Agent 兼容

首版正式目标：Codex、Claude Code、Cursor、OpenClaw。

仓库提供各平台明确的安装、卸载和验证说明。辅助安装器可以检测平台、展示目标位置、等待确认、复制同一个版本快照，并重新扫描确认 Skill 可见。

兼容性原则：

- 核心方法只维护一份；
- 相同 `name` 和触发描述；
- 相同状态格式；
- 相同计划模板；
- 相同安全边界；
- 平台差异必须在适配器内显式降级。

安装验证以“目标 Agent 实际发现并能触发 Skill”为完成标准，复制文件本身不算安装成功。

## 12. 错误处理与降级

- 无联网搜索：Validation 标记为不完整，禁止原创声明。
- 无 GitHub 权限：只使用公开信息，私有状态由用户补充。
- 无终端：允许 Discover 和 Plan，禁用自动状态与 Git 证据。
- 非 Git 仓库：允许发现和规划，Track 暂不启动。
- Python 3.10 不可用：进入无脚本降级模式，生成可复制的恢复摘要。
- 本地状态不可写：明确说明未保存，不得假装记忆成功。
- 状态损坏：保留原文件，只读进入恢复模式，不静默覆盖。
- Schema 不兼容：展示迁移预览，确认后迁移。
- 两个 Agent 并发写入：通过 `revision` 拒绝旧写入并重新合并。
- 正式计划与状态矛盾：展示差异，以用户确认的正式计划为准。
- 仓库移动或改名：通过 Git 身份提出重新关联，用户确认后处理。
- 脏工作区：Track 保持只读，不试图清理或恢复用户改动。

## 13. 测试策略

### 13.1 结构测试

检查 frontmatter、manifest、引用文件、模板、脚本和相对路径完整性。

### 13.2 状态单元测试

覆盖首次创建、原子写入、画像 Diff、纠正、遗忘、导出、revision 冲突、损坏恢复和版本迁移。

### 13.3 场景测试

固定场景包括：

- 完全没有想法的新用户；
- 已有模糊方向的用户；
- 方向验证失败后转向；
- 计划完成后交接开发；
- 开发中途偏离计划；
- 从另一种 Agent 恢复项目；
- 项目暂停后重新开始。

### 13.4 沟通质量测试

每份黄金对话检查：

- 是否先给价值再提问；
- 是否避免连续盘问；
- 是否给出明确建议；
- 是否说明判断依据；
- 是否一次只留下一个真实选择；
- 是否在用户打断后回到主线；
- 是否按阶段写入状态；
- 是否避免越界开发。

### 13.5 跨 Agent 契约测试

Codex、Claude Code、Cursor、OpenClaw 分别验证：发现、触发、渐进加载、共享个人画像、恢复项目状态、交互降级、职责边界和真实卸载。

### 13.6 安全测试

验证 Track 不修改业务源码、不提交 Git、不运行未知项目脚本、不上传文件、不把个人画像写入仓库，并且计划变更前一定产生可审阅 Diff。

## 14. v0.1 内测

### 14.1 第一轮：冷启动价值

在空仓库中，由没有明确想法的用户调用 Carpe Diem。验证引导是否先给判断、候选是否来自真实上下文、是否排除同质化方向，以及用户是否产生“值得继续”的明确感受。

### 14.2 第二轮：计划与交接

选择方向后完成 Validate 和 Plan。验证差异化证据、计划完整性、里程碑验收标准、开发 Agent 是否无需重新询问核心需求，以及 Carpe Diem 是否停止在规划边界。

### 14.3 第三轮：跨 Agent 续接与跟踪

由开发 Agent 完成部分开发，再从另一 Agent 调用 Carpe Diem。验证状态续接、Git 证据判断、范围偏移识别和不越界开发。

### 14.4 评分维度

每项 1 至 5 分：

- `Relevance`：方向与用户的真实关联；
- `Novelty`：有证据的独特切口；
- `Guidance`：被带领而非被审问；
- `Clarity`：计划清晰程度；
- `Handoff`：开发 Agent 可直接接手；
- `Continuity`：跨 Agent 无损续接；
- `Trust`：记忆、授权和边界透明。

通过标准：

- 无未经证据支持的原创声明；
- 用户无需重新讲述核心上下文；
- 开发 Agent 无需重新决定项目定位；
- Carpe Diem 未修改业务代码；
- 用户明确认为最终方向值得开始；
- `Guidance`、`Clarity`、`Handoff` 均不低于 4 分。

重点失败信号：随机创意感、连续问卷、记忆未影响判断、竞品列表没有结论、计划无法执行、跨 Agent 丢失状态或阶段、Carpe Diem 越界开发。

## 15. v0.1 范围与非目标

v0.1 必须交付：

- 可安装的根 Skill；
- 四阶段 Playbook；
- 沟通方法内核；
- 双层本地记忆；
- 渐进授权；
- 计划与交接模板；
- 只读 Git 证据；
- 状态查看、纠正、遗忘和恢复；
- 四个目标 Agent 的安装与契约验证；
- 三轮内测记录方式。

v0.1 不交付：

- 自带模型；
- Web UI；
- MCP 或后台服务；
- 业务代码开发；
- 自动执行项目计划；
- 自动提交或 Issue 管理；
- 定时主动唤醒；
- 团队云同步；
- 商业化和付费功能。

## 16. 开源约定

v0.1 采用 Apache-2.0 许可证，以便开放复用并保留明确的专利授权条款。仓库提供贡献指南、行为准则、Issue 模板和可复现的 Skill 结构与契约测试。

社区贡献优先接受：新的 Agent 安装适配器、真实内测案例、沟通质量修正、状态兼容性和更可靠的验证方法。不得以平台专属分叉的方式复制核心方法。

## 17. 成功定义

Carpe Diem v0.1 的成功不是 Star 数，也不是生成了多少点子。成功是：

> 一个原本没有项目头绪的人，在被真正带领、被现实证据约束并保有最终决定权的情况下，形成一个愿意开始的项目方向和可直接交接的实施计划；开发开始后，他可以在不同 Agent 中回来继续，而不必重新解释自己和项目。
