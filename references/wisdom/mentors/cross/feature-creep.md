# 行为卡：功能蔓延

> 触发条件：规划阶段功能列表不断增长，或用户说"这个功能加上去应该会有人用"

## 问题本质

每个新功能都看起来"很合理"——用户提的需求、竞品有的功能、团队觉得"可能会有用"的创意——但累积起来的结果是：产品越来越臃肿、维护成本越来越高、核心价值越来越模糊。

问题的根源是：**你把"功能数量"当成了"产品价值"的衡量标准**。更多的功能不等于更好的产品。实际上，每个新功能都带来三个成本：开发成本（做这个功能的时间）、维护成本（持续修复和兼容的成本）、认知成本（用户理解和使用这个功能的难度）。当功能数量超过某个阈值后，每加一个功能，产品的整体价值反而下降——因为用户找不到核心功能、产品变得难以使用、维护成本吞噬了所有开发资源。

## 触发条件

用户正在执行以下任一操作时触发：

- **场景一：规划阶段功能列表不断增长，但从未删减过**。如果用户每次讨论都是"再加一个功能"，而从未主动删减过功能，说明他正在经历功能蔓延——每个新功能都被接受了，但没有人问"这个功能值得删掉哪个功能来换取？"

- **场景二：用户说"这个功能加上去应该会有人用"**。如果用户用"可能有人用"作为加功能的理由，说明他还没有区分"有人会用的功能"和"产品核心需要的功能"。大多数功能都有人用——但问题是，这个功能是否值得用产品的复杂度来换取。

- **场景三：用户因为"竞品有"或"用户要求"而添加功能，但没有评估这个功能是否符合产品定位**。如果用户加功能的理由是"别人都有"或"有人提了"，而不是"这个功能强化了我们的核心价值"，说明他正在被动响应外部需求，而不是主动塑造产品。

- **场景四：用户说"先加上去，后面可以关掉"或"先做出来再说"**。如果用户用"可以关掉"或"先做出来"作为加功能的理由，说明他低估了功能的长期成本。功能一旦做出来，就不容易关掉——用户可能依赖它、团队可能维护它、删除它可能引起用户不满。

## 行为指导

### 1. 每个新功能必须回答"它解决什么核心问题"

在决定加一个功能之前，先问清楚：这个功能解决什么核心问题？如果答案模糊，就是不要做的信号。

判断标准：
- "用户需要导出数据" → 清晰的问题（用户需要用自己的数据做分析）
- "用户可能需要这个" → 模糊的问题（你猜的用户需求）
- "竞品都有这个功能" → 不是问题（竞品有≠用户需要）
- "加一个分享功能可以增加传播" → 模糊的问题（分享不是问题，用户为什么愿意分享才是问题）

只有当你能够用一句话说清楚"这个功能解决什么具体问题"时，才考虑加这个功能。

### 2. 加一个功能前先想删一个功能

这是一个硬约束：**每次加一个新功能，必须先删一个旧功能**。如果你找不到可以删的功能，说明你现在手头的功能都已经是最小集了——不需要加新功能。

具体做法：
- 列出所有功能，按"使用频率"和"核心价值"排序
- 如果找不到要删的功能，重新审视候选功能的价值——它真的比现有某个功能更重要吗？
- 如果所有功能都"不能删"——说明产品功能已经饱和，不需要再加

### 3. 用"不做清单"管理被拒绝的需求

"不做清单"不是"以后再说"的清单，而是"明确决定不做"的清单。这个清单的价值在于：
- 记录你为什么不做某个功能（避免以后反复讨论同个需求）
- 让团队看到"我们拒绝了很多东西"（避免认为"产品功能不够全"）
- 让用户看到"我们做了选择"（而不是"还没做"）

具体做法：
- 创建一个"不做清单"文档
- 每个条目包含：功能名称、拒绝理由、拒绝日期
- 定期审视——如果拒绝理由不再成立，可以重新考虑；但大多数情况下，拒绝理由依然成立

### 4. 区分"用户想要"和"产品需要"

用户想要的功能是"对我有帮助"——这类功能非常多，每个用户都有自己的需求。产品需要的功能是"没有这个功能，产品核心价值无法实现"——这类功能很少。

判断方法：
- 问"没有这个功能，用户的核心任务能否完成？"
- 如果能完成（只是不够方便），这个功能是"用户想要"的
- 如果不能完成，这个功能是"产品需要"的
- 优先做"产品需要"的，推迟做"用户想要"的

### 5. 定期审视功能使用率，删除低使用率功能

功能蔓延不是一次性问题，而是持续累积的过程。需要定期审视功能使用率，主动删除低使用率的功能。

具体做法：
- 每季度审视一次功能使用率
- 对每个功能，问"过去 30 天内有多少用户使用了这个功能？"
- 如果使用率低于某个阈值（如低于 5% 的用户使用），考虑删除
- 删除前，主动通知受影响用户，给他们适应时间
- 删除后，记录删除原因——如果未来有人问"为什么没有这个功能"，可以直接回答

### 6. 问"如果没有这个功能，用户会流失吗？"

这是最严格的筛选条件：如果一个功能被删除，用户是否会因此流失？如果答案是"不会"，这个功能就不是必须的。

具体做法：
- 对每个候选功能，问"如果这个功能不存在，用户会离开吗？"
- 如果答案是"会"——这个功能是核心功能，值得做
- 如果答案是"可能会"——这个功能很重要，但不是必须的，可以先做核心功能
- 如果答案是"不会"——这个功能不是必须的，不要做

## 不适用场景

- **平台型产品**：如果用户正在构建一个平台型产品（如电商平台、开发者平台、应用市场），功能的丰富度本身就是产品价值的一部分。平台需要提供足够多的功能来满足不同用户群体的需求——在这种场景下，适度的功能扩展是必要的。但即使如此，仍然需要区分"核心功能"和"扩展功能"，并确保核心功能不因功能扩展而被稀释。

- **企业定制需求**：如果用户正在服务企业客户，并且企业客户明确要求某些特定功能作为采购条件，那么这些功能属于"必须做"的范畴——即使它们不是核心功能。企业客户的需求是硬性约束，需要在合同范围内满足。但需要注意：企业定制功能应该与企业客户的合同绑定，而不是成为产品的永久功能（除非它们有广泛的通用价值）。

- **合规性需求**：如果用户需要添加的功能是为了满足法律法规、安全标准、行业合规或平台政策要求，这些功能不能拒绝。合规性需求是硬性约束，不属于"功能决策"的范畴——即使它们增加产品复杂度，也必须实现。

- **用户处于快速实验阶段（找 PMF 之前）**：如果用户还在寻找产品-市场匹配的阶段，需要快速尝试不同的功能和方向来找到"什么有用"。在这个阶段，"功能蔓延"的担忧不应该阻碍实验——关键是快速验证、快速放弃、快速学习。功能蔓延的约束应该在 PMF 确认后、产品需要规模化时启用。
